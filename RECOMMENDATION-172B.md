# Recommendation — SPEC 172B

## 1. Verdict

Build a **Linux-only, bounded Git-ref side-channel using Bun 1.3.14's built-in `node:fs.watch`, reconciled from the engine's physical repo discovery**. Parcel's Linux defect is specifically that its live directory-add path watches only the newly reported directory and never crawls children that already exist; Bun's pinned implementation does both the initial recursive walk and a descendant walk after a newly created/moved directory, and it owns an inotify fd separate from Parcel's working-tree queue. Watch only the positive ref surface (`gitDir/HEAD`, `commonDir/packed-refs`, `commonDir/refs/stash`, and recursive `commonDir/refs/{heads,tags}`), deduplicate shared Git dirs, cap the registry, route every hit through the existing signal debouncer, and perform an arm-then-push handshake. Leave macOS on the existing single workspace FSEvents stream. Keep the Linux 60-second safety floor for every eligible, pending, failed, or over-cap repo because Bun still has silent descendant-add and queue-overflow cases. This is candidate C, refined around the actual Bun runtime rather than Node's abstract API contract.

## 2. Mechanism

### The actual Parcel mechanism

The corrected diagnosis is the classic recursive-establishment hole, not an ignore mismatch and not primarily overflow. On Linux, Parcel's **initial** subscription calls `getTree`, whose FTS walk physically traverses the root, applies the watcher's ignore predicate, skips ignored subtrees, and adds every admitted entry; `subscribe` then calls `watchDir` for every directory in that tree (`node_modules/@parcel/watcher/src/linux/InotifyBackend.cc:66-79`; `node_modules/@parcel/watcher/src/unix/fts.cc:19-47`).

The live path is materially different. For `IN_CREATE | IN_MOVED_TO`, `handleSubscription` constructs the one reported path, applies `watcher->isIgnored`, `lstat`s it, adds only that entry to the cached tree, and—if it is a directory—calls `watchDir` only on that directory (`node_modules/@parcel/watcher/src/linux/InotifyBackend.cc:151-183`). `watchDir` only calls `inotify_add_watch` and records the `(tree, path, watcher)` subscription; it performs no enumeration (`node_modules/@parcel/watcher/src/linux/InotifyBackend.cc:81-94`). Therefore, if `git init` creates `.git/refs/heads` before Parcel processes and arms the watches on `.git` and `.git/refs`, those already-present grandchildren never enter Parcel's tree and never receive descriptors. A populated repo moved into the workspace is deterministic: `IN_MOVED_TO` takes the same one-directory path, so Parcel watches the moved repo root but does not discover its existing `.git` descendants.

The ignore hypothesis is ruled out by source. Both paths call the same `Watcher::isIgnored` (`node_modules/@parcel/watcher/src/unix/fts.cc:40-43`; `node_modules/@parcel/watcher/src/linux/InotifyBackend.cc:151-163`), and the JS wrapper normalizes each `ignore` entry once into either a resolved path or a picomatch regex before passing those options to the binding (`node_modules/@parcel/watcher/wrapper.js:5-37,55-64`). Within `.git`, rbox excludes only `.git/objects` and `.git/logs` from Parcel's native tree, not `.git`, `refs`, or `refs/heads` (`src/engine/ignore.ts:211-226`). The missing ref watch is consequently an arrival-order/no-recrawl bug.

Overflow remains a real secondary fault: Parcel explicitly discards `IN_Q_OVERFLOW` (`node_modules/@parcel/watcher/src/linux/InotifyBackend.cc:96-123`). Initial `inotify_add_watch` failure rejects subscription (`node_modules/@parcel/watcher/src/linux/InotifyBackend.cc:71-76`; `node_modules/@parcel/watcher/src/binding.cc:183-189`), but the same failure during a live directory add removes the new tree node and returns without an error or retry (`node_modules/@parcel/watcher/src/linux/InotifyBackend.cc:178-183`). That distinction explains why restarting the daemon heals coverage while a live failed subtree stays uncovered until that directory is recreated, the watcher is rearmed, or the daemon restarts.

The rig symptom matches this mechanism but does not establish it by itself. The seeded repo's empty commit was event-driven in 3.484 seconds; a three-file repo created after daemon start had an event-driven working-tree commit, then its empty commit took 38.972 seconds and had a safety scan before capture (`scripts/rig/runs/20260720-230123-git-commit-propagation/report.md:50-57,67-82`). The big new repo likewise had a 6.689-second event-driven working-tree commit and a scan-bound empty commit (`scripts/rig/runs/20260720-230123-git-commit-propagation/report.md:83-99`). Tiny-repo reproduction eliminates queue overflow as the primary cause; Parcel source identifies the permanent missing-descendant mechanism.

### The proposed side-channel

The implementation should add a `GitRefWatchRegistry` with these responsibilities:

1. **Authoritative input.** Feed it the physical repo contexts produced by ordinary Git discovery/capture, not `manifest.gitRepos` keys. `discoverGitRepos` is the exact ignore-pruned physical walk (`src/engine/git-discover.ts:28-52`), the ordinary push planner already invokes it on every Git-enabled plan (`src/cli/sync-git/plan.ts:243-258`), and `repoCtxFromDisk` already resolves each repo's per-worktree `gitDir` and shared `commonDir` without a subprocess (`src/engine/git/shared.ts:281-328`). The present watcher uses discovery only once to compute an immutable startup boolean (`src/cli/daemon/watcher.ts:267-272,324-344`); the missing seam is to return the discovered contexts to the live watcher after each plan.

2. **Prompt discovery of every new shape.** A new outer repo directory or atomic move already yields an ordinary Parcel file batch, which drives a plan and discovery. Also classify a created/moved `.git` directory or pointer **before** the sync matcher as a repo-candidate signal, because `git init` inside an already-existing directory may otherwise create no ordinary syncable file. That signal requests a Git-aware push/discovery but never creates a `WatchEvent`, never calls `onRawEvent`, and never enters `pendingEvents`—the same separation currently enforced for ref signals (`src/cli/daemon/watcher.ts:289-316`; `src/cli/daemon/daemon.ts:553-576`).

3. **Positive watch roots.** On Linux, and only when the main backend is Parcel, maintain:
   - one shallow watcher on each unique `gitDir`, accepting `HEAD` and `HEAD.lock`;
   - one shallow watcher on each unique `commonDir`, accepting `packed-refs` and `packed-refs.lock` and noticing creation/replacement of `refs`;
   - one shallow watcher on each existing `commonDir/refs`, accepting `stash`/`stash.lock` and noticing creation/replacement of `heads` and `tags`;
   - recursive watchers on existing `commonDir/refs/heads` and `commonDir/refs/tags`.

   This never watches objects, logs, remotes, or rbox scratch refs. Shared common dirs for worktrees/submodules are reference-counted; only per-worktree `gitDir/HEAD` handles remain distinct. Canonical targets outside the workspace stay scan-bound rather than expanding rbox's watch authority beyond the sync root. Reftable remains scan-bound, matching the existing classifier (`src/engine/ignore.ts:160-170`).

4. **Use Bun's missing operation.** The release and CI toolchains pin Bun 1.3.14 (`.github/workflows/release.yml:43-46`; `.github/workflows/ci.yml:66-69`). Its Linux `fs.watch` manager creates its own process-global inotify fd and reader thread, initially walks recursive roots, and adds a descriptor per directory ([`path_watcher.zig:419-477`](https://github.com/oven-sh/bun/blob/bun-v1.3.14/src/runtime/node/path_watcher.zig#L419-L477), [`path_watcher.zig:524-533`](https://github.com/oven-sh/bun/blob/bun-v1.3.14/src/runtime/node/path_watcher.zig#L524-L533)). Crucially, when a new/moved directory appears under a recursive root, Bun adds that directory **and then walks its already-present descendants** ([`path_watcher.zig:659-670`](https://github.com/oven-sh/bun/blob/bun-v1.3.14/src/runtime/node/path_watcher.zig#L659-L670)). Parcel independently creates its own addon-owned inotify fd (`node_modules/@parcel/watcher/src/linux/InotifyBackend.cc:22-24`), so a Parcel working-tree arrival storm cannot fill the Bun ref-side queue. If the main backend is Chokidar, do not enable the side-channel: Chokidar also rides Bun `fs.watch`, so the queue-isolation advantage would disappear.

5. **Treat target locks as conservative pre-signals.** Bun suppresses same-kind events delivered within roughly one millisecond through per-handler duplicate suppression ([`path_watcher.zig:120-143`](https://github.com/oven-sh/bun/blob/bun-v1.3.14/src/runtime/node/path_watcher.zig#L120-L143)); in a local Bun 1.3.14 probe, `main.lock` was delivered while the immediately following `main` rename could be coalesced. Therefore a lock adjacent to an admitted target must wake the signal debouncer too. This may produce a harmless no-op push if a Git ref transaction aborts, but it avoids depending on the final rename being observable. Locks under remotes, scratch refs, objects, and logs are outside the watched roots. The quiet-period debounce normally fires after the ref transaction completes.

6. **Close the arming interval.** After all roots for a newly discovered or identity-replaced repo are armed, push the existing `SignalDebouncer` once. A ref mutation before arming is captured by this follow-up push; a mutation after arming produces a watch signal. This arm-then-push handshake is necessary—merely creating the handles after the plan would leave a small capture-to-arm gap.

7. **Reconcile and bound lifecycle.** Serialize reconciliation; cap desired repo contexts at the existing Git admission ceiling (`src/cli/sync-git/shared.ts:54-60`); key handles by canonical path plus shallow/recursive mode; and store `(dev, ino)` identity so delete/recreate at the same repo path forces detach and re-arm. Close handles whose last owning repo disappears. A failed attach stays in desired/pending state and retries with capped backoff on the next candidate, plan, or safety scan. `close()` fences any in-flight reconcile, closes every handle, and disposes the one shared signal debouncer.

8. **Keep the backstop dynamic.** Replace the startup snapshot meaning of `gitRefWatchActive` with a live `gitRefWatchRequired/Active` view. On Linux, any eligible repo—including attaching, failed, over-cap, or otherwise scan-bound—keeps `SAFETY_SYNC_MS` at 60 seconds (`src/cli/daemon/policy.ts:6,103-112`; current pin site `src/cli/daemon/daemon.ts:689-696`). A side-channel event is still only a push hint; scanner/manifest exclusion remains authoritative and unchanged (`src/engine/ignore.ts:288-306`).

| macOS + Parcel | No side-channel. Parcel creates a workspace-root FSEvents stream with file events, receives full item paths without per-directory `inotify_add_watch`, and surfaces dropped-stream conditions to its watcher (`node_modules/@parcel/watcher/src/macos/FSEventsBackend.cc:48-115,184-186,206-264,322-328`; `node_modules/@parcel/watcher/src/Watcher.cc:123-134`). | Existing event path; watcher error pins scan. Add a mac rig assertion before declaring parity proven. |
| Pointer repo with out-of-tree control dirs, reftable, or over-cap repo | No new external watch authority and no false promise of event coverage. | Explicitly scan-bound; 60-second Linux floor. |

## 3. Why not the others

### A. Dedicated Parcel subscription per repo

This is the best fallback, and it would fix the immediate new-repo case because a subscription rooted at a newly discovered `.git` gets Parcel's full initial FTS crawl. It does not, however, isolate bursts: Parcel obtains a process-shared backend for all subscriptions (`node_modules/@parcel/watcher/src/binding.cc:165-185`; `node_modules/@parcel/watcher/src/Backend.cc:24-27,71-84`), so the main workspace and every ref subscription share the same addon inotify fd and queue. Future nested branch/tag directories also re-enter the defective one-directory live path (`node_modules/@parcel/watcher/src/linux/InotifyBackend.cc:165-183`). On macOS it would create one extra FSEventStream per repo (`node_modules/@parcel/watcher/src/macos/FSEventsBackend.cc:206-264,322-328`) where the existing workspace stream already has the needed recursive semantics. A is less powerful than the Bun side-channel while requiring essentially the same repo registry and teardown logic.

### B. Restart/re-arm the main Parcel subscription after a miss

This heals only after scan latency, needs new trigger provenance to distinguish “scan caught a watcher miss” from ordinary coalesced push requests, and pays a full-workspace crawl. It is also trickier than “subscribe again”: watchers are shared by `(dir, ignorePaths, ignoreGlobs)` (`node_modules/@parcel/watcher/src/Watcher.cc:24-32`; `node_modules/@parcel/watcher/src/Watcher.hh:40-42`), the directory tree cache is keyed by root (`node_modules/@parcel/watcher/src/DirTree.cc:31-47`), and `getTree` does not reread a tree already marked complete (`node_modules/@parcel/watcher/src/shared/BruteForceBackend.cc:6-15`). A reliable rearm therefore requires a completed unsubscribe that releases the old tree, an exposed event gap, and another whole-workspace crawl—then it remains vulnerable to the next dynamic directory and silent overflow.

### D. Polling, Watchman, upgrading, or patching Parcel

A correct poll is not a handful of `stat`s: symbolic `HEAD` does not change on an ordinary branch commit, and a shallow `refs/heads` directory stat misses updates inside nested branch namespaces. rbox's existing complete common-dir fingerprint recursively walks every loose ref and hashes small ref files (`src/cli/sync-git/fingerprint.ts:157-168,204-224`), so running it every 1–2 seconds is O(total refs), permanent disk wakeup, and unnecessary on idle repos. Watchman adds an external service/dependency. An upgrade is not presently a fix: [Parcel 2.6.0's tagged Linux source](https://github.com/parcel-bundler/watcher/blob/v2.6.0/src/linux/InotifyBackend.cc#L66-L184) retains the same initial-vs-dynamic logic and silent overflow, while its [release note](https://github.com/parcel-bundler/watcher/releases/tag/v2.6.0) concerns RegExp ignores. Upstreaming a native Parcel fix is worthwhile, but a race-free recursive-add algorithm and prebuilt binaries for both Linux release architectures would make rbox maintain a native fork in the meantime. The Bun side-channel uses an already pinned shipping primitive and remains small enough to test as a runtime contract.

## 5. Implementation sketch

Estimated production change: roughly 300–450 lines; tests roughly 250–400 lines.

- **New `src/cli/daemon/git-ref-watch.ts` (~200–260 lines):** bounded registry, `RepoCtx` canonicalization and in-root check, shared-root refcounts, shallow/recursive `FSWatcher` handles, positive filename/lock filtering, root-lifecycle attachment, retry state, identity replacement, reconcile/close fencing, and one callback into the existing signal debouncer.
- **`src/cli/daemon/watcher.ts` (~60–100 lines):** construct the registry only for Linux+Parcel, expose `reconcileGitRefs(contexts)` and live required/active state on `Watcher`, recognize `.git` repo candidates before matcher filtering, keep all side-channel activity outside file batching, and close registry plus both debouncers.
- **`src/cli/sync-git/plan.ts` and `src/cli/sync/push.ts` (~30–60 lines):** return the authoritative discovered physical contexts (bounded and resolved once) through the internal push result; do not infer them from the wire manifest.
- **`src/cli/daemon/daemon.ts` (~30–60 lines):** reconcile after each completed plan and safety discovery, request the arm-handshake push, keep desired/failed refs pinned to the Linux floor, and make repo-candidate events request discovery without touching `pendingEvents`.
- **`docs/CODEMAP.md`:** add the new module's one-line ownership boundary, required for a new module under `src/cli/daemon/` (`docs/CODEMAP.md:84-98`).
- **`scripts/rig/Dockerfile`:** update the stale Bun 1.3.5 device pin to the release/CI 1.3.14 runtime before using the rig as proof (`scripts/rig/Dockerfile:8-23`). This is load-bearing because the recommendation relies on the 1.3.14 dynamic descendant walk.
- **No scanner/manifest change:** `BUILTIN_IGNORE`, `isHardExcluded`, manifest generation, upload, and apply receipt remain untouched. `.git` bytes never become file events or synced content.

Tests that prove the design:

1. Start the daemon watcher first, `git init` a tiny repo afterward, reconcile the returned repo context, make an empty commit, and require a Git signal in under 10 seconds with `settled`, raw events, and `pendingEvents` all empty.
2. Initialize Git inside an already-existing workspace directory and at the workspace root; the `.git` repo-candidate path must cause discovery, arm, and a follow-up push.
3. Move a fully populated repo into the workspace atomically, then empty-commit after convergence; prove the ref side-channel is event-driven.
4. Create first-time nested branch/tag namespaces rapidly (`refs/heads/a/b`, `refs/tags/a/b`); accept target lock pre-signals, prove the eventual push sees the new ref, and prove no `.lock` path enters the file plane.
5. Cover detached/worktree `HEAD`, `packed-refs`, stash, branch/tag delete, missing-then-created `refs/{heads,tags}`, shared-common-dir dedupe, pointer repos, and out-of-root refusal.
6. Inject root attach failure, runtime `error`, repo removal/recreation at the same relPath, over-cap input, reconcile races, and close during attach. Every case must stay at the 60-second floor and retry without leaking handles.
7. Add a compiled Bun 1.3.14 runtime contract test for initial recursive attach, dynamic descendant recrawl, and target-lock delivery. A Bun upgrade must pass this test before release.
8. On macOS, prove no side-channel handles are created and add a post-daemon new-repo empty-commit test against the existing FSEvents stream.
9. Tighten both corrected rig rounds from `degrade-bounded` to `event-driven`: `small-repo-empty` and `big-repo-empty` must show capture before any `safety scan:` and remain under the existing 30-second coarse ceiling (`scripts/rig/scenarios/git-commit-propagation.ts:193-200,245-257,443-462,504-519`). Run `bun run rig` with the rebuilt 1.3.14 image; unit tests alone are not acceptance.

## 6. Risks and first validation

The largest risk is reliance on Bun implementation details beyond portable `fs.watch`. That is acceptable only because release and CI pin Bun 1.3.14 and because a compiled contract test can make the dependency executable rather than tribal knowledge. The second risk is target-lock pre-signaling: aborted ref transactions may cause no-op pushes, while a ref lock held longer than the debounce window can cause an early push; measure no-op rate under commit, rebase, fetch, tag, stash, and failed-lock workloads, and retain the safety floor for a missing final event. Third, the registry has a bounded number of JS handles but recursive heads/tags still consume one kernel descriptor per namespace directory; measure descriptors, RSS, attach wall time, and teardown at 1, 100, and the configured maximum repo count. Fourth, Bun still silently ignores descendant-add failures and likely overflow, so do not advertise perfect watcher health or relax the 60-second floor.

Validate the narrow runtime premise first, before threading discovery through the daemon: in a compiled Bun 1.3.14 harness, arm the proposed four-root layout after (a) fast `git init`, (b) atomic move-in, and (c) creation of a nested branch directory whose child already exists when the callback runs. Run each repeatedly while flooding the separate Parcel workspace watcher. The pass condition is that the Bun side receives a target or target-lock signal and a debounced read observes the new ref, with no ref path entering a file batch. Only after that passes should implementation proceed to the repo-map seam and full rig.
