# The 10x hunt: single-carrier sync

**Date:** 2026-08-18
**Baseline:** `main` at `d20cf1c` (277 Slice B landed, Slice A not yet in tree)
**Field anchor:** `docs/design/data/277-baseline-2026-08-17.md`
**Status:** Search only — no implementation. Every claim carries file:line evidence
from this working tree.

## The finding in one paragraph

For a one-file change, the information that must cross the network is about
3 KB: a signed commit (~2 KB), a manifest-delta envelope (~0.6 KB), and one
small ciphertext. Today the sender moves **5.09 MB across 8 strictly serialized
round trips** — 99.94% of it a refset sidecar the receiver never reads — and at
the exact moment the server accepts the commit, the Durable Object is **holding
the complete signed commit in a local variable** (`stored`,
`apps/api/src/workspace-sync.ts:708`) and broadcasts a three-field doorbell
instead (`:760-763`), forcing the receiver into **5 more serialized round
trips** to rediscover what the server just had in hand. The 10x is to let the
change ride the carriers it already passes through: **one commit POST carries
the whole change up; one WS frame carries the whole change down.** None of the
four slices below appears anywhere in the 200+ design docs, the audits, the
proposals, or the issue trail — verified by a dedicated sweep. Combined with
the already-planned work (277 Slice A, #775), the small-change propagation
critical path becomes: 400 ms debounce → encrypt (already done, slice 4) → one
commit RTT → fanout → O(change) apply. **~2–3 s end-to-end against today's
measured 41–51 s.**

## Where the numbers stand (so the prize is judged against the right base)

From the 277 baseline and STATUS: desktop zero-change push 7.2–7.7 s, content
push 17.0 s; Mac receive ~9 s; FM pull 51–63 s; observed e2e propagation
41–51 s against the ≤10 s founder target. Planned work already owns a large
share: 277 Slice A (state loads, ~5–7 s/host), #775 (bundle refetch 12–17 s +
CAS acquire 11–12 s on FM), 235 Phase B (un-ratified O(N) receiver passes).
**Even after all of that lands, the cycle keeps its wire shape: 8 sender RTTs,
5.09 MB uplink, 5 receiver RTTs, and a serialized notify→pull→fetch chain.
That wire shape is the unclaimed 10x.** It is also the part that no amount of
state-plane optimization touches, and it is what stands between the fleet and
low-single-digit-seconds propagation.

## The current wire, measured against a one-file change

Sender (all strictly serialized; sites verified):

| # | Request | Size | Why it exists |
|---|---|---:|---|

| 2 | `POST /v1/blob-batch/put` (`src/cli/remote/blob-batch/uploader.ts:295`) | ciphertext | the real payload |
| 3 | `POST …/receipts/redeem` (`sync-recovery.ts:507`) | ~300 B | receipt could ride the commit |

Server, per commit: two full-sidecar R2 GETs with SHA-256 over ~4.5 MB each

`POST /v1/blob-batch/get` (`e2ee-remote.ts:504-533`, `sync/pull.ts:83-110`,
`engine/apply.ts:353`). Five RTTs, ~1 KB of actual payload.

## The proposal: single-carrier sync, four slices

Each slice stands alone, ships behind its own kill switch, and degrades to
today's path on any mismatch. Together they collapse the wire to its
information content.

### S1 — Broadcast the envelope (receiver 5 RTTs → 2, zero server I/O)

Send `{type:"committed", sequence, deviceId, commit: <SignedCommit>}`. The DO
serializes exactly these bytes into KV two lines above the broadcast
(`workspace-sync.ts:708,714-740,760`); attaching them costs nothing. A
steady-state receiver whose pin equals `parentSeq` verifies the signature and
hash chain locally (`e2ee-remote.ts:519-527`) and skips `/latest` and
`/commits?since` entirely. Because the commit body names `encManifestSha` and
`manifestChain`, the delta-envelope GET and the account-keys refresh can be
issued in parallel the moment the frame arrives.

This overturns design 105's "notify-only, never data" invariant — deliberately,
and on the invariant's own stated terms. Its security rationale (105 §3.2) is
that a frame's capability must not exceed what polling `/latest` already
grants. The SignedCommit envelope **is** the `/latest` response body
(`workspace-sync.ts:1305-1311`): same bytes, same E2EE opacity (the server
cannot read it today and still can't). The "never correctness" half survives
untouched: the frame stays best-effort, the receiver treats the payload as a
verified hint, and any signature/chain/pin mismatch falls back to the full pull
— exactly today's degraded path. Two real checks before shipping: (a) device
revocation must close live sockets so the long-lived connection can't outlive
the `/latest` capability it mirrors — the purge path (`apps/api/src/ws-purge.ts`)
is the place to prove that; (b) a frame-size guard for the inline-`blobRefs`
mode (<4000 refs), where the body can approach the 1 MiB `MAX_COMMIT_BODY`.

### S2 — Take the refset off the wire (5.08 MB → ~100 B per commit)

The server already computes `parent ∆ child` itself (`commit-delta.ts:40-95`)
and already refuses commits whose delta doesn't validate — enforce mode is
live. The client, meanwhile, knows its exact ref delta for free: it is the
manifest delta it already encodes. Replace the per-commit full-refset upload
(`e2ee-remote.ts:772-781`) with a signed **refset-delta descriptor**
(added/removed refs + parent refset hash); the server applies it to its stored
parent refset, persists the child set in the DO-side root state it already owns
(`seq_roots` / `dropped_index`, `workspace-sync.ts:246-248`), and periodically
requires a full-set checkpoint (reusing the design-84 snapshot cadence,
`MAX_MANIFEST_DELTA_CHAIN = 16`) so recovery and GC keep an anchored root.

Removes per content commit: the 5.08 MB uplink (99.94% of bytes), client-side
serialize/sort/hash of 127k refs (`refset.ts:94-112`), both hot-path 4.5 MB R2
GETs + SHA-256 passes, and the alarm fold's third GET — the fold becomes
O(change). This is the residual design 84 §6.1 explicitly scoped out to "a
companion design" that was never written; the enforcement machinery it needs is
already deployed. Estimated 1.5–2.5 s off every content push (`p1.7` server
phase + `sidecarMs` + upload wall on non-symmetric links) and the largest
single de-scaling of the whole protocol: commit cost finally stops growing with
workspace size anywhere.

### S3 — One-RTT publish (sender 8 RTTs → 2)

- Inline the ~0.6 KB delta envelope in the commit POST body. `MAX_REQUEST_BODY`
  is 8 MiB measured on bytes actually read (`commit-envelope.ts:17-26`), so
  budget is a non-issue. The DO stores it next to `seq:<n>` and — with S1 —
  echoes it in the frame, making the receiver's remaining fetch just the file
  blob.
- Receipts ride the commit body instead of two separate redeem POSTs
  (`commit-accounting.ts:137-147` already accepts receipt-backed refs; this
  moves where the receipt arrives, not what it proves).
- Drop the `blobs/check` preflight for addresses this push just minted; keep it
  for carried/recovery addresses (the delta-preflight machinery,
  `sync-recovery.ts:68,320-329`, already knows the difference). The 422 +
  bounded-repair path remains the backstop, unchanged.
- Issue `GET /v1/keys/account` concurrently with the upload lane; it is
  independent of everything before signing (`e2ee-remote.ts:952-957` argues
  freshness, not ordering). Also mint the download/upload grants on the commit
  response and frame (grants are stateless HMAC, `grants.ts:128-131`), so no
  request ever exists solely to refresh a grant.

Result: blob PUT ∥ keys GET, then one commit POST. 3–6 WAN RTTs removed per
push, and the WAN-RTT count stops depending on protocol ceremony.

### S4 — Spend the debounce window (the never-considered speculative lane)

The 400 ms quiet / 3 s burst debounce (`watcher.ts:330-331`) is treated purely
as quiescence today; nothing overlaps it. Both halves are safe to overlap
because the primitives are already idempotent:

- **Sender:** on the first watcher event, start encrypting the touched paths
  and optimistically batch-PUT the ciphertext. Content-addressed writes are
  idempotent and receipt-minting is stateless; a file that changes again before
  quiesce wastes one small upload (bounded by a byte budget), and the commit
  simply references whichever address the final scan proves. By the time the
  debounce fires and the plan is built, the bytes are already durable
  server-side — encrypt+upload leaves the critical path entirely.
- **Receiver:** on frame arrival, before the mutex/dequeue (`wake("notify")` →
  pull can wait behind an in-flight op; priority `deepScan > fullScan > pull`),
  prefetch the commit/delta/blob into a staging cache so the pull op starts
  with bytes in hand. With S1+S3 the frame already carries the first two, and
  the prefetch is just the blob batch-GET. This attacks the measured
  `notify_latency_ms` class of waits without touching scheduler semantics —
  design 232 §6 rejected *preemption*; prefetch needs none.

### What the critical path becomes

debounce 400 ms → commit POST (1 RTT; bytes already uploaded) → DO CAS +
fanout (alarm arming moved after fanout — today a storage RTT sits between
acceptance and notify, `workspace-sync.ts:758-760`) → frame carries
commit+delta → receiver applies O(change) → parallel blob GET already in
flight. With 277 Slice A and #775 landing as planned, ~1.5–3 s e2e on every
host. Against today's 41–51 s that is >10x; against the fully-optimized
planned world (~15–20 s) it is still the only route under the ≤10 s target
with margin.

## Secondary finds — concrete wastes in no design, issue, or ledger

Surfaced during the trace; none appears in 277/#775/235/268 or the backlog:

1. **A fifth full state materialization.** 277 §0 counts four; `daemonBindingMatches`
   (`daemon.ts:1637` → `sync-state.ts:511` → adapter) unconditionally
   materializes all 127k entries **to read two scalars** (`stream`,
   `stateNonce`). Worth ~1.8 s/cycle on its own and invisible to 277's
   red-first count test as written.
2. **`matcherForState` rebuilt per pull** (`sync/pull.ts:244`): with
   `respectGitignore`, construction runs a synchronous full-tree `readdirSync`
   walk plus ~107 `git rev-parse` spawns (`engine/ignore.ts:581-586,678-698,729`)
   — on the event loop, uninstrumented by any span. The daemon holds a
   correctly-guarded matcher (`daemon.ts:2872-2892`) that pull ignores.
   Est. 1–3 s/pull; threading `deps.matcher` is cheap.
3. **`DirCache.load` on scan-free pulls**: the daemon passes `cache` but not
   `dircache` (`daemon.ts:2170`), so every trusted-view pull re-parses and
   re-validates the full dircache JSON. ~0.1–0.3 s; one-line class of fix.
4. **`EncryptAddressCache` full-file rewrite per push**: one `record()` marks
   dirty → `flush()` in the `finally` (`sync-recovery.ts:532`) rewrites and
   fsyncs the entire ~127k-entry JSON, with `toJSON` re-sorting every key
   (`engine/encrypt-address-cache.ts:200-225`) — tens of MB for a one-entry
   change, hidden in unattributed phase gaps. Also re-loaded twice per no-op
   push (`push.ts:680` → `sync-recovery.ts:121`).
5. **Commit-encode redundancy** (~1 s of the measured 1.7 s `encodeMs` +
   the 1.1 s `delta_base`): `encodeDeltaEnvelope` re-validates both manifests
   it was handed and recomputes a diff the caller already holds
   (`engine/manifest-delta.ts:360-362` vs `publish-candidate.ts:250`);
   `delta_base` re-validates + re-hashes a base whose canonical hash is already
   persisted as `state.manifestMeta.manifestHash` (`push.ts:758-777`), with a
   memo that is per-op instead of per-`(stateRevision, encManifestSha)`.
6. **267's elision asymmetry on the receiver**: one file action defeats the
   global no-op audit (`sync-state-elision.ts:101-113`), so all 107 repo
   transitions are recomposed and restaged for a 1-file receive
   (`sync-state.ts:315-326`). A per-record elision predicate decoupled from
   the global one recovers it.
7. **The WS reliability cliff that caps every latency win**: `ws-fanout.ts:39`
   swallows per-socket send errors; `remote-wakeup-channel.ts:232` drops
   frames outright while `!ready`; recovery is the 45 s cursor or the 300 s
   backstop. Any single-digit-seconds propagation story needs a delivery-gap
   detector faster than 45 s (e.g., the frame carrying `parentSeq` — free
   under S1 — turns every frame into its own gap detector: receiving seq N
   with parent ≠ pin proves a miss immediately).

## Crazy-ideas appendix (checked against the corpus; unexplored)

- **LAN peer transfer between own hosts** (desktop↔Mac are frequently
  co-located): zero prior consideration anywhere. Post-S1–S4 it is unnecessary
  for small-change latency; it remains the only lever that beats WAN physics
  for multi-GB blob movement. Park until a large-blob corpus exists.
- **Incremental/Merkle manifest hash**: `resultHash` is the one
  architecturally O(N) term left in the delta protocol — writer and every
  reader recompute a full canonical hash per delta
  (`manifest-delta.ts:365,558`); design 84 §6.1 books it as "the accepted
  residual." A rolling/tree hash makes fold O(change) end-to-end. Wire-format
  change; sequence after S2. (Merkle-for-refsets was twice the losing branch
  historically — this is a different, narrower use.)
- **Connection warmth**: no measurement exists of TLS/TCP setup share across
  the cycle's request burst. Mostly mooted by S3's RTT collapse; worth one
  instrumented number before dismissing.

## Suggested gates (falsifiable)

- S1: steady receiver performs ≤2 requests per received commit; frame-carried
  commit byte-identical to `/latest`; revocation closes sockets (test).
- S2: content-commit uplink ≤ ciphertext + 4 KB; server hot path performs zero
  full-sidecar reads; GC/fence/recovery suites green against delta-maintained
  root state; checkpoint cadence bounds worst-case recovery reads.
- S3: one-file push performs exactly 2 requests (blob PUT ∥ keys, commit);
  409/422/repair paths byte-identical.
- S4: publish→frame wall on a quiet host ≤ debounce + 1 RTT + server accept;
  wasted-upload bytes bounded and metered.
- Combined: cross-host 1-file propagation p50 ≤3 s on desktop→Mac, e2e rig
  regression-pinned.
