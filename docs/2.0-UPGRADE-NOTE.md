# Upgrading rbox to 2.0

**Draft for founder review — not sent yet.** The user-facing part is written to
the non-developer copy bar. The appendix is for the founder only.

---

rbox 2.0 changes one thing you will notice: rbox now keeps a list of which
folders on this computer it is allowed to sync, and that list is the boss.
Older versions worked it out on the fly. The upgrade needs one extra command to
write that list for the first time.

Do this on **each computer**, one at a time. It takes about a minute.

**1. Get the new version**

```
curl -fsSL https://rbox.to/install.sh | sh
```

**2. Write the folder list**

```
rbox config regenerate
```

It prints a short warning and asks `Replace the current rbox folder
configuration? [y/N]` — press `y`. Then it prints the folders it found. **Check
that every folder you sync on this computer is in that list.** If one is
missing, add it:

```
rbox config add /path/to/that/folder
```

**3. Restart background sync**

In each synced folder:

```
rbox stop && rbox start
```

That's it.

## What to expect

- **Downtime: seconds.** Your files are never touched. Nothing is uploaded
  again and nothing is downloaded again.
- **One quiet catch-up.** The first time the new version starts, it re-reads
  the files in your folder to rebuild an internal index it can no longer reuse.
  On a big folder this can keep a CPU busy for a few minutes. It does **not**
  re-upload anything and it does not use your bandwidth.
- **No re-login.** You do not need your recovery phrase, and you do not need to
  pair or approve anything again.
- **Your other computers keep working** while you upgrade, on whatever version
  they are on. There is no rush to do them all at once.

## What NOT to do

- **Don't delete anything in `.rbox`** — not `state.json`, not the `state`
  folder. If rbox ever says a file was written by a newer version, that message
  means "leave it alone and upgrade", never "delete it".
- **Don't skip step 3.** Until you restart it, the background sync on that
  computer is still running the old version. `rbox status` will tell you so.
- **Don't go back to an older version.** There is no supported way back down,
  and an older rbox will refuse to touch a folder the new one has already
  converted.

## If something looks wrong

**"rbox folder configuration is absent; run `rbox config regenerate`"**
This is the expected message if you restarted sync before step 2. Run
`rbox config regenerate`, press `y`, then `rbox stop && rbox start` in that
folder.

**A folder stopped syncing and you don't know why**
The folder list from step 2 probably missed it. Run `rbox config` to see the
list, and `rbox config add /path/to/the/folder` for anything missing. Then
`rbox stop && rbox start` in it. Nothing was deleted — that folder was simply
sitting still.

**`rbox status` says the background sync is on an older version**
Run `rbox stop && rbox start` in that folder. That's step 3.

**You moved a synced folder to a new place on this computer**
Run `rbox config repair /new/path`. It refuses if the old folder still exists,
so move it rather than copying it.

If none of that fits, run `rbox doctor` in the folder and send the output.

# Appendix for the operator (founder)

Every claim below is anchored to code read in this checkout (`main`, at
`26806c02f`) or to `CHANGELOG.md`. Anchors were opened and read, not relayed.

## A1. The one that actually bites: `rbox upgrade` leaves sync DOWN

`rbox upgrade` does stop → convert state → restart, per workspace
(`src/cli/upgrade-cmd.ts:176-197`). The restart goes through
`resumeDesiredDaemon(row.desired, { startDaemon: start })` at
`src/cli/upgrade-cmd.ts:202` — note it passes **no** `trustedFolderAdmission`,
so `src/cli/autostart/daemon-state.ts:71` runs
`await requireFolderAdmission(abs)`, which calls `ensureFolderAuthority`
(`src/cli/autostart/folder-admission-gate.ts:5-10`). On a 1.11.4 machine there
is no `~/.rbox/config.json` but there are discoverable bindings, so
`src/cli/folder-authority.ts:17-19` throws
`rbox folder configuration is absent; run \`rbox config regenerate\``
(`src/cli/folder-catalog-publish.ts:179`).

Net effect of a bare `rbox upgrade` on a 1.11.4 host:

1. binary swapped and committed (no rollback of the swap),
2. every live daemon **stopped**,
3. state **converted to SQLite** (see A2) — one-way,
4. restart fails: `daemon <key>: restart failed; run rbox stop && rbox start in
   that workspace` (`src/cli/upgrade-cmd.ts:209`),
5. command throws `UpgradeDaemonRestartError` → exit 1
   (`src/cli/upgrade-cmd.ts:90-94,145`).

Sync stays down on that host until someone runs `rbox config regenerate --yes`
and `rbox start`. This is why the user-facing note above recommends the
**installer** path, not `rbox upgrade`: the installer is a pure binary swap
(`scripts/install.sh:83-87`), the old daemon keeps running and syncing until
the user restarts it, and the folder list gets written before anything stops.

Design 231 anticipated the manual step (`docs/design/231-folder-config-authority.md:747`,
"The founder upgrades or re-onboards the three external users") — it just isn't
wired into the upgrade command.

**Decision due:** either accept the installer-first recipe above as the
published upgrade path, or fix `rbox upgrade` to regenerate (or to refuse
before stopping anything, which is strictly better than stopping and failing).

## A2. State plane: converted by `rbox upgrade`, not by the daemon

- The daemon **never** converts. `establishStateAuthority` has exactly two
  production callers: `src/cli/state-plane-cmd.ts:100` (`rbox migrate`) and
  `src/cli/upgrade-state-window.ts:91` (the upgrade stop window). A 2.0 daemon
  started against 1.11.4 JSON reads it unchanged — `selectSqliteAuthority`
  returns `undefined` unless the authority marker is present
  (`src/cli/state-plane/adapters/whole-state-compat.ts:59-66`), and `undefined`
  means "legacy JSON is authority".
- Nothing is discarded or rebuilt. On migration the legacy document is kept as
  two preamble-prefixed copies under `.rbox/state/legacy-json/`
  (`src/cli/state-plane/paths.ts:50-58`), deliberately non-parseable so a stale
  base can't be copied back.
- Migration is admitted for a genuine 1.11.4 workspace: the downgrade floor is
  `BARRIER_DOWNGRADE_FLOOR = "1.11.0"`
  (`src/cli/state-plane/migration/last-writer-witness.ts:25`) and 1.11.4
  maintains the witness.
- Refusals during the upgrade window are silent by design
  (`src/cli/upgrade-state-window.ts`, `worthSaying`); only a `blocked` refusal
  prints one line. Conversion failure never blocks the restart
  (`src/cli/upgrade-cmd.ts:186-196`).
- **Consequence:** installer-path users stay on legacy JSON indefinitely and
  remain downgradable; `rbox upgrade` users are converted and are not.
  **Decision due:** do we want 2.0 stable to actually flip everyone to SQLite
  (then the recipe must include `rbox migrate`), or is JSON-until-they-run-
  upgrade acceptable for GA?

## A3. One-time hashcache discard — real, silent, local only

`src/engine/hashcache.ts:125-130`: if the caller supplies an expected
`gitPolicy` and the file records none, the whole cache is dropped. A 1.11.4
`hashcache.json` has no `gitPolicy` key (the field is new on the 2.0 line), so
the first 2.0 **daemon** start discards it — the daemon is the only loader that
passes a policy (`src/cli/daemon/daemon.ts:835` +
`hashCachePolicy()` at `daemon.ts:3283-3285`; `status-read-port.ts`,
`sync/deps.ts`, `ignore-cmd.ts` pass none).

Cost: a full local re-hash on the next scan. **Not** a re-upload — the sync base
in `state.json` is untouched, and re-hashing unchanged files reproduces
identical sha256s, so the push diff is empty. There is no user-visible message
and no test pinning "discard ⇒ zero uploads"; the no-upload claim is read off
the code path, not measured. On the Mac's large workspace this is the most
likely source of an "rbox is pegging my CPU after the upgrade" report.

## A5. Manual-fix steps per breaking change

**B1 — folder config authority absent (design 231, #632).** Every 1.11.4
machine hits this. Symptom: `rbox folder configuration is absent; run
\`rbox config regenerate\`` from `rbox sync`/`start`/`config`/`ignore`/`track`
and from daemon construction (`src/cli/daemon/daemon.ts:3683-3687`);
`rbox status` does **not** surface it (`src/cli/status-projection.ts:160-161`
falls back to the binding's own options and no renderer consumes `admission`) —
a machine can look healthy in `status` while refusing to start.
Fix, in order:

```
rbox config regenerate --yes     # or interactive; --json is rejected
rbox config                      # verify every synced folder is listed
rbox config add <path>           # for anything missing
rbox stop && rbox start          # per folder
```

Regenerate reconstructs from bindings — sorted by path, labels from basenames
with ` (2)` disambiguation, per-folder policy snapshotted from the binding,
global options reset to product defaults
(`src/cli/folder-catalog-generate.ts:87-117`). It cannot recover labels,
ordering, global defaults, or inheritance choices; it says so verbatim
(`folder-catalog-generate.ts:132`).

Two sharp edges worth knowing before the users hit them:

- Regenerate calls `observeFolderGeneration(state)` **without** `currentRoot`
  (`src/cli/folder-config-cmd.ts:110`), unlike every other caller. Evidence is
  the union of catalog paths + registry rows + daemon desired rows
  (`src/cli/folder-inventory-union.ts:190-198`). A real binding whose registry
  row and desired row are both gone is neither generated nor listed under
  "Bindings that will be omitted" — it silently becomes `detached` and stops
  syncing. That's the reason step 2 of the user note says "check the list".
- At login, `bootResume` skips non-admitted roots with a log line only
  (`src/cli/autostart/boot-resume.ts:37-41`) and, on a catalog-absent machine,
  aborts the whole resume before the loop (`boot-resume.ts:33`). Nothing
  reaches the terminal.

Damaged (as opposed to absent) catalogs get their own copy:
`rbox folder configuration is damaged: <reason>. Copy ~/.rbox/config.json
somewhere safe, then run \`rbox config regenerate\`.`
(`src/cli/folder-catalog-publish.ts:174-180`).

**B2 — moved folder.** `rbox config repair <newpath>`, non-interactive and
crash-convergent. It refuses if the same workspace+device binding still exists
elsewhere, and refuses if the old path still exists ("refusing to guess whether
this is a copy") — `src/cli/folder-repair-cmd.ts:107-131`.

**B3 — someone downgrades after a conversion.** Message:
`<file> was written by a newer version of rbox that stores sync state in a
database. This version cannot read or replace it. Upgrade rbox (\`rbox
upgrade\`); never delete this file.` (`src/cli/state-plane/errors.ts:30-34`).
Fix: reinstall 2.0. There is no un-migrate path in the tree. Do not delete the
records.

**B4 — beta users stay on `next` forever.** The channel is persisted at
`<exe>.channel.json` (`src/cli/upgrade-channel.ts:16`) and stable publication
never writes the `next` channel (`docs/DEPLOYMENTS.md`, `scripts/release.ts`).
A user on 2.0.0-beta.2 running bare `rbox upgrade` after v2.0.0 is tagged gets
`already up to date (2.0.0-beta.2)` — indefinitely. Fix:
`rbox upgrade --channel latest`, or run the stable installer (which deletes the
channel file, `scripts/install.sh:85-87`). Related wart: `rbox doctor` always
queries the **stable** manifest regardless of channel
(`src/cli/doctor-cmd.ts:394-405`), so those users see "update available (2.0.0)"
while `rbox upgrade` says they're current. Worth fixing before GA or the beta
users will report it.

**B5 — rollback.** Not supported. `install.sh` takes no version pin
(`scripts/install.sh:6-8,30-31`); `rbox upgrade` takes no version argument and
is structurally forward-only via the floor in `<exe>.release.json`
(`src/cli/upgrade-cmd.ts:400,454`). Immutable versioned artifacts do exist at
`$BASE/bin/v<version>/…`, so a hand rollback is physically possible, but after
one it prints `verified upgrade floor is 2.0.0; this process is 1.11.4 — run
\`rbox upgrade\` again from a fresh shell` (`src/cli/upgrade-cmd.ts:70`), and
if state was converted it is blocked by B3 anyway.

## A6. Never tested — say this out loud before the tag

- **No mixed-binary test exists anywhere in this repo.** The compat matrix
  builds its "legacy workspace" with today's code
  (`src/cli/state-plane/compat-matrix.test.ts:57-65`), and the real row is a
  todo: `test.todo("dual-binary rig: signed v1.11.0 over a candidate-migrated
  workspace (fleet rig owns this)")` (`compat-matrix.test.ts:271`). Same gap in
  the crash matrix: `test.skip("F3/F6 require the published signed 1.10.x /
  1.11.0 binaries in the rig")` (`migration/crash-matrix.test.ts:410`), with an
  explicit "do not replace this with a hand-built fixture". `scripts/rig/`
  drives multiple devices from **one** build.
- Therefore every "verified compatible" in A4 is verified **by reading the
  diff**, not by running a 1.11.4 binary against a 2.0 one. That is a real
  standard of evidence, but it is not a passing test.
- No test covers the hashcache discard as an upgrade scenario (loading a
  policy-less 1.11.4-shaped file with an expected policy).
- The full 1.11.4 → 2.0 sequence in this note has **not been executed
  end-to-end**. The A1 failure was traced through code, not observed.

Cheapest thing that would close most of this: one rig scenario that installs a
real signed v1.11.4, syncs, swaps in the candidate binary, and runs the recipe.

1. **OPEN — does 2.0 stable intend to convert everyone's state?** Installer
   path leaves them on legacy JSON; `rbox upgrade` converts. Product decision,
   not a code question. It determines whether the published recipe includes
   `rbox migrate`.
2. **OPEN — is the A1 `rbox upgrade` behavior acceptable, or a blocker?**
   Stopping sync and exiting 1 on every existing install is a bad first
   impression for the 2 less-technical users. Fix vs document is a founder call.
3. **OPEN — do the 4 external users have folders whose registry AND desired
   rows are gone?** If so, regenerate omits them with no warning (B1, edge 1).
   Only checkable per host, not from this repo.
4. **OPEN — real-world cost of the hashcache re-hash** on the largest external
   workspace. Never measured; only the code path is known.
5. **OPEN — does the 2.0 push-conflict surrender (120s) starve a 2.0 machine
   against a 1.11.4 peer that has no matching surrender?** Needs the two-binary
   rig; unreachable by reading.
6. **OPEN — does RboxBar surface the absent-catalog refusal**, or does the menu
   bar just look idle? Not searched under the app sources.
7. **OPEN — which of the 4 users are on `next` today** (B4 applies to them and
   not to the others). Answerable from `rbox device list` /
   `devices.last_seen_version` in prod, not from the repo.
8. **OPEN — is there any third caller of `establishStateAuthority`** beyond the
   two found? Both known call sites were read; no exhaustive proof of absence.
