Client design decisions

  • Zero-knowledge by construction — encrypt below the sync seam; server stores opaque blobs + a signed commit.
  • Content-addressed + convergent — identical content → identical encSha → free dedup; blobRefs are the unique blob set.
  • Ignore-first watching — the watcher prunes ignored dirs, so npm ci emits zero events. Daemon stays O(changed).
  • Tunable concurrency — RBOX_{UPLOAD,DOWNLOAD,ENCRYPT}_CONCURRENCY.

Client bottlenecks & status

  • Sequential blob transfer — FIXED: worker pool, default 32 (measured knee).
  • Empty/dup-file edges — FIXED: tag-only decrypt + unique temp names + blobRef dedup.
  • Encrypt double-pass — re-hashes plaintext the scan already hashed. Suspect; bench before refactor.
  • Chain verify — history-linear on pull; needs a verified-checkpoint cache past some depth.

Server design decisions

  • Durable Object as the sequencer — commit ordering needs strong consistency; that's why it's a DO, not KV (KV is eventually consistent → split-brain).
  • R2 content-addressed blobs — sha-verified on PUT; convergent ciphertext dedups across the account.
  • D1 for metadata only — composite PKs cover the hot queries (commits by seq, blob_refs by account+sha). Indexes are not the bottleneck.
  • Opaque to the server — it reads a few commit fields for validation, never decrypts.

Server bottlenecks & next work

  • Per-blob D1 writes — each PUT = R2 + 2 D1 writes; 1041 blobs ≈ 2082 D1 round-trips. conc=4 already threw D1 "connection lost". NEXT: batch ref/entitlement writes (D1 batch() or move to commit-time).
  • Commit body size — blobRefs inlined in the signed body; 1 MB cap is interim. Move them to a side R2 object referenced by hash → unlocks 50k-file monorepos.
  • Async candidates (Queues) — GC of superseded blobs, usage aggregation off the commit hot path, webhook retry. Not transfer speed — robustness/cost.
  • Observability gap — no server timing today; can't attribute R2 vs D1 vs DO. Workers Analytics Engine + per-op spans (planned).
