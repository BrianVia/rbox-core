# Adversarial review — Design 125 daemon log rotation

1. **BLOCKING — The design has no viable owner or initialization point for the rotating fd.** `render.log` is currently a rootless module function (`src/cli/daemon/render.ts:4`), while the runtime root exists in `runDaemon`; `runDaemon` also performs `buildAuthedRemote` and `loadState` before constructing the daemon (`src/cli/daemon/daemon.ts:2150-2154`). A process-global configured logger would make direct `RboxDaemon` tests and concurrent tests share the wrong root. **Concrete fix:** specify a per-daemon `RotatingDaemonLogger(root, clock, fs)` created at the beginning of `runDaemon`, inject its bound sink into `RboxDaemon` and downstream logging seams, and close/drain it after the final stop line. Explicitly classify failures before logger initialization as crash-sink-only.

2. **BLOCKING — The fd lifecycle does not guarantee whole, ordered records across rollover.** Every current call site treats `log()` as synchronous/fire-and-forget. If the replacement uses async `FileHandle.write`, callbacks can overlap, a date transition can close an fd with an earlier write pending, and short writes can tear a line. Computing the filename and ISO timestamp from separate clock reads can also put a next-day timestamp in the prior-day file. **Concrete fix:** mandate either synchronous `openSync`/`writeSync`/`closeSync` with `O_APPEND` and one complete UTF-8 record per write syscall (handling short writes), or one serialized async queue that orders date selection, open, write, close, and shutdown drain. Capture one `Date` per record for both timestamp and filename. Add native-Bun tests for simultaneous calls, a midnight boundary, short writes, write failure, and close ordering.

3. **BLOCKING — Two launchers can spawn two daemons, but the design silently assumes one writer.** `startDaemon` checks the pid and later spawns/writes the pidfile without an atomic launch claim (`src/cli/daemon-control.ts:273-327`), so concurrent `rbox start`s can both pass. Two processes may then write and prune the same daily files. **Concrete fix:** either add launch serialization/atomic ownership as part of this design, or make and test the log protocol explicitly multi-process-safe: `O_APPEND`, exactly one syscall per line, no rename/truncate of dated files, prune closed dates only, benign `ENOENT` between pruners, and boot-id/PID on boot records. Include a real two-process rollover/prune test.

4. **BLOCKING — `daemon.log` is not a crash-only sink today; ordinary daemon output bypasses `log()`.** The reachable bypasses are: top-level rejected `runDaemon` errors through `fail` (`src/cli/index.ts:23-31`); stream-mismatch warnings (`src/cli/config.ts:552-557`); E2EE applied-head lag (`src/cli/e2ee-remote.ts:683-688`); changing-file deferrals, including full path lists under `RBOX_DEBUG` (`src/cli/sync-recovery.ts:534-536`); publish-pipeline encryption churn (`src/cli/publish-pipeline/shared.ts:62-66`); recovered blob-integrity events (`src/cli/remote/blobs.ts:140-144`); downloader debug and liveness-watchdog output (`src/cli/remote/blob-batch/downloader.ts:13-15,138-143`); multipart metrics' default sink (`src/cli/remote/multipart-metrics.ts:37-41`); macOS bulk-walk warnings (`src/engine/darwin-bulk-walk.ts:84-90`); crypto worker fd-cap/spawn warnings (`src/engine/crypto-pool/config.ts:59-62`, `src/engine/crypto-pool/pool.ts:210-220`); and git ref-equivalence warnings whose engine default remains `console.warn` (`src/engine/git/apply.ts:91,406,539`). Bun/runtime diagnostics, panics, and uncaught failures bypass it as intended. **Concrete fix:** enumerate this inventory in the design and route operational/metrics warnings through the injected daemon logger, including an engine warning sink. Reserve inherited stdio for front-door/runtime fatal diagnostics. If any potentially repeated operational/debug emitters intentionally remain, the crash sink itself needs rotation or a startup size cap; the claim that it stays small is otherwise false.

5. **BLOCKING — Treating the crash sink as a fallback hides exactly the failures it exists to preserve.** Once any dated file exists, the proposed `rbox logs` order selects it and ignores a later startup failure, uncaught exception, or panic appended to `daemon.log`; `doctor` currently follows the same first-success rule (`src/cli/doctor-cmd.ts:503-506`). This is especially bad when a new boot fails before creating today's file. **Concrete fix:** model `daemon.log` as a concurrent channel, not a fallback. Specify how an initial `rbox logs` tail and diagnostics include bounded crash-sink output alongside the active dated stream, and make `--follow` monitor both with unambiguous source markers or another explicit merge policy. Add crash-after-dated-file and fail-before-dated-file tests.

6. **BLOCKING — “Re-checks for a date rollover” is not a lossless follow contract.** The current follower binds one pathname forever and only handles same-path shrink (`src/cli/daemon-control.ts:456-477`). Switching as soon as a new file appears can lose final bytes in the old file; staying on the old path misses the new stream. It must also promote from crash-only or legacy sources when a dated stream appears. **Concrete fix:** specify a polled source-state machine. The writer publishes the new pathname only after the old fd is closed; the reader keeps its old handle, drains it to stable EOF, then opens the new file at offset zero, while independently monitoring the crash sink. Test final-old plus first-new records, crash-to-dated and legacy-to-dated promotion, disappearance/recreation, and signal cleanup.

7. **BLOCKING — The pointer line becomes stale after the first UTC rollover and has undefined failure ordering.** “First `log()` line each boot” points to the boot-day file for a daemon that runs for days. The design also does not say whether the pointer is written before or after the dated open succeeds, so it can advertise a nonexistent file. **Concrete fix:** after every successful startup/rollover open, synchronously write a boot/transition pointer containing basename, boot id, PID, and timestamp to the crash sink before/with the first dated record. On open failure write a failure diagnostic, not a pointer. Test multi-day uptime and an initial open failure.

8. **BLOCKING — Retention is not safe under the stated name-pattern plus mtime rule.** `daemon-*.log` matches unrelated names; `stat` follows symlinks; mtime can be old on a restored current-day file (causing the live pathname to be unlinked) or future (retained forever); and `readdir`/`stat`/`unlink` races with replacement. An open Unix fd can keep accepting invisible writes after unlink. **Concrete fix:** use an anchored `^daemon-(\d{4})-(\d{2})-(\d{2})\.log$`, validate it as a real UTC calendar date, `lstat` and accept regular files only, never prune the current/open basename, and base age on UTC filename dates. If mtime remains, require both an old filename date and old `lstat` mtime so it is only a conservative secondary gate. Treat only concurrent `ENOENT` as benign. Test junk/invalid names, symlinks, old mtime on today, future mtime, and disappearance/replacement races.

9. **BLOCKING — Existing direct readers outside `rbox logs` are omitted and will silently break.** `readStarvationWarning` opens `daemonLogPath(root)` to derive status locking health (`src/cli/sync-mutex.ts:55-75`); after this change it reads the quiet crash sink and may report `ok` during starvation. Doctor tails `daemonLogPaths` (`src/cli/doctor-cmd.ts:503-506`). The rig harvest/classification scripts glob only `*/daemon.log` (`scripts/rig/lib/capture.ts:435-441`, `scripts/rig/lib/device.ts:286-295`), so design validation can lose the daemon stream and watcher-mode evidence. **Concrete fix:** audit every direct `daemonLogPath`/`daemon.log` reader, move status and doctor to a shared resolver/channel abstraction, and update rig capture/classification to collect ordered dated logs plus crash sink. Rename the old helper to `daemonCrashLogPath` so it cannot keep masquerading as the operational stream. Add dated/rollover tests for status, doctor redaction, and rig capture.

10. **BLOCKING — “Directory vanished → write fails → stdout” is false with a kept-open Unix fd.** `removeDaemonRuntime` recursively unlinks the directory (`src/cli/daemon-control.ts:152-155`), but the existing fd can continue to accept writes into an unlinked inode until rotation or exit; manually deleting today's file behaves similarly. The fallback never runs and logs disappear. **Concrete fix:** prove and enforce that runtime removal happens only after process exit, and separately define manual-unlink behavior; or detect `fstat().nlink === 0` / path-to-fd identity mismatch and reopen before writing. Add unlink-while-open and untrack tests.

11. **BLOCKING — The repoMs cap removes forensic distributions that this repository has actually used.** The current entry carries independent queue, wall, result/group, and fresh-chain component timings (`src/cli/sync-git/apply.ts:88-101,143-151,1077-1088`). Design 83 diagnosed a uniform 85–195 ms subprocess floor and queue ramp toward 1.5 s from the full 98-entry line (`docs/design/83-git-plan-fingerprint-cache.md:33-39`); design 74 explicitly requires per-repo queue/wall timings (`docs/design/74-pull-parallelism.md:55-69,158-164`); design 100 added chain decomposition for exactly this measurement plane (`docs/design/100-fresh-join-cold-apply.md:214-223`). Slowest eight by an undefined metric plus one suppressed maximum destroys the typical distribution and queue ramp. **Concrete fix:** retain bounded exemplars but add all-repo p50/p95/max for both queue and wall, and equivalent aggregates for each chain component when present. Select/deduplicate exemplars across highest wall, highest queue, and anomalous/non-unchanged results; define deterministic ties/order and do not mutate `repoTimings`. Test that these aggregates preserve the design 83 uniform-floor and queue-ramp shapes.

12. **SHOULD-FIX — “Newest dated file” is underspecified and legacy compatibility can select a stale stream.** `daemonLogPaths` is currently a synchronous static `{primary, legacy}` pair (`src/cli/daemon-control.ts:145-150`); discovering a dated file requires directory I/O. Mtime selection is touch-sensitive, while loose lexical selection admits invalid/future dates. Once a dated file exists, a later downgrade/legacy daemon writing `daemon.log` can also be hidden forever. **Concrete fix:** put a pure dated basename/path constructor in `rbox-paths.ts` and one async resolver in `daemon-control.ts` using calendar-valid names and explicitly defined date ordering. Define future-date and clock-rollback behavior and how an actively growing legacy/crash stream is distinguished from stale dated files.

13. **SHOULD-FIX — The current follow read loop has races that rollover work will amplify.** It stats a pathname, then opens it, allocates `st.size - offset`, ignores `bytesRead`, and advances to the stale stat size (`src/cli/daemon-control.ts:465-474`). Replacement between stat/open can emit zero-filled bytes or skip data. **Concrete fix:** open first, fstat that handle, loop until the intended range is read, emit only returned bytes, and track file identity/source generation. Keep handles in `finally`. Add replacement-between-stat/open and short-read seams.

14. **SHOULD-FIX — Follow lifecycle semantics are incomplete.** Today `rbox logs -f` returns immediately if no log exists (`src/cli/daemon-control.ts:434-442`), yet source promotion is now required. Conversely, after `untrack` removes the runtime, the current follower waits forever and can attach to a future workspace bound at the same root because `workspaceKey` is root-derived. **Concrete fix:** have follow-with-no-source wait and discover a subsequent boot, but capture workspace binding/boot/runtime generation and exit on untrack, binding change, or a new unrelated lifecycle. Test follow-before-start and untrack/re-init.

15. **SHOULD-FIX — The fallback is not guaranteed non-fatal.** Dated-file failure and inherited stdout can share the same ENOSPC/EIO condition, and Bun stream failures may surface asynchronously. Mixing direct fs writes with buffered `console.log` also leaves pointer/fallback ordering undefined. **Concrete fix:** define a best-effort sink that catches primary and fallback failures, suppresses/reports at most once without recursion, and never throws or rejects. If deterministic ordering matters, write directly to fd 1 rather than through `console.log`. Test simultaneous primary and fallback failure while daemon work continues.

16. **SHOULD-FIX — `RBOX_LOG_RETENTION_DAYS` parsing has no contract.** “Min 1” does not define empty, junk, fractional, `Infinity`, negative, or unsafe-large values; several of these can silently disable pruning. **Concrete fix:** specify a strict base-10 positive safe-integer parser, the invalid-value behavior (warning plus default 14 is reasonable), and an upper bound. Test absent, zero, negative, fraction, junk, infinity, and huge inputs.

17. **SHOULD-FIX — The repoMs escape hatch and acceptance gate name the wrong seam/operation.** The formatter is `formatGitApplyMetrics`, not `summarizeGitApply` (`src/cli/sync-git/apply.ts:138`), and existing `RBOX_DEBUG` convention is truthy rather than exact `=1` (`src/cli/http-error.ts:12`, `src/cli/sync-recovery.ts:536`). `repoMs` is emitted by pull-side git apply (`src/cli/sync/pull.ts:238-250`), so acceptance requiring an ordinary `rbox push` line is nondeterministic except when push happens to perform a recovery pull. **Concrete fix:** name the actual formatter, define debug truthiness consistently, note that a daemon must inherit the env at startup, and test capped versus debug-full output on a synthetic >8 timing set. Make field acceptance a pull/daemon-pull with >8 repos, not push.

18. **SHOULD-FIX — The design cites the wrong incidents as evidence for retaining repoMs.** STATUS attributes the ~35 Mbps uploader conclusion to raw R2 probes and upload slot/batch sweeps (`docs/STATUS.md:20,653-665`); `repoMs` is pull-side git apply. The append-hot move-aside incident was reconstructed from corrupt manifest tuples and rename/fd behavior (`docs/design/92-manifest-entry-integrity.md:20-80`), not repoMs. Design 93 itself contains no repoMs dependency; the actual consumers are designs 74, 83, and 100. **Concrete fix:** correct section 4's rationale and specify the queue, wall, result/group, and chain-distribution signals that the diet must preserve.

19. **NIT — “Spawn banner” is not written to the inherited sink, and the user-facing path will be misleading.** The banner at `src/cli/daemon-control.ts:328` is printed by the parent after spawn; only child stdout/stderr inherit the opened fd. It also tells the user that `daemon.log` is “logs” although the normal stream is moving elsewhere. **Concrete fix:** remove the spawn-banner claim or add an explicit child boot record, and change the start message to direct users to `rbox logs` (optionally mentioning the runtime directory) rather than presenting the crash sink as the live log.
