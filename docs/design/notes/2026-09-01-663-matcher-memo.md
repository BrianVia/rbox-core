# #663 — per-directory ignore-matcher memoization

*Design note, 2026-09-01. Evidence read on main @ `d8d2658e9`. No code changed.*

## The problem

The scan asks the ignore matcher about every entry it sees, and each question
redoes work that depends only on the entry's *directory*. On a big workspace that
repeated work is a real share of scan time — and it is already measured.

## The mechanism, on current main

The walk calls the matcher once per entry — `prunesForGitDiscovery` and `prunes`
per child directory (`src/engine/manifest.ts:577-579`), `ignores(childRel)` per
file (`:605`). Each lands in `fullDecision` (`src/engine/ignore.ts:525-535`),
which reruns the layered decisions fresh for the full path every time:
`legacyDecision` (`ignore.ts:454-464`), `nestedGitDecision` (`:433-452`),
`rboxNegationRescues` (`:466-483`).

`nestedGitDecision` is the expensive one. Per entry it rebuilds the candidate
base list, then walks it calling `evaluateGitLayers(loaded, base + "/")` at
`:441` at each step, just to re-establish "is one of my ancestor directories
already excluded". That ancestor work is identical for every entry in the same
directory, and it is O(depth) `ig.test` calls each time.

The only caches today are per-base, not per-directory: the `gitLayers` map
(`ignore.ts:404`, filled by `getGitLayer` at `:409-417`) caches a base's parsed
`.gitignore`, not any decision; the tracked-paths sidecar (`ignore.ts:743-750`,
`readTrackedCache`/`writeTrackedCache`) is keyed on the index's mtime+size.
Instrumentation already exists: every matcher call in the walk is wrapped by
`timedMatcher` (`src/engine/manifest.ts:715-717`) into the `matcherMs` bucket.

## Proposed change

Memoize the *directory-determined inputs*, never the entry's answer.

**Memo key:** `(directory relPath, nestedGitignore flag)`. The directory alone is
not enough — `prunesForGitDiscovery` calls `fullDecision(dirRel, true)`
unconditionally (`src/engine/ignore.ts:576`) while `ignores`/`prunes` pass
`opts.respectGitignore` (`:543`, `:561`). With `respectGitignore` false the two
callers want different answers for the same directory.

**Memo value:** the resolved `GitRuleLayer[]` chain for that directory, whether
the ancestor walk broke early at `:442`, and the ancestor half of the
`rboxNegationRescues` loop (`:476-481`, iterations `i <= parts.length - 1`). Per
entry what remains is one `testLayer` per loaded layer on the entry's own local
path — the part that genuinely varies. Chain identity is stable within one walk
(`getGitLayer` reads lazily, never invalidates), but carry it in the value anyway
so a future invalidating matcher cannot silently reuse a stale chain.

## The safety property at risk, and how it is proven

**`.rboxignore` negation can un-ignore a path below an ignored parent**
(`src/engine/ignore.ts:466-483`, and the two rescue call sites at `:532-533`).
A memo that cached "this directory is ignored, therefore its children are" would
destroy that, which is precisely the bug this design must not ship.

The memo is safe because it caches *inputs*, not verdicts: `fullDecision` and
both rescue call sites still run per entry, and the entry-specific first
iteration of the rescue loop (`i = parts.length`, testing the entry itself as a
directory prefix) stays outside the memo.

Proof: extend the design-72 §7 corpus, which already names the exact cases —
precedence matrix (builtin vs root vs nested vs `.rboxignore` vs hard rules),
per-base exactness (`foo` vs `/foo` vs `foo/` vs `**` at a nested base),
no-re-include-below-excluded-parent, and `.rboxignore` negation rescuing across
it. Run it **differentially**: same corpus, memo on and memo off, identical
verdicts for every path. `src/engine/ignore.test.ts` holds that table.

## Acceptance measurement

`matcherMs` on a scan of a large real workspace, memo off vs memo on, same
manifest output. Target a clear majority cut; under ~30% is not worth the concept.

## Not worth it if…

…`matcherMs` is not a top-two pole on the workspace being optimized. Measure
first: the bucket already exists, so this costs one scan to find out. Also not
worth it if the key has to grow past `(directory, nested flag)` — at that point
the cache tracks the decision, not the directory, and will outlive its correctness.
