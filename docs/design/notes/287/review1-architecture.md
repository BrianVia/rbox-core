# Design 287 architecture review — round 1

Scope: written plan G6/F7/X1–X4 and dependency consistency, not a new repository audit. No source edits or subagents. Verdict: **REVISION REQUIRED for the umbrella plan**. The measured fixes can proceed independently; the issues below are amendments to design-gated/research package admission, not demands to implement every future protocol now. No Claude/cross-model alignment is claimed.

## A1 — G6's checkout-local hold policy does not account for shared-ref side effects [P1]

**Lines136–152**, especially “hold affected checkout, allowing unrelated stores/checkouts to progress.” Shared refs are store-wide. If checkouts A and B share the store and a received branch/ref change affects B's current HEAD, holding B's index/worktree while applying A's shared branch transition can still change what B resolves as HEAD. A held checkout is not automatically independent just because it owns a private index. Common-config and branch ownership changes have the same coupling.

**Required amendment:** G6b's conflict design must define a store-level effect/dependency set: shared refs/config/object changes, all checkout observations they affect, and which transitions may commit together. A held checkout blocks any shared transition that would invalidate its expected-local proof; independent object import may continue, and genuinely disjoint effects can progress. Name how the existing logical CAS and physical journal express one shared-store transition with multiple checkout outcomes. Add fixture: one sibling locally dirty/on branch X, another receives X movement or branch ownership changes; no visible HEAD/index mismatch and no hidden advancement of held BASE. Replace “unrelated checkouts” with “checkouts whose shared-state dependencies are proven unaffected.”

This does not require an all-siblings global mutex for every read; it requires a precise admission rule for shared mutations.

## A2 — G6 local common-dir grouping is not portable topology identity, and lifecycle cases are missing [P1]

**Lines140–148.** The plan correctly rejects URL/object-overlap equivalence, but jumps from canonical common-dir grouping to “same logical checkout” conflicts and relocation reconnection without stating what lifecycle evidence makes those identities stable. A path is not stable across relocation or inode reuse; a copied `.rbox`/Git directory can duplicate an ID. Remote deletion versus local recreation under the same path is an ABA case. An old offline writer can resurrect topology after a removal unless publication admission understands the activation/tombstone epoch.

**Required amendment:** keep G6a identity explicitly operation-local. G6b must define store and checkout birth identities, installation binding, move/removal/tombstone semantics, copied-directory handling, and the exact evidence for reconnecting a relocated checkout. Do not choose UUIDs as if uniqueness alone proves continuity. Receiver admission must distinguish “same store relocated,” “cloned/copied identity,” and “new checkout at old path”; ambiguous identity holds, without attaching or pruning. Test copy/restore from backup, sender root rename, cross-volume move, delete/recreate, stale offline writer after feature activation and duplicated registry IDs. Maintain tombstone/recovery retention as an explicit support policy.

**Rollout amendment:** “capable writer/reader floor” must be enforced per stream by the authoritative acceptance path after activation, or another proven mechanism must prevent a reconnecting incompatible writer from publishing an erasing projection. A fleet snapshot that all currently online devices are new is not enforcement. New-reader-first alone is insufficient.

## A3 — F7 must budget total reachable chunk references and distinguish repetition from invalid duplication [P1]

**Lines253–257.** “Every reachable chunk as a normal protected blob” is directionally right, but ordinary files becoming hundreds/thousands of blobs can exceed the existing workspace/accounting/refset limits even when each file/descriptor is within its own limit. History/key rotation/manifest carriers contribute additional retained or admitted references. The plan lists chunk-count/file limits but no aggregate admission calculation or over-cap fallback behavior. Its “duplicated chunks” rejection test is also ambiguous: repeated identical chunk content at different positions in a repetitive file is valid and must reconstruct exactly.

**Required amendment:** before format activation, define max chunks per descriptor, per commit/current refset, descriptor bytes, total staged bytes/FDs, and bounded historical reconstruction work. Compute projected aggregate unique encrypted-ref cost **before upload/publication**, including carriers and key-epoch effects; choose whole-file fallback or actionable refusal without partially publishing a chunk representation. Do not silently increase server caps. Deduplicate storage/admission by ciphertext identity while preserving ordered descriptor occurrences; reject duplicate positions/overlapping lengths, not legitimate repeated chunk hashes. Include repeated-content files, multiple chunked files crossing the aggregate limit, zero-length file, key rotation, exact size sum/overflow, and removed-file chunks shared by retained history.

**History/GC addition:** specify whether a version's chunk descriptor is self-contained or delta-based, what it roots and how prune retains the entire reconstruction closure. A whole-file SHA validates reconstruction but cannot tell GC which blobs it must retain. Differential compare rooted chunk sets through checkpoint pruning and key rotation, not only restored plaintext.

## A4 — X1 tree proposal leaves the encryption/root-admission boundary implicit [P1]

**Lines353–357.** A persistent tree “keyed by canonical path encoding” with missing-node fetch and “every retained node reachable by existing admission/GC” is not a sufficient encrypted wire design. File names/tree structure cannot be casually put in server-visible node keys. Existing server ref accounting cannot discover children by decrypting encrypted nodes. Re-encrypting the whole tree or using randomized node encryption can erase structural sharing. Omitting semantically required metadata from the root changes signed identity; normalizing Unicode can collapse currently distinct filenames.

**Required amendment:** X1c must first specify plaintext logical-node identity versus ciphertext blob address; all path-bearing nodes are encrypted under an explicitly reviewed domain/key-epoch scheme. Define how signed root, child references and ciphertext refs bind together, and how the client supplies the exact node+file retention delta to the server without exposing plaintext names. Reuse S5 reference accounting if compatible; do not claim the current GC can traverse an encrypted tree. State that canonical path byte identity is preserved by default; Unicode normalization is a product/format change, not a free tree-design choice. Measure parent re-encryption, node-upload and epoch-rotation amplification. Hostile node budget must include cumulative decoded bytes/edges, repeated-node/cycle traversal and validation work, not merely per-node depth/size.

**Gate:** old/new manifests reconstruct exactly the same file/Git/checkout metadata, not just same file bytes. Reachability set equality and no plaintext paths at server-visible boundaries. Treat content-hash or encryption changes as separately ratified choices, keeping current codec optimizations independent.

## A5 — X3 inventory and X4 persistent processes need durable-possession proof, not only successful reads [P1]

**Lines374–388.** X3 verifies completeness before ref/index mutation, but does not name how receiver objects remain available through the eventual physical effects and crash recovery. A concurrent Git GC can invalidate inventory or remove newly imported but not-yet-rooted objects between verification and installation. Existing keep pins are listed as reused but their lifetime is unspecified. X4 also may retain open pack descriptors, so a read-only child can answer for bytes no longer durably reachable on disk; “invalidates on store replacement” does not cover pack/object removal, alternates changes, or process-private stale negative results.

**Required amendment:** bind omitted transfer/completeness evidence to receiver identity, object format and graph observation; establish operation-owned retention roots before they can be collected, using existing pins/journal owner. Keep them until logical acceptance or durable rollback ownership has settled, with expected-old cleanup. Missing-object fallback happens before authoritative ref/index mutation. X4 batch answers are observations, not durable-possession certificates; limit initial service requests to fully qualified OIDs and forbid extending graph/absence cache lifetime solely because the process persists. Define invalidation for Git config/alternates/object-store generation and treatment of negative lookups. Test `git gc`/repack/prune between inventory, import, verification and apply; deleted pack still open in helper; new object after cached miss; crash after import before pin, and pin cleanup while another actor replaces it.

This can remain a requirement on the existing object/transaction owner, not a new ownership layer or custom database of Git objects.

## A6 — X2 should separate opaque-hash possession from current workspace authority and avoid a broad S4 dependency [P2]

**Lines359–368.** Mutual “current account/device evidence” plus workspace/key context still needs a source-side authorization rule: being authenticated to an account or knowing a ciphertext hash must not permit fetching every ciphertext the peer caches, including bytes from an old/unlinked workspace or another context. Offline roster evidence can be stale after token revocation. The text says verify current access but does not specify availability behavior when freshness cannot be checked.

**Required amendment:** first explicit-address harness uses a server-verified current access proof or another reviewed freshness contract, bound to requester, workspace, intended peer/audience and expiration. Source must apply the same authorized account/workspace scope promised by the existing acquisition policy; hash knowledge is not proof. If the peer protocol claims narrower workspace-scoped access, it needs an explicit retained/cached entitlement mapping to enforce that claim. Do not silently invent a stronger per-workspace rule than the product currently supports. Define deny/fallback when authority is stale/offline and prove revoked credentials cannot stretch replay windows. Do not reuse cloud secret grants directly. Test workspace unlink, account switch, cross-context cache collision and stale credentials.

**Dependency adjustment:** require the trusted device/session binding and revocation contract work, not S4's receipt coalescing or rich WS deployment. Those do not establish peer authentication and should not block an independent loopback experiment.

## A7 — Split execution prerequisites from measurement inputs; the current graph delays useful independent work [P2]

The table says waves are priorities, but package-level prerequisites still make avoidable hard dependencies:

- X1a/b list F2/F3/F4 measurements as prerequisites (line347). Exact-input validation/diff reuse does not require cache SQLite migration, certified matcher reuse or deletion batching to land. Require B0 plus demonstrated codec cost and exact-input identity; use F2/F3/F4 measurements when available.
- S5 declares S4 a dependency (line333). Refset codecs/shadow membership/current-format compatible upload reduction do not require signed WS delivery and its revocation project. Separate hard prerequisite from coordinated rollout: S1 recovery and root/GC compatibility matter; S3 only where bounded replay uses it; S4 integration is optional latency work.
- X3 requires G6 common-store ownership (line372). Sharing capture/import across portable sibling topology does depend on G6; measuring receiver inventory or background compaction for an existing standalone repository does not. Split experiment and deployment prerequisites.
- G6 requires all G5 in the wave table (line28). Correct complete roots and batching-compatible proof semantics are required; launch-count optimizations are not prerequisites to a read-only topology observation/design fixture.
- X4a wording “per active common store/operation” conflates operation-scoped batching and cross-operation process reuse. Make those separately benchmarked stages: the former can reuse G4/G5 now; the latter needs persistent process invalidation/resource proof.

**Concrete document amendment:** add columns or compact labels `hard dependency`, `measurement input`, `rollout coordination` to package prerequisite lines. Retain wave priority without making every earlier package a mandatory gate. Update package map and per-package paragraphs together, so a future dispatcher cannot infer contradictory ordering.

## Recommended round-1 disposition

Accept A1–A5 as required additions to focused design admission and failure matrices. Accept A6's explicit access/freshness contract and narrow its dependency. Accept A7's dependency classification. None requires choosing a new schema ID, branch-conflict product policy, crypto derivation or deployment version in this umbrella document. Record those as unapproved exact decisions at the package gate, with the named proof obligation. Existing G1/F1/F2/G5/S1 independent fixes need not wait on these research decisions.
