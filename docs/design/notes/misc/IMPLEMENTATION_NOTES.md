# Design 93 implementation notes

## Step 1 — grammar and canonicalization

- Added a node-free shared module so the same allowlist, grammar, bounds, and canonical-wire checks can be imported by capture/apply code and by Worker-bundled manifest validation.
- Canonicalization removes repeated identical local values first-seen-first and reports rejected allowlisted values; credential-bearing HTTPS URLs are explicitly identified for the later once-per-repo loud log required by step 7.
- Decision not explicit in the design: wildcard fetch refspecs are accepted only when both source and destination use `*`. Git itself rejects one-sided wildcard refspecs, and admitting them would create wire values that cannot be applied.
- Decision not explicit in the design: SSH URL passwords are rejected while `ssh://user@host/` remains accepted. This keeps the documented SSH username form without creating a second credential-bearing URL path.
- Decision not explicit in the design: “scp-form” is treated as `[user@]host:path`, with non-empty host/path and no whitespace. `::` remains independently rejected as required.
- Decision not explicit in the design: “serialized total” is measured as the UTF-8 byte length of `JSON.stringify(config)`, matching the actual manifest wire representation.
- Decision not explicit in the design: a `branch.*.remote` target counts as present when any allowlisted `remote.<name>.*` key survives projection; the design does not require a URL specifically.
- Test evidence: `bun test src/engine/git/config-sync.test.ts` — 91 pass, 0 fail; `bunx tsc --noEmit --incremental false` — green.

## Step 2 — wire validation and raw Git reads

- Added the optional `GitSection.config` wire type without a schema bump. `validateGitSection` now delegates only that field to the shared canonical validator; unrelated unknown git-section fields remain accepted and untouched, pinned by regression test.
- Added a non-trimming `gitRaw` helper while preserving the existing trimming behavior of `git`. The `-z` local config reader explicitly disables includes, treats exit 1 as “no keys,” preserves successful empty values and embedded newlines, and rethrows real Git failures.
- Added the common-dir `config.lock` path to `gitBusy`; a pointer worktree-local path with that name does not create a false busy result.
- Test evidence: focused grammar/raw/manifest suites green; `bun run typecheck` green (root and Worker); `bun test ./src/` — 1,036 pass, 11 skip, 0 fail, 4,185 assertions across 94 files (173.23s).

## Step 3 — reusable lockfile primitive and config transaction

- Added isolated `lockfile.ts` and `config-txn.ts` modules without wiring them into sync/apply/state code. The existing `gitBusy` lock probes now use `lstat` so busy detection also follows the §7 no-follow rule.
- The production marker identity uses the exact v7 sources: macOS `kern.uuid`, `kern.bootsessionuuid`, and binary `kern.proc.pid.<pid>` (`kinfo_proc.kp_proc.p_starttime`); Linux `/etc/machine-id`, `/proc/sys/kernel/random/boot_id`, and `/proc/<pid>/stat` field 22. Probe failures remain non-reapable/foreign.
- Atomic lock creation stages a same-directory 0600 `O_EXCL` marker, fsyncs it, hard-links it into place, and removes the staging name. Recovery uses a separately owned `<lock>.reap` fence and exact no-follow marker rechecks; only provably dead same-host+boot incarnations are removed. A failed post-commit release is tracked as stale-ours in-process so the next acquisition can recover that exact marker without treating arbitrary live same-process locks as stale.
- The config transaction performs bounded stat-bracketed 1 MiB+1 reads, parses only same-directory snapshot files, builds incarnation-named candidates unlocked, reopens/fsyncs the final candidate path, performs a locked literal B2/B1 CAS and owner recheck, and treats rename as the commit point. Parent-fsync/release/read failures after rename are returned as warnings, not failed applies.
- Orphan sweeping removes parseable candidates only for dead same-host process incarnations and removes unparseable `*.rbox93[.lock]` names only after 24 hours. The fresh-target helper deliberately uses ordinary `git config --local --add` and removes the caller-specified fresh target on any failure.
- **DECISION NOT EXPLICIT IN THE DESIGN:** the persisted config stat token is `{dev, ino, size, mtimeNs, ctimeNs}` as lossless decimal strings. Including ctime detects same-size edits even if mtime is restored; step 4 can store this object verbatim.
- **DECISION NOT EXPLICIT IN THE DESIGN:** a stable Git parse failure is permanent/disabled, while candidate-construction failures are transient/deferred unless their filesystem errno is one of the §4 permanent classes. Canonicalization results are returned explicitly (including over-wire-bounds failures) rather than silently converting an unrepresentable local config to `{}`.
- The §11 live-file assertion uses an injected Git runner that verifies Git receives the bounded snapshot path and matching snapshot bytes, so no strace/dtruss test was skipped.
- Test evidence: `bun test src/engine/git/lockfile.test.ts src/engine/git/config-txn.test.ts` — 27 pass, 0 fail, 84 assertions; `bun test ./src/` — 1,063 pass, 11 skip, 0 fail, 4,269 assertions across 96 files (180.56s); `bun run typecheck` — green (root and Worker).

## Step 4 — transactional state unit and workspace sync mutex

- Replaced all three `sync.ts` whole-state save sites with packet composers. Pull, commit ACK, and no-op bookkeeping now emit per-repo generation transitions with exact sidecar values and observed absences; global candidates are file-only, and every accepted state rebuilds `lastSyncedManifest.gitRepos` solely from authoritative post-merge records.
- The state writer uses `<state>.lock`, exact `expectedStream` + `expectedNonce`, `repoGen` equality as the sole repo CAS, bidirectional whole-packet source atomicity, `sourceSeq` ordering on recompute, a maximum of three in-operation attempts, `stateRevision`, and first-save random nonce installation. Existing physical sidecar maps remain compatibility projections of `RepoRecord` values.
- Added the sync-point apply/ACK helpers and `GitPushPlan.authoredCfgHashByRepo`. Step 4 initializes the authorship map empty; only later step-5/step-7 publication/capture rows are allowed to populate it. ACK composition stamps only entries present in that map.
- Added `.rbox/state/sync.lock` ownership at every named production boundary: daemon pump iterations; CLI push/pull/sync; recover; ignore purge after confirmation with a locked recompute; init/setup across reset/rebind and the entire first-sync branch; and track rebind. Nested sync, retry, and 409-recovery operations receive the existing handle. Export's unique staging pull is explicitly documented as the sole exemption, and a static caller-inventory test pins the complete set.
- Daemon contention leaves the selected `want` bit set, backs off, and retries; CLI contention waits briefly and throws `another sync is in progress (pid …)`. Every daemon iteration revalidates both stream and nonce under the mutex before consuming its wakeup or mutating state.
- Reset/rebind now owns both the sync mutex and state lock, rotates the nonce even for same-binding resets, and clears per-binding caches/sidecars. A delayed A→B→A or pre-reset packet therefore fails the nonce precondition.
- **DECISION NOT EXPLICIT IN THE DESIGN:** CLI mutex acquisition uses 16 attempts at 50 ms intervals (about 750 ms total wait after the first attempt). The design says “waits briefly” but gives no duration.
- **DECISION NOT EXPLICIT IN THE DESIGN:** reset persists the new `{stream,stateNonce,stateRevision}` in `.rbox/state/state-incarnation.json` while `state.json` remains absent until the first accepted save. This preserves the pre-existing pinned assertion that a rebind removes the poisoned baseline while still fencing delayed legacy and pre-reset packets. The transactional loader treats this as the logical empty state; the first accepted state write removes the marker.
- **DECISION NOT EXPLICIT IN THE DESIGN:** direct mutex-less sync API calls retain the pre-existing stream-mismatch replacement behavior only when `loadState` manufactured a fresh mismatch baseline. All enumerated live-workspace production callers pass a mutex and therefore use strict stream+nonce rejection; the sole production mutex-less call is export's fresh private staging root. This kept the existing rebind safety regression unchanged.
- **DECISION NOT EXPLICIT IN THE DESIGN:** when macOS denies the specified `sysctl` identity sources inside an application sandbox, lock identity falls back to the same machine and boot UUIDs exposed by `ioreg`. Other-process start-time probing remains unknown/live (never reaped) when `kern.proc` is denied; normal unsandboxed macOS continues to use the specified sysctl sources.
- No existing pinned test was modified.
- Test evidence: `bun test src/cli/sync-state.test.ts src/cli/sync-mutex.test.ts` — 25 pass, 0 fail; targeted sync/owner regression suites — 40 pass, 0 fail; `bun test src/cli/sync.test.ts` — 45 pass, 0 fail; `bun test ./src/` — 1,094 pass, 11 skip, 0 fail, 4,372 assertions across 98 files (169.75s); `bun run typecheck` — green (root and Worker).

## Step 5 — §6 push config lane

- Added the exact presence/edit predicate to owned identity-carry rows. A publication clones the carried `GitSection` and replaces only `config`; `GitPushPlan.authoredCfgHashByRepo` is populated at that wire mutation and nowhere else. Pending, needs-resolution, busy/transient, structural-drop, forced-422, empty, undiscoverable/ignored, linked-pointer policy-skip, and capture-failure paths retain verbatim carry/drop behavior with no authorship.
- Added `cachedLocalCfg = {hash, nonEmpty}` to both divergence-cache whole-entry writers, bracketed by the exact before/after fingerprint. The file cache version is now 4; v3 and entries missing the summary take a slow pass. A trusted hit carries immediately only when the cached predicate says no publication is due; a due result falls through for the canonical config map required on the wire.
- Over-wire-bounds projections never publish: each host carries its current base section byte-for-JSON-byte, records no authorship, and surfaces the disabled reason. The focused test pins the A→B→A base trace so an unrepresentable local config cannot oscillate the remote value.
- Status now uses the same cached/slow predicate. Snapshot failures are conservatively divergent and render `config: checking`; permanent/over-bounds lanes render `config: disabled`. The former `.catch(() => 0)` path is gone, including for unexpected whole-evaluation errors.
- The existing divergence-cache version assertions were updated from v3 to v4. This is the one explicitly superseded pinned expectation: §6 mandates a FILE-level cache-version bump so legacy entries force a slow pass.
- **DECISION NOT EXPLICIT IN THE DESIGN:** config hashes are SHA-256 over the UTF-8 bytes of `JSON.stringify` on the already-canonical wire map. Canonical key order makes this stable and matches the serialized value whose equality drives publication.
- **DECISION NOT EXPLICIT IN THE DESIGN:** text status distinguishes known permanent/over-bounds failures as `config: disabled`, while transient/read instability is `config: checking`; both count conservatively as divergent. JSON status exposes the same result in an additive top-level `gitConfig` object.
- **DECISION NOT EXPLICIT IN THE DESIGN:** a completely unexpected status-evaluation exception uses `configChecking: ["*"]`, rendered simply as `config: checking`, and counts as one divergent repo because the design forbids zero-on-error but does not define a repo identity for a workspace-level failure.
- Test evidence: `bun test src/cli/sync-git-config-push.test.ts src/cli/status-cmd.test.ts` — 10 pass, 0 fail, 57 assertions; `bun test ./src/` — 1,102 pass, 11 skip, 0 fail, 4,424 assertions across 99 files (180.04s); `bun run typecheck` — green (root and Worker).

## Step 6 — §6 pull config lane

- The due predicate now runs before both the remote-unchanged and already-converged shortcuts. A due config-only failure records the complete incoming section in `gitPendingRemote`, retains the old base, and emits no lane completion; a completed run advances/clears only afterward. Conflict checkpoints compare the recorded local identity first and hold config until that identity changes, then reuse the same due decision.
- Combined changes pass config as `applyGitState`'s final mutation callback. Ordinary rows therefore reuse `LocalSnapshot` rollback on any pre-rename failure. CLEAN-MATERIALIZATION rows snapshot only after their destructive hook, so the same failure lands pending without pretending the pre-wipe state was restored. Incoming-ref and temp-directory cleanup after a successful config rename are now best-effort/non-fatal.
- Existing owned dir repos use the optimistic config transaction and consume `preHash`/`postHash`/`incomingHash`/`baseHash` plus the post token computed while `config.lock` is held. The transaction rename remains the commit point; post-rename read/fsync/release failures remain warnings and always return a completed result with a token (candidate-token fallback deliberately makes the next due check self-heal if the installed re-read failed).
- Receiver ownership is re-derived from the local repo shape and common-dir containment. `cfgShape` records `{shape, realpath, dev, ino, birthtime-or-0}`; a mismatch clears the old config markers before any non-owned return. Pointer/cross-shape receivers skip config and log once per workspace/repo for the process lifetime. Scoped wire sections carrying config are rejected.
- Pull lane changes feed the existing step-4 generation-CAS save packet as `RepoStateValues.configLane`; a present entry replaces only the four lane fields, while unrelated records and ACK markers are preserved. There is no second state save.
- **LOUD — FRESH-TARGET BINDING DETAIL:** the design simultaneously requires hashes under the config transaction lock and mandates the step-3 plain `git config --local --add` helper for a private fresh target. Fresh targets therefore use that explicit no-outer-lock exception: after the helper completes, the code performs a bounded parsed snapshot for `C_post`/`cfgToken`; existing repos compute every sync-point hash while the transaction lock is held.
- **LOUD — SHAPE INVALIDATION DETAIL:** a missing legacy `cfgShape` is treated as a mismatch, so old lane markers are cleared before the first step-6 apply. This fails safe (one additive re-apply) and establishes the binding required to prevent inode/receiver-shape reuse from trusting stale `cfgApplied`/`cfgToken`.
- Focused test evidence: `bun test src/cli/sync-git-config-pull.test.ts` — 7 pass, 0 fail; combined transaction/state/manifest/pull/sync regression wave — 121 pass, 0 fail; `bun test ./src/` — 1,110 pass, 11 skip, 0 fail, 4,464 assertions across 100 files (183.65s); `bun run typecheck` — green (root and Worker).

## Step 7 — §6 real-capture config embed

- Successful real captures now re-derive the local repository context and embed canonical config only for an owned dir/all receiver whose git dir equals its contained common dir. Pointer/scoped and unprovable/out-of-containment captures emit no `config`, record no authorship, and use the existing once-per-workspace/repo loud ownership log.
- Owned captures perform a fresh bounded config read after the git artifact capture. The step-3 snapshot helper now extends its no-follow stat/read/stat bracket across the snapshot-only Git parse with a final live-path stat; persistent instability or a parser/filesystem failure retains only the base section's config on the newly captured git section (or leaves config absent when the base was absent), never `{}` or a partial projection.
- Over-wire-bounds capture projections are distinguishable and suppress embedding while retaining the base config verbatim. Credential-bearing HTTP(S) URLs are excluded by canonicalization and produce one loud log per workspace/repo for the process lifetime; the filtered canonical map remains eligible for embedding.
- `GitPushPlan.authoredCfgHashByRepo` is populated at the exact successful capture wire mutation, using the hash of the embedded map. Stability/subprocess failure, over-bounds, non-owned capture, and base carry create no entry. The existing presence rule can therefore heal a later old-writer strip end-to-end.
- Added §11 rows for snapshot-only parse plus persistent stability carry, snapshot parser failure carry, once-only credential logging, owned-dir versus pointer/scoped capture, real-capture over-bounds suppression, and real-capture → old-writer-strip → presence-republish.
- **LOUD — STABILITY BRACKET EXTENSION:** step 3's parsed-snapshot helper previously completed its live-file bracket before invoking the Git parser. Step 7 adds a separate stable parsed-snapshot entry point with the required final no-follow stat after the subprocess; apply B1/B2 behavior remains unchanged.
- **LOUD — OWNERSHIP RECHECK AT BOTH WIRE MUTATIONS:** the §9 receiver-shape predicate is applied both to real-capture embedding and to the existing identity-carry publication seam. This prevents an out-of-tree pointer/scoped repository from receiving `config` through the step-5 patch path while keeping all non-owned base carries verbatim.
- No existing pinned test was modified; step-7 assertions were added to the existing focused push-config suite.
- Test evidence: `bun test src/cli/sync-git-config-push.test.ts src/engine/git/config-txn.test.ts src/cli/sync-git-config-pull.test.ts` — 37 pass, 0 fail; `bun test ./src/` — 1,115 pass, 11 skip, 0 fail, 4,497 assertions across 100 files (188.53s); `bun run typecheck` — green (root and Worker).

## Step 8 — §11 two-root E2E suite

- Added a dedicated two-root real-Git suite with an E2EE ciphertext/blob remote patterned after `git-sync.test.ts`. It covers fresh materialization against a local bare remote (`remote -v`, `status -sb`, and a real `git pull` through a local test SSH transport); config-only wire publication with stable Git identities/artifacts; same-head manual-delete healing proven by a changed `cfgToken`; present-different convergence with at most one flip and two full idle cycles producing neither sequences nor commit attempts; old-writer strip and structural-drop presence recovery; both config-only unchanged shortcuts; combined Git+config rollback; historical all-base pointer carry; scoped→standalone→pointer ownership skip; independent nested config lanes; deterministic unstabilizable status; and two real Bun processes racing daemon/CLI-shaped state saves.
- The five `REVIEW-93.md` implementation-risk seams are represented directly: repeated state-save/source atomicity is exercised across processes; echo behavior is pinned across repeated sync cycles; push fast/carry/drop recovery is covered by config-only, strip, structural, and pointer rows; pull base/pending ordering is fault-injected at both shortcuts and the combined rollback boundary; capture ownership/stability is covered by pointer, nested, and unstable-status rows. The mutex/caller-inventory/purge contention rows remain in the step-4 transactional suites, which are included in the focused acceptance wave rather than duplicated in the two-root harness.
- Added a narrow `GitDivergenceStatusOptions.gitConfigRunner` test seam and threaded it through both status cache-miss population and its fallback read. This is necessary to prove a persistently unstable read deterministically; production callers omit it and behavior is unchanged.
- **LOUD — ADD-ONLY FIELD-GATE INTERPRETATION:** §7 binds receiver apply to `present ⇒ untouched; never delete`, and §8 explicitly says existing URLs are never overwritten. Therefore “config-only edit propagates” and the rig's “URL edit propagates” are asserted at the received wire/persisted-base boundary, with Git identity unchanged; an already-present local URL intentionally remains local. The separate delete/heal row proves the incoming edited value installs once the key is absent. ## Whole-branch cleanup pass

- Reused the engine SHA-256 helper for canonical config hashes, moved directory fsync into `fsutil`, and shared the NUL-delimited Git config parser between direct and snapshot reads. Config stat-token equality, config-lane projection, and record-to-state projection now each have one implementation.
- Wired the already-tested orphan sweeper into the config transaction itself. It runs best-effort only when an apply is due, so crash debris is reclaimed without adding work to warm carry cycles.
- Made local config duplicate removal linear with per-key sets, while preserving first-seen value order and all canonicalization outcomes. The validator also reuses its first key parse instead of reparsing every key.
- Removed reset's dynamic mutex imports, reused the common mutex assertion, collapsed daemon mutex release to one `finally`, removed repeated lock-marker parsing/error classification, and cleaned the incremental mutex-wrapper indentation seams.

### Findings intentionally not changed

- Did not replace lock-marker or config-candidate creation with `writeFileAtomic`: §7 requires `O_EXCL` + `O_NOFOLLOW`, a fully-fsynced marker followed by `link()`, and owner-checked publication; the general atomic writer does not provide those semantics.
- Did not batch the per-value `git config --add` subprocesses or remove the candidate/final parses: §7 explicitly pins add-per-value construction and derives `C_post`/the post token from installed bytes while the lock is held.
- Did not collapse B1/B2, the status/apply preflight read, or same-directory snapshot parsing. Those reads can look redundant, but §§4/6/7 bind the stability bracket, optimistic byte CAS, due-before-shortcut rule, and “Git never opens the live file” discipline.
- Did not merge the workspace sync mutex with the short state/config locks. They fence different boundaries: the operation-wide decision→filesystem→state interval versus owner-checked atomic publication.
- Did not remove the nonce-less/link-unsupported compatibility path or `state-incarnation.json`. §6 explicitly preserves legacy git-state behavior when the config lane cannot safely use hard links, and the incarnation marker fences reset/rebind while `state.json` remains absent.
- Did not unify the config stat token with the divergence fingerprint's internal `StatToken`: the persisted token is lossless bigint identity for the config due predicate, while the fingerprint token is a broader cache-only shape with content/stat fallbacks.
- Did not add cross-repo config parsing batches. Each owned repo has an independent common config and lock; the v4 divergence cache already makes warm carry/status cycles parse-free, while cold misses must use the per-repo snapshot parser required by §4.

## Field-gate follow-up — stale rig checkout binding

- Root cause: the rig uses process-global `rig-dev-a`/`rig-dev-b` container names, while their `/app/src` and `/app/scripts` bind mounts are fixed when the containers are created. `ensureUp` previously reused any existing names without checking mount sources. Running this worktree's host-side scenario after another checkout had created the guests therefore executed that other checkout's real CLI. An older CLI produces the observed signature exactly: Git artifacts capture/apply, but the design-93 `GitSection.config` lane is absent.
- The binding code itself is intact: init's first publish calls `push` → `pushManifest` → `planGitSections`; a real capture calls the §6/§9 `captureWithConfig` seam; and fresh pull apply invokes `materializeFreshGitConfig` as the final mutation. Added an encrypted-transport regression that begins with an empty state, publishes an owned nested repo with remote/tracking keys, verifies the decrypted wire section, then fresh-materializes and reads the local keys.
- `ensureUp` now inspects existing Apple-container mount configuration before reuse. If either expected source points outside the current checkout, or inspect is unavailable/malformed, the rig-owned container is deleted and recreated with the current worktree mounts. Extra scenario mounts remain allowed. The pure regression pins the stale-other-checkout rejection.
- The `git-config-sync` materialization step now treats exit-0 plus empty `git remote -v` as an immediate step failure: it records the failed assertion and throws before later assertions can leave the step marked PASS.
- Focused evidence: `bun test scripts/rig/lib/container.test.ts src/cli/e2ee-sync.test.ts` — 15 pass, 0 fail, 151 assertions. Acceptance evidence: `bun test ./scripts/rig/` — 82 pass, 0 fail, 231 assertions across 14 files; `bun test ./src/` — 1,125 pass, 11 skip, 0 fail, 4,548 assertions across 101 files (222.57s); `bun run typecheck` — green (root and Worker).

## Field-gate follow-up — Linux lock identity degradation
