# Review 124 — Git deferral drilldown + copyable fix brief

1. **Blocking — the proposed fix brief recommends a resolver that cannot fix every listed deferral.** `status --json` includes apply, capture, and config lanes, but `gitResolveCmd` only has resolvable incoming state when the record has `pending`, `resolutionKey`, or an apply deferral (`git-cmd.ts:173-176, 473-478`). `keep-mine` is unconditionally unsupported, and `take-theirs` requires a fresh `show-me` snapshot followed by `--confirm` (`git-cmd.ts:454-470, 492-500`). **Concrete fix:** define actionability per repo from the actual record/incoming state; offer resolve commands only for actionable apply state, give capture/config/no-incoming cases their real remediation, state plainly that `keep-mine` is unavailable, and render the real two-step `show-me` then `take-theirs --confirm <snapshot>` flow.

2. **Blocking — lane-level deferrals and repo-level summaries are conflated.** `git.deferrals` is one element per lane (`status-cmd.ts:484-497`), while `deferredRepos` and `projectGitDeferralRepos` collapse multiple lanes to one row per repo (`status-view.ts:194-232`). The design alternates between “per-deferral,” “per repo,” and “same array,” so counts, sorting, commands, and `+N more` can all be implemented differently or even go negative. **Concrete fix:** name and specify a repo-summary DTO for the human list, brief, and ambient UI; preserve the lane array only inside the documented JSON shape; define how all lanes/reasons are represented in a repo brief; sort/cap repo summaries; and compute `+N` as `max(0, deferredRepos - displayedValidRepoRows)`.

3. **Blocking — paused and dead-daemon details would be stale while appearing current.** A paused status is accepted indefinitely and carries the previous count/age (`ambient-status.ts:192-204`; `StatusReader.swift:120-134`); a dead verdict also carries fields from the last stale status (`StatusReader.swift:141-155`). Copying `ageSeconds` freezes age, and resolving or otherwise changing durable state while paused leaves both the drilldown and fallback obsolete. The fresh-populate path also borrows ambient fields without checking the ambient heartbeat (`StatusReader.swift:63-85`). **Concrete fix:** define freshness/provenance for live, paused, populate, and dead paths. Carry a validated `deferredSince` and derive age at render time; label paused data “as of pause”; borrow details during populate only from a fresh, attributed ambient record; treat dead-daemon details as stale/display-only; and never silently use stale ambient rows as the current fallback diagnosis.

4. **Blocking — the promised schema compatibility is proven only for unknown top-level keys, not for the new nested schema.** Swift currently probes selected dictionary keys and therefore ignores a new top-level key (`StatusReader.swift:186-232`), but the design does not say how to validate an array item, an unknown future reason, a detached or missing checkout, an extra nested key, or one malformed item among valid ones. Rejecting the whole status would falsely turn a healthy daemon into attention/dead; accepting arbitrary strings creates display and clipboard sinks. **Concrete fix:** specify the exact bounded nested schema: maximum five items; bounded, control-sanitized strings; nonempty repo; valid ISO `deferredSince`; optional checkout union rather than a required `branch`; unknown item keys tolerated; unknown reasons rendered generically; and malformed details dropped independently without invalidating core daemon status. Add old-reader/new-writer and new-reader/old-writer tests plus malformed, unknown, oversized, and mixed-validity cases in both parsers.

5. **Blocking — the brief's privacy claim contradicts its required contents.** Absolute workspace paths and hostnames commonly contain user/account/device identifiers, while relative repo paths and branch labels commonly contain customer, organization, ticket, email, or person names. `safeResolveText` only replaces the exact workspace-root prefix, URL credentials, and token-like strings (`git-cmd.ts:331-337`); it does not redact those identifiers. Calling this human- and LLM-pasteable under the `resolve --json` redaction stance is therefore inaccurate. **Concrete fix:** choose and document the trust boundary. For an LLM-safe default, omit hostname and absolute root and redact or alias repo/branch identifiers, with an explicit opt-in local diagnostic form for executable paths; alternatively label the unredacted brief as sensitive and stop claiming it is safe to share. Pin the decision with fixtures containing home usernames, email-like hostnames, customer repo names, and ticket/user branch names.

6. **Blocking — interpolated repo names do not produce safe or portable commands.** Legal paths can contain spaces, quotes, leading dashes, backticks, `$()`, newlines, and Markdown delimiters. The current output sanitizer is unsuitable for a multiline Markdown document, and the fallback's canned `rbox git resolve <repo>` has neither shell quoting nor a workspace anchor. A command copied from RboxBar and pasted outside the workspace need not resolve the intended root. **Concrete fix:** define separate field control sanitization, Markdown escaping, and POSIX argv quoting; generate commands from quoted arguments rather than string interpolation; and make every pasted command location-independent with a supported workspace selector, a shell-quoted absolute repo argument, or `cd <quoted-root> && ...`. Test hostile legal names and pasting from an unrelated directory.

7. **Should-fix — “one vocabulary in `git-cmd.ts`” conflicts with the existing ownership and with the Swift fallback.** `status-view.ts` already owns a complete reason map and the repo projection (`status-view.ts:141-160, 194-232`), whereas `refusalMessage` is private, resolver-specific failure prose (`git-cmd.ts:378-397`). Importing the heavyweight resolver module into ambient daemon code would create the wrong dependency direction. Swift is then also asked to author fallback prose and commands, contradicting the single-owner claim. **Concrete fix:** put the exhaustive presentation data in `status-view.ts` or a small dependency-leaf deferral-presentation module, with distinct typed fields for short label, explanatory sentence, and remediation class. TypeScript should own resolution semantics and canonical command rendering; Swift should only wrap validated opaque fields in an explicitly partial/stale fallback.

8. **Blocking — the Copy subprocess API described by the design does not exist and can wedge every action.** `RboxActions.run` merges stdout and stderr, returns no output, blocks on `readDataToEndOfFile`, and has no timeout (`RboxActions.swift:128-147`). The only timeout is in the unrelated version probe, and all actions share one serial queue (`RboxActions.swift:24, 79-117`). A hung or verbose brief can therefore block copy, pause, restart, upgrade, and version indefinitely. **Concrete fix:** specify a separate capture API returning stdout and bounded stderr, with concurrent draining or files, an output-size cap, a deadline, terminate/kill-and-reap behavior, and exactly-once completion. Test nonzero exit, hang, child ignoring terminate, oversized output, invalid UTF-8, and stdout/stderr separation; do not cite the existing upgrade action as already providing this pattern.

9. **Blocking — the fallback cannot uphold “never dead-ends” or “self-contained.”** A new bar can read an old daemon's `deferredRepos` without the optional detail array while an old installed CLI rejects `git deferrals`; even when present, ambient details are capped at five and can be stale, so the fallback cannot describe “all of them.” A generic resolve line may also be inapplicable per finding 1. **Concrete fix:** define a version-skew/failure state machine. Key the full action off a known root and current CLI result; if no validated current details exist, show an honest update/run-status error rather than claiming success; if a capped last-known fallback is copied, label it prominently as partial and stale with the omitted count and do not present generic resolve as a guaranteed fix.

10. **Should-fix — Copy action state and clipboard failure behavior are omitted from the implementation scope.** Existing actions are coordinated by `AppModel`, which owns in-progress state, main-actor completion, and errors (`AppModel.swift:88-155`), but `AppModel.swift` is absent from the file list. The design also assumes pasteboard writes succeed and does not say what happens if selection changes while the subprocess runs or when “Copied ✓” resets. **Concrete fix:** add `AppModel.swift` and its tests to scope; capture workspace identity/root at invocation; define interaction with the shared action queue; perform pasteboard mutation on the main actor; check the pasteboard Boolean result; never flash success on write failure; and specify confirmation lifetime and cancellation/reconciliation when the selected workspace changes.

11. **Should-fix — the CLI contract is not precise enough to implement compatibly.** “The same array ... plus `schemaVersion`” does not define valid JSON: an array cannot have a serialized named property. The design also does not define `--brief --json`, path/workspace arguments, ordering, exit codes, or help/flag registration; current dispatch only recognizes `git resolve` (`main-dispatch.ts:424-439`) and the help registry has no `git deferrals` entry. **Concrete fix:** publish an exact wire example, preferably `{ "schemaVersion": 1, "deferrals": [...] }`, define whether that nested lane array is byte-for-field identical to `status --json`, reject conflicting modes, specify root selection and empty/error exits, and include dispatch/help/completion/flag-registry changes and tests in scope.

12. **Should-fix — age and reason semantics can make the diagnosis false.** Durable state has both episode-level `deferredSince` and `reasonSince`, because the current reason can change without ending the episode (`config.ts:202-210`). `projectGitDeferralRepos` also chooses display reason by precedence but oldest time independently, so “local operation · 4d” can mean a four-day episode whose current local-operation reason is new. Invalid timestamps are coerced to age zero in `status --json` (`status-cmd.ts:490`), making corrupt/unknown data look fresh. **Concrete fix:** carry both timestamps and word the UI/brief as “deferred for X; current reason Y since Z,” or explicitly choose another truthful relation; render invalid times as unknown rather than zero; define future-time handling; and test reason transitions, multiple lanes, malformed dates, and clock skew.

13. **Should-fix — count/detail reconciliation and drilldown safety are underspecified.** The full count may be nil, smaller than decoded rows, or larger because rows were capped or rejected. Basenames can collide, and repo/reason strings can be long, Unicode, or contain line/control characters in a fixed 296-point panel (`MenuContentView.swift:19, 207-219`). **Concrete fix:** make the validated full count authoritative where present, display at most `min(5, count)` rows, clamp omitted counts, show a generic undisclosed-details row when count exists without details, sanitize controls at the producer and consumer, specify one-line truncation/accessibility labels/full-path help, and test colliding long basenames plus all count/array mismatch cases.

14. **Should-fix — the acceptance plan misses the failure modes on which the feature's safety depends.** A happy live-deferral check and golden brief do not cover old/new daemon-Bar skew, stale paused/dead/populate data, actionability by lane, unsafe identifiers, subprocess timeout, clipboard refusal, or fallback completeness. Hostname/version also make the proposed golden nondeterministic unless injected. **Concrete fix:** add a cross-surface matrix covering those cases; dependency-inject clock, hostname, and version for deterministic CLI snapshots; add Swift parser/model/action tests and TypeScript ambient/dispatch tests; and require the field check to exercise both a resolvable apply deferral and a non-resolvable capture/config deferral before implementation is considered validated.
