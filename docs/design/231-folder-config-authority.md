# Design 231: User-owned folder configuration authority

**Status:** ALIGNED round 3; implementation authority. **Fully amended
2026-08-11 for the pre-2.0 breaking-simplification ruling.**
**Snapshot:** `origin/main` at `74f8faff1`; slice-2 contract landed in
`dd189f83a`.
**Product direction:** one readable `~/.rbox/config.json` lists the folders this
machine intends to sync, with global option defaults and per-folder overrides.

## 1. Problem

Design 230 made the ordinary CLI folder-first, but deliberately left the old
durable model in place. A user still cannot inspect one file and answer:

- which folders this machine intends rbox to manage;
- what defaults apply to all of them;
- which folder differs from those defaults; or
- whether a folder is configured but not yet bound to remote state.

The existing files answer different internal questions:

- `<root>/.rbox/workspace.json` owns a binding's remote stream/device identity,
  scope seal, and scope crash journal;
- `~/.rbox/workspaces.json` is a reconstructible binding registry and redundant
  scope witness; and
- `~/.rbox/daemons/<key>/desired.json` owns running/stopped mode and maintenance
  obligations.

Turning any one of those into a user settings file would either expose remote
identity as product configuration or collapse independently crash-sensitive
facts into one record. Adding a fourth mirror without assigning exclusive facts
would be worse.

## 2. Outcome and schema

`~/.rbox/config.json` becomes the sole user authority for:

1. the ordered list of locally named synced-folder intents;
2. the path of each intent on this machine;
3. global user-option defaults; and
4. explicit per-folder option overrides.

This example is illustrative; §5 is the single normative option/schema
contract.

```json
{
  "schemaVersion": 1,
  "globalOptions": {
    "syncGit": true,
    "git": {
      "incremental": true
    },
    "respectGitignore": false,
    "noDrift": false,
    "trash": {
      "days": 30,
      "maxBytes": 2147483648
    }
  },
  "folders": [
    {
      "name": "Development",
      "path": "~/Development",
      "options": {
        "respectGitignore": true,
        "trash": {
          "days": 14
        }
      }
    }
  ]
}
```

`folders` is an array. `name` is a local, user-editable label and is never an
identity key for remote data. `path` locates the folder. The hidden binding at
that path continues to carry `remoteWorkspaceId`.

The local name is distinct from `workspace.json.name`, which is the cached,
immutable, server-visible display name. Output-surface compatibility is owned
once, in §9.

## 3. Ownership map

### 3.1 New `FolderCatalog` Module

`src/cli/folder-config.ts` owns:

- strict schema parsing and validation;
- `~` / `~/…` expansion and friendly path collapse;
- normalized-path duplicate detection and physical-overlap diagnostics;
- local-name uniqueness;
- fieldwise global/per-folder option resolution;
- pre-catalog policy snapshotting through the one function specified in §5;
- the config byte digest pinned by one operation;
- locked compare-before-write mutation, atomic publication, and directory
  durability;
- catalog state inspection (`absent`, `authoritative`, or `damaged`) with an
  opaque revision;
- first-run generation plus the loss description, confirmation binding, and
  guarded publication operations used by the explicit regeneration loop; and
- explicit add/update/remove operations.

It must never own:

- remote workspace creation, selection, or deletion;
- workspace/device/stream identity;
- credentials, encryption keys, or server URLs;
- daemon process transitions or desired modes;
- registry or desired-row discovery;
- scope edits, pruning, adoption, or sync orchestration.

Its complete Interface is:

```ts
inspectFolderCatalog(): Promise<FolderCatalogState>
readFolderCatalog(): Promise<FolderCatalogSnapshot>
initializeFolderCatalog(inventory: FolderGenerationInventory): Promise<FolderCatalogSnapshot>
prepareFolderRegeneration(
  state: FolderCatalogState,
  inventory: FolderGenerationInventory,
): FolderRegenerationAttempt
publishFolderRegeneration(
  attempt: FolderRegenerationAttempt,
  authorization: ConfirmedRegeneration,
): Promise<{ kind: "published"; snapshot: FolderCatalogSnapshot } | { kind: "catalog-changed" }>
recordFolder(root: string, seed: FolderSeed): Promise<FolderCatalogSnapshot>
forgetFolder(root: string): Promise<FolderCatalogSnapshot>
setFolderOptions(root: string, patch: FolderOptionsPatch): Promise<ResolvedFolderPolicy>
```

`FolderRegenerationAttempt` is opaque and binds the exact loss description,
generated bytes, and observed catalog revision. `ConfirmedRegeneration` is an
operation-scoped authorization for that attempt; it cannot authorize different
bytes or a different revision. The `rbox config regenerate` Adapter owns the
outer loop in §6.3 and has no frozen-inventory parameter: it observes state and
inventory, prepares the loss description, obtains confirmation, and retries the
whole interaction on `catalog-changed`. `--yes` changes only the confirmation
Adapter. This prompt boundary is a real asynchronous seam, not a protocol that
ordinary callers must reconstruct. Other callers receive validated snapshots
and effective policy, never parsing or publication phases.

### 3.2 New `FolderInventory` Module

`src/cli/folder-inventory.ts` is the read-only composition root joining a
`FolderCatalogState`, per-root binding observations, the compatibility
registry, daemon desired rows, and an optional current resolved root. It alone
classifies configured, unbound, missing, detached, damaged, and overlapping
roots. Setup, status, doctor, generation, boot resume, and daemon Adapters
consume its observations instead of rebuilding the join.

The registry remains best-effort evidence. A configured path with a readable
binding is admitted even when its registry row is absent or conflicting.
Inventory never heals or mutates: the existing convergence Adapter may consume
its observation and repair the cache best-effort after admission. A conflicting
registry identity is diagnostic, not binding authority. The existing
design-212 rule remains narrower and stronger: a present scope witness
escalates uncertainty and may fail closed to protect the publication seal.

Inventory produces one row per normalized root in the complete union of
catalog paths, persisted registry paths, daemon desired-row paths, and the
current resolved root. It deduplicates the union without dropping source
evidence. Rows are not registry-shaped: registry, desired, binding, and catalog
evidence are independently optional, so catalog-only unbound and missing rows
remain representable. For generation, a discoverable binding means a readable
`<root>/.rbox/workspace.json` reached through that union. An unreadable or
dangling observation is reported distinctly but is not a binding. These
existing tolerant discovery readers remain cache readers: corruption is
visible but does not become a second authority.

The Interface separates bounded one-root admission, machine inventory, and the
read-only generation observation:

```ts
observeFolderAdmission(root: string, state: FolderCatalogState): Promise<FolderAdmission>
listFolderInventory(
  state: FolderCatalogState,
  context?: { currentRoot?: string },
): Promise<FolderInventorySnapshot>
observeFolderGeneration(
  state: FolderCatalogState,
  context?: { currentRoot?: string },
): Promise<FolderGenerationInventory>
```

The state argument is required and is never a bare snapshot, so bounded
admission can classify `damaged` and reuse an observation without fabricating
catalog authority. Inventory snapshots carry that opaque input revision, and
`prepareFolderRegeneration` rejects a state/inventory revision mismatch. There
is no separate upgrade-reader Module.
`FolderCatalog` transforms the typed inventory into generated user authority
without importing registry or autostart code, and `FolderInventory` never
writes the catalog, registry, desired rows, or bindings.

### 3.3 Existing records retain narrower facts

| Record | Exclusive authority after cutover |
|---|---|
| `~/.rbox/config.json` | user folder intent, local label, global options, per-folder overrides |
| `<root>/.rbox/workspace.json` | remote/device/stream binding identity, scope seal/journal, binding schema facts |
| `~/.rbox/workspaces.json` | observed-binding compatibility registry and redundant scope witness |
| `~/.rbox/daemons/<key>/desired.json` | requested running/stopped state, pull-only mode, pending mode, maintenance |

`workspaces.json` remains internal. Its union with desired rows is a discovery
net, but it cannot add entries to `config.json` except through the explicit
regeneration operation. Failure to write that registry can never make a valid
configured binding unusable.

### 3.4 No binding-record mutation Interface

This design adds no Interface that mutates binding records for folder-option
compatibility. Binding persistence keeps its existing owners and lock order;
the field-retention boundary is specified only in §13.

## 4. Linking folders to remote identity

The config never stores a workspace ID.

```text
folders[] entry
    -> normalized local path
    -> <path>/.rbox/workspace.json
    -> remoteWorkspaceId + deviceId + stream coordinates
```

An inventory row is:

- **bound** when catalog membership and a readable binding are present;
- **unbound** when the path exists without a binding;
- **missing** when the configured path does not exist; or
- **detached** when an observed binding is not listed in the authoritative
  catalog.

Names never establish or repair a binding. Registry `rebound` remains a
diagnostic about a best-effort observation; it is not catalog admission and
cannot stop a readable configured binding. Existing stream/reset/desired-state
checks continue to fence the identities they own. An unbound entry never
creates or joins remote state passively; guided setup performs that explicit
transition.

## 5. Option model

The supported user options are exactly:

```ts
interface FolderOptions {
  syncGit?: boolean;
  git?: { incremental?: boolean };
  respectGitignore?: boolean;
  noDrift?: boolean;
  trash?: { days?: number; maxBytes?: number };
}
```

Nested objects merge field-by-field. `false` and `0` are values; only an absent
field inherits. Normative new-folder defaults are `syncGit: true`,
`git.incremental: true`, `respectGitignore: false`, `noDrift: false`,
`trash.days: 30`, and `trash.maxBytes: 2147483648` (2 GiB). `null`, unknown
keys, invalid types, and non-finite/non-integer numbers are errors. Catalog
trash values must already be integers within 0–365 days and 0–1099511627776
bytes (1 TiB); unlike binding normalization, user authority is rejected rather
than silently truncated or clamped.

For a new folder:

```text
product default <- globalOptions <- folders[i].options
```

`snapshotPreCatalogPolicy(binding)` is the only conversion from persisted
binding options to catalog options. It returns a complete explicit object and
materializes every field as follows:

```text
syncGit          = binding.syncGit          when present, otherwise false
git.incremental  = binding.git.incremental  when present, otherwise true
respectGitignore = binding.respectGitignore when present, otherwise false
noDrift          = binding.noDrift          when present, otherwise false
trash            = trashConfig(binding)
```

The `syncGit` difference is intentional and safety-critical: an absent binding
value means false, while the catalog's product default is true. Generation
therefore always stores the complete result in every generated entry's
`options`; omitted or partial `options` is not legal generation output. Users
may later delete individual per-folder fields to opt into inheritance.

Existing bind flags retain their supported meaning:

- an explicit `--git true|false` becomes an explicit folder override;
- an explicit respect-gitignore choice becomes an explicit folder override;
- low-level `init`/`track` default behavior remains its historical concrete
  value when the catalog is not yet available;
- guided setup on an authoritative catalog inherits global values unless the
  user explicitly chooses otherwise;
- same-workspace re-track preserves today's flag-derived result by updating the
  corresponding override; and
- a different-workspace rebind preserves local folder options unless an
  explicit bind flag replaces them. Identity/scope never carry from the old
  stream.

The init plan records option provenance (inherited versus explicit/compatibility
default) so the catalog writer does not infer it from a final boolean.

The environment override `RBOX_NO_DRIFT=1` retains its existing final
precedence. `encrypted` is a safety invariant, not a preference.

The following are rejected from generic options:

- `scope`, `scopeGeneration`, and `scopeIntent` — the design-212 publication
  seal and journaled filesystem transaction;
- `pullOnly` — daemon desired-mode authority; and
- identity, server, credential, and E2EE fields.

Schema v1 is closed at every object level. Required fields are
`schemaVersion`, `globalOptions`, `folders`, and each entry's `name`/`path`;
hand-authored `options` is optional. Limits are 1 MiB total bytes, 1,024
folders, 128 Unicode scalar values per local name, and 4,096 UTF-8 bytes per
path. Names must be valid Unicode scalar sequences, already NFC-normalized,
non-empty, free of leading/trailing whitespace, and unique by exact NFC
spelling. Case-distinct names remain distinct and name-addressed commands
require exact spelling. Unsupported `~user`, NUL, lone UTF-16 surrogates,
non-absolute post-expansion paths, unknown keys, `null`, and a schema version
newer than 1 fail with actionable errors. Existing missing paths use lexical
normalization. Normalized-identical absolute paths are rejected. Physical
aliases and ancestor/descendant roots are accepted by the codec and reported by
inventory when observable; guided add may refuse introducing a new overlap.
Neither observation rewrites stored spelling.

## 6. Authority activation and generation

### 6.1 Durable states

`config.json` is the authority record. Its complete state model is:

| `config.json` | State | Opaque revision | Meaning |
|---|---|---|---|
| absent | `absent` | absent sentinel | apply the activation rule in §6.2 |
| present and valid | `authoritative` | digest of the exact bytes | use the validated bytes |
| present, readable, and invalid | `damaged` | digest of the exact bytes | fail closed with the exact parse error and a repair-copy path |
| present and unreadable | `damaged` | unreadable sentinel | fail closed with the exact read error and a repair-copy path |

Every read validates the current bytes. A hand-authored valid file is therefore
authoritative immediately; no import or rewrite occurs. A parse failure never
degrades to an empty folder list. Callers may retain and compare a revision for
freshness but may not interpret its digest or sentinel representation.

### 6.2 Activation trigger

Every catalog-aware entry point ensures authority before it needs policy or
inventory. When `config.json` is absent, it gathers the §3.2 generation
observation:

- zero discoverable bindings is treated as a fresh machine and silently
  generates the empty catalog described in §6.3; or
- one or more discoverable bindings returns an error naming the exact recovery
  command, `rbox config regenerate`. It never generates implicitly.

This binding-presence rule is the complete provenance test. No hidden durable
record attempts to distinguish a genuinely fresh machine from a deleted
catalog. A machine with data gets an explicit destructive operation; a machine
with no discoverable binding has no binding policy to preserve.

`rbox config regenerate` works whether the file is absent, authoritative, or
damaged. Before writing, it prints that local labels, ordering, global defaults,
inheritance choices, overrides not reflected by current binding policy, and
unbound/missing entries cannot be reconstructed. When the old file is readable,
the output also names the affected entries. It then requires interactive
confirmation; `--yes` is the only non-interactive authorization. Declining
leaves every byte unchanged.

### 6.3 Generation algorithm

Both the silent empty-file path and explicit regeneration use one generator:

1. obtain one §3.2 inventory observation; unreadable/dangling paths are retained
   as diagnostics but do not become entries;
2. process readable bindings in sorted-normalized-path order. Derive each local
   label by NFC-normalizing and trimming the path basename; if that yields an
   empty string (including a filesystem root), use the literal `folder`. If the
   label is already assigned, append ` (2)`, ` (3)`, and so on, choosing the
   first unused candidate. Before each assignment, truncate the base by Unicode
   scalar value—not UTF-16 code unit or byte—to leave room for the complete
   suffix and keep the final label at most 128 scalars. Collapse home paths to
   `~/…`, and store the complete `snapshotPreCatalogPolicy` result from §5;
3. order generated entries deterministically by normalized path, and set
   `globalOptions` to the complete product defaults from §5;
4. validate and serialize the whole schema-v1 file;
5. for first-run generation, acquire the existing catalog lock, re-read
   `config.json` immediately before publication, and publish only if it is
   still absent using an atomic no-replace publication; if another generator or
   a hand-authored file won, re-read and adopt the winner instead;
6. explicit regeneration is an Adapter-owned outer loop. Each attempt freshly
   calls `inspectFolderCatalog`, passes that full state to
   `observeFolderGeneration`, prepares the generated bytes and loss description,
   and obtains confirmation. After taking the catalog lock, publication compares
   the attempt's opaque catalog revision with a fresh inspection. On any change
   (a different byte digest or transition to/from the absent/unreadable
   sentinels), it returns `catalog-changed`; the Adapter discards the attempt and
   authorization, re-observes both state and inventory, and re-runs the loss
   description and confirmation. No inventory is frozen across attempts; and
7. publish with the temporary-file, atomic-publication, and directory-durability
   protocol owned by §8.

The silent path is legal only when step 1 found zero discoverable bindings.
Explicit regeneration may include any number of readable bindings and reports
every skipped unreadable/dangling path after publication. The opaque attempt and
successful publication result retain those diagnostics for the Adapter to print;
reporting does not depend on rediscovering a path that regeneration intentionally
removed from the catalog.

The catalog lock is never held while prompting, performing network work, or
creating/removing a binding. Race ordering is:

- binding creation retains §7.1 ordering; if generation publishes first, the
  later locked `recordFolder` adds the root, including when the binding appeared
  after the generation observation;
- untrack retains §7.2 ordering; whichever catalog write publishes first, its
  later locked `forgetFolder` makes the final catalog omit that root; and
- daemon startup follows §7.3: it waits for the authority check and cannot
  begin authenticated runtime work from an unresolved absence.

## 7. Operation semantics

### 7.1 Setup, init, track, and adoption

- Validate/create the local directory through existing guarded flows.
- Remote create and join remain explicit existing transitions.
- Persist and fsync the binding before adding the catalog entry.
- A crash between those steps leaves a valid detached binding, not an orphaned
  remote effect; repair/explicit setup can record it without creating again.
- `recordFolder` is skipped for export's synthetic staging binding.
- Rebind preserves the local catalog entry/options but replaces binding
  identity; scope and old stream state never carry.
- Adoption's lifecycle owner mints a typed `JournalPinnedFolderPolicy` from an
  admitted snapshot and stores it in the adoption journal. It contains the
  catalog byte digest plus all resolved safe fields: `syncGit`,
  `git.incremental`, `respectGitignore`, `noDrift`, and normalized trash days/
  maxBytes. Journal validation owns its closed codec. Resume never re-resolves
  current policy until the physical transaction completes; later edits apply
  afterward.
- Export's staging owner mints a typed `EphemeralExportPolicy` with its current
  synthetic semantics: `syncGit: true`, `git.incremental: true`,
  `respectGitignore: false`, `noDrift: false`, `trash.days: 0`, and
  `trash.maxBytes: 2147483648`. It remains outside catalog membership because
  its synthetic staging binding is not a machine folder. Neither case is
  represented by a generic bypass boolean.

### 7.2 Untrack and manual removal

`rbox untrack` retains its guarded destructive ordering:

1. stop and acknowledge the daemon;
2. remove the proven internal `.rbox` tree;
3. remove daemon runtime;
4. remove the catalog entry; and
5. strictly forget the compatibility row.

A crash leaves a visible missing/detached condition and retry converges. A hand
edit removing a folder does **not** delete `.rbox` or user data. New binaries
stop/skip its daemon at the next safe boundary while retaining desired-state
and binding records as dormant recovery evidence. Re-adding resumes the prior
desired mode; `rbox untrack` is the explicit destructive cleanup.

### 7.3 Daemon and foreground operations

- The runtime boundary consumes one `FolderAdmission` from `FolderInventory`:

  ```ts
  type FolderAdmission =
    | { kind: "admitted"; generation: string; policy: ResolvedFolderPolicy }
    | { kind: "unbound" | "missing" | "detached" | "damaged"; reason: string };
  ```

- Every foreground sync and daemon cycle pins one validated admission after
  acquiring the workspace mutex.
- A concurrent edit applies on the next cycle, never halfway through a
  scan/pull/push.
- A configured folder's effective safe fields are attached without replacing
  runtime-injected `encrypted`, KEK, account/epoch, token, or credential URL.
- A damaged catalog halts before the next pull/publish boundary and surfaces
  the exact error.
- A removed entry stops at daemon startup or the next operation boundary; it
  never triggers binding deletion. Detached bindings permit read-only
  status/doctor/config diagnosis only. `sync`, `pull`, `push`, `start`,
  `recover`, `ignore` mutation, and `include` mutation require the idempotent
  explicit transition `rbox config add <path>`; no command silently re-adds it.
- Boot resume skips missing, detached, and unbound entries.

Daemon construction performs the §6.2 authority check and an admission check
before authenticated runtime work; startup cannot wait for the later ordinary
boundary. Reload copies only the resolved safe policy fields onto the existing
boot object, preserving runtime-injected E2EE/credential fields exactly as the
current `respectGitignore` regression requires. `respectGitignore` hot-applies
with a matcher rebuild; `trash` applies at the next operation boundary;
`noDrift` is a foreground completion concern and causes no daemon transition;
`syncGit` and `git.incremental` changes require an acknowledgement-gated daemon
recycle and uncached rescan. No field mutates an in-flight operation.

### 7.4 Moves and copies

Hand-editing `path` does not silently infer a safe move. The edit represents a
move only when the new path carries a binding whose `rootPath` names the old
path, the old path is absent, and no configured/observed path carries the same
`(workspaceId, deviceId)` pair. Otherwise status reports an ambiguous copy or
rebound condition and no daemon starts.

The first implementation requires an explicit repair/move command to rewrite
`rootPath`, registry state, and daemon runtime key. It must not treat a matching
workspace ID alone as proof because multiple devices may legitimately bind the
same remote folder.

Existing ancestor/descendant and lexical-alias roots remain supported. New
guided setup refuses a newly introduced physical overlap because two new sync
owners over the same bytes would compete, but direct parsing keeps existing
layouts readable and diagnosable.

## 8. Concurrency and durability

- One global config lock serializes CLI mutations.
- Ordinary mutations re-read and compare the source digest immediately before
  atomic publication so an editor change observed since planning is usually
  rejected. This is best-effort stale-edit detection, not true CAS against an
  editor that can race between comparison and rename.
- First publication uses the stronger no-replace rule in §6.3.
- No config lock is held across network calls, daemon shutdown, filesystem
  scans, adoption, scope transitions, or confirmation prompts.
- Readers take no lock and see complete old/new bytes through atomic
  publication.
- Before publication, the catalog owner creates any missing config-directory
  chain without following symlinks. It records exactly which directories it
  created and fsyncs each created child entry bottom-up through the first
  pre-existing ancestor, preserving the landed created-ancestor durability
  contract.
- Every catalog publication calls `fsyncDirectory` after the atomic file helper;
  the helper fsyncs file bytes but does not make the parent-directory update
  durable by itself.
- Folder mutations and scope transactions touch disjoint owned records.

Publication crash recovery has only the prior path state or a complete new
file. A crash before publication leaves the prior state and an ignorable
temporary file. A crash after publication yields the complete valid file if the
directory update survived; if a first publication did not survive, the next
command observes absence and applies §6.2. In particular, when explicit
regeneration started from absence with bindings, loss of its publication cannot
silently rebuild over them: the next command returns to the explicit
regeneration error.

## 9. Protected functionality ledger

| Protected behavior | Owner | Required evidence |
|---|---|---|
| Create vs join and first push/pull ordering | existing setup/init Modules | differential setup/init tests + onboarding rig |
| Binding/stream/device identity | `workspace-config.ts` + reset/state gates | identity byte fixtures, reset compatibility |
| Scope publication seal and journal | `scope/*` + registry witness | scope crash/mismatch matrix |
| Non-empty adoption/collision retention | adoption Modules | adoption resume/crash tests |
| Running/stopped/pull-only/maintenance intent | autostart Modules | desired-state transition tests |
| E2EE runtime attachment survives reload | auth remote + daemon | v0.9.2 regression and daemon reload tests |
| Missing/rebound roots remain visible | binding registry + aggregate status | aggregate health tests |
| Explicit untrack guards and ordering | untrack Module | crash-step matrix |
| Environment drift override | sync completion policy | existing env tests |
| Trash bounds/defaults | workspace config normalization | fieldwise boundary tests |

The sync, encryption, upload, server, and wire protocols are unchanged.

Machine status/doctor JSON schema v1 remains registry/binding-shaped and keeps
its closed `binding` values and remote `name` meaning. Human aggregate output
may add a separate configured-but-unbound section. `rbox config --json` owns a
new schema-v1 folder-intent/status payload including local names, unbound and
detached state; no new enum is inserted into the old schema.

## 10. Requirement challenges

| Requirement | Complexity cost | Decision |
|---|---|---|
| Put workspace IDs in user config | exposes implementation identity and makes hand edits dangerous | rejected |
| Treat folder name as remote identity | collisions/renames could bind wrong data | rejected |
| Make scope a normal override | bypasses prune/journal/publication seal | rejected |
| Config addition auto-creates remote state | passive typo could cause network mutation | rejected |
| Config removal deletes `.rbox` | destructive side effect from text edit | rejected |
| Config membership replaces desired daemon mode | collapses separate crash-sensitive intent | rejected |
| Guess which pre-catalog values were explicit | may change existing sync behavior | rejected |
| Delete `workspace.json`/`workspaces.json` now | active identity and scope-witness ownership remains | not approved |
| Put new folder states into machine JSON v1 | changes a protected closed schema | separate `rbox config --json` surface |
| Keep old binaries working after cutover | retains a second option authority and cross-file convergence machinery | rejected by §14 — pre-2.0 posture, founder 2026-08-11 |

## 11. Implementation slices

1. **DONE — dormant foundation:** strict bounded catalog codecs, path
   normalization, pure fieldwise resolution, authority inspection, atomic
   durable publication, best-effort stale-edit detection, and pure generated
   file construction. It changes no runtime behavior. Some landed code embodies
   the superseded model and is scheduled for exact deletion in slice 3: every
   state variant except `absent | authoritative | damaged`; the second-file
   codec and path plus `parseAuthority`; the second-file half of
   `publishInitialFolderCatalog`; `skipUnavailable` and its refusal branch;
   `authorityActivated`; and their tests.
2. **DONE — merged registry wrapper (`origin/main` `dd189f83a`):**
   `FolderInventory` joins an inspected `FolderCatalogState` and per-root
   binding observations over the existing registry enumeration, preserves that
   enumeration's rows/order and fields, and performs no healing. Its optional
   state parameter, registry-shaped row model, registry/desired enumeration,
   and temporary `legacy` admission reproduce the pre-activation contract; they
   are not the final §3.2 Interface. No command behavior changed.
3. **Atomic activation, complete inventory, generation, runtime switch, and
   repair — one PR:** delete the exact dormant artifacts named in slice 1; make
   the `FolderCatalogState` argument required; remove `legacy`; add the full
   catalog/registry/desired/current-root union, normalized-root deduplication,
   catalog-only rows, overlap classification, readable-binding admission despite
   registry conflict, and `observeFolderGeneration`; add §5 policy snapshotting
   and the §6 outer regeneration loop; then switch setup/track/untrack, ignore
   mutation, foreground runtime, daemon startup/boundaries, boot resume,
   adoption/export witnesses, and human/config status together. The explicit
   move/copy repair command required by §7.4 also lands here. All admission types
   become the closed §7.3 union in this PR. Every affected `docs/CODEMAP.md` line
   is updated in this PR. Every §12 gate, including compiled CLI smoke and the
   onboarding, daemon, and scoped rigs, must pass before this activation PR may
   merge.
4. **Post-activation cleanup only:** delete only code proven unused after the
   activation switch. No ownership change, required repair, or activation
   validation may be deferred to this slice.

The dormant foundation and inventory may land alone because neither changes
behavior. Authority activation may not land partially: all
admission/runtime/lifecycle consumers switch in one reviewed activation PR or
none do. Do not ship a second live authority with ambiguous ownership.

## 12. Validation gates

### Differential and compatibility

- `snapshotPreCatalogPolicy` fixtures cover true, false, omitted, zero, partial
  nested values, malformed trash, truncation, and clamping, with a differential
  against the prior effective policy (§5);
- end-to-end fixtures run generated catalog bytes through strict parsing and
  effective-policy resolution, then differentially compare every resolved field
  with the pre-catalog binding policy; testing `snapshotPreCatalogPolicy` alone
  is insufficient;
- existing JSON status/error/name schemas remain byte-compatible;
- setup, init, track, same-workspace re-track, and rebind preserve the §5 flag

## 13. Retirement and deletion statement

At cutover, new binaries stop reading `syncGit`, `git.incremental`,
`respectGitignore`, `noDrift`, and `trash` from `workspace.json`; their existing
bytes are retained unchanged. Removing those inert fields is a later cleanup
requiring persisted-format, fixture, tooling, and owner evidence.

`workspaces.json` is not approved for deletion. It can retire only after its
scope witness moves, snapshot tooling changes, and aggregate tests prove the
replacement. Daemon desired rows remain independent. No command, alias, import,
export, build path, package path, automation, or documentation is approved for
deletion except the exact dormant artifacts in §11.

## 14. Pre-2.0 breaking-simplification decision record (2026-08-11)

### 14.1 Product decision

**Founder ruling, 2026-08-11:** before the 2.0 release, breaking changes are
preferred over compatibility machinery. There are three real external users;
the founder can manually fix or re-onboard each. Clean design wins over
scaffolding whose only purpose is keeping an older binary working after the
new authority activates.

Historical note: this full supersession removes the earlier authority marker,
compatibility projection, strict migration-evidence readers, and
`legacy`/`candidate` catalog states. Those terms describe rejected history
only; they are not part of the resulting design.

### 14.2 Posture scope

This is a general pre-2.0 posture and is re-evaluated at 2.0 GA. It changes only
the compatibility decision; every normative correctness and safety requirement
lives exclusively in §§3–13.

### 14.3 Client-skew story

The founder upgrades or re-onboards the three external users. The server wire
protocol is untouched, so skew is confined to a user running a pre-cutover CLI
against a machine already using `config.json`. That old CLI continues reading
the retained option bytes in its local binding and misses later catalog edits
until upgraded. This limited behavior gap is accepted before 2.0; no local
cross-version convergence mechanism is built.
