Native Git may refresh shared-index timestamps; shared-file metadata immutability is not claimed. Preserve exact staging modes/stages/flags, current encrypted artifact descriptors, `indexTree` grammar (`40-hex` or `raw:<sha256>`), ordinary raw-index identity, absent-index behavior, scoped refs, resolution stability checks, scratch cleanup and recovery. ## Executed normalization and compatibility experiments

`notes/289/normalization-probe.ts.txt` creates independent ordinary, explicit-split and `core.splitIndex=true` repositories, both merged and unmerged. Three independent copies per case run native split detection, conditional normalization, clear-resolve-undo, stash and write-tree. It records hashes and source index/config/shared-index membership.

1. Explicit split normalization is deterministic in these repetitions; ordinary non-split unmerged output retains the original raw hash.
2. **Naive normalization is insufficient when `core.splitIndex=true`.** With ambient repository config, private commands still produce split indexes and create new source shared-index files. `normalization-probe.txt` records this counterexample.
3. The initial six-case probe passed with `core.splitIndex=false` alone (`normalization-private-config-probe.txt`), but that is **not sufficient evidence for configured index extensions**. Review added partial resolve-undo, a real filesystem-monitor hook and untracked-cache configuration. With those inputs, disabling split during detection can hide an actual dependency in Git's in-memory post-read conversion. `review-round1-probes.txt` records that counterexample, and `review-detection-probes.txt` records the corrected native query.
4. The read-only dependency query pins `core.splitIndex=true`, `core.fsmonitor=false`, `core.untrackedCache=keep`. Git returns the actual shared-index OID for a split input and an all-zero `sharedindex.000…` sentinel for an ordinary input. Recognize that sentinel explicitly. All private **writes** instead pin `core.splitIndex=false`, with the same monitor/cache policy. The query and writes do not alter persistent config. Repeated partial-conflict tests validate ordinary configured-split input, actual split input, hook non-invocation and unchanged source bytes/dependency names (not a shared-index timestamp guarantee).

`notes/289/old-reader-probe.ts.txt`, run with Bun 1.4.0, uses the unchanged baseline reader. An ordinary unmerged artifact still applies with the identical original raw identity. A previously captured split artifact cannot apply without its missing shared index. Replacing only its index artifact/identity with the native normalized representation lets the unchanged reader apply successfully, reproduce exact stage entries and compute the same new raw identity. All stage objects in this compatibility probe are deliberately retained in committed history, separating index format from design 288's missing-object defect. Evidence: `old-reader-probe.txt`.

The `.ts.txt` files are diagnostic source evidence, excluded from product lint/type inventories; copy to an owned temporary `.ts` path with resolved imports if rerunning. These are bounded experiments, not proof for all index extensions, Git versions, old released binaries or concurrency. Permanent differential tests below are required.

## Small implementation

### Shared private snapshot primitive

Reuse native Git and current file-copy/scratch ownership. A narrowly scoped `copyPortableIndex(repoDir, source, privateDestination): Promise<boolean>` will copy an existing index to caller-owned scratch, query `rev-parse --shared-index-path` under the **private** `GIT_INDEX_FILE` and the read-only configuration described above. For every nonempty response, require basename `^sharedindex\.([0-9a-f]{40})$`; reject an unexpected shape. Recognize only its all-zero OID as ordinary. Only an actual dependency invokes native `update-index --no-split-index` followed by `update-index --clear-resolve-undo`. Return whether normalization was required, because identity must preserve the legacy non-split raw fallback exactly.

A small `private-index.ts` is justified only as the shared owner of this complete copy/detect/normalize operation used by capture and identity; it is not a generic Git runner, snapshot framework, state machine or additional journal. Its `Never:` header forbids source-index/config rewrites, shared-index content rewrites and shared-index creation. Publication, refs and persistence remain outside its Interface. Callers own directory lifetimes. No manual parsing/re-encoding of the index or copied shared-index sidecar escapes onto the wire.

The same module exposes `gitWithPrivateIndex(repoDir, privateIndex, args)` as owner of private-index process configuration; callers do not assemble environment or configuration arrays. All subsequent Git commands using the private copy use explicit `-c core.splitIndex=false -c core.fsmonitor=false -c core.untrackedCache=keep`. This applies even to already non-split private copies: repository config must not reintroduce a dependency or write shared files during a read/projection. The argument changes only that invocation, not live repository configuration. Do not alter the shared live-index `clearIndexResolveUndo` helper globally; capture can issue the equivalent private command with this explicit policy.

A detection/normalization failure rejects capture before artifact publication and retains existing cleanup. Identity must not interpret it as an absent/empty index. Identity propagates snapshot failure instead of returning a plausible identity for an unreadable dependency. Divergence-cache callers already catch identity failures; capture and resolution propagate failure and retain their cleanup. Review must assess direct apply callers as part of the compatibility gate. Failed `write-tree` after a successful snapshot remains the normal raw fallback.

### Capture integration: `capture.ts`

Replace its raw source copy with the shared private snapshot operation, then preserve the current clear-resolve-undo policy using the private command override. Apply the same snapshot preparation to `opts.resolution`'s live comparison copy. Run stash only against the private index (including the existing absent-index path) with split creation disabled. Preserve recorded refs, operation-state snapshots, unique scratch pins, bundle increment behavior and collector cleanup.

When `indexTree` is raw/unmerged, call existing `stagedIndexObjectOids` for **ordinary capture as well as resolution**. Parse the mode explicitly; skip mode `160000` gitlinks because the superproject does not own those submodule commits. Retain nonzero blob OIDs and sparse-directory tree OIDs, deduplicate before object verification, and preserve native object-existence checks and failure. Keep existing successful write-tree pinning for resolution; ordinary merged capture remains on its current stash closure in this bounded slice. Do not silently ignore malformed nonempty staged-entry records or missing required objects.

### Identity integration: `identity.ts:indexTreeOfPath`

Use the same private copy/detection/normalization before write-tree, disabling private split writes. A successful write-tree returns exactly its existing tree OID. On failed write-tree:

- If the input was non-split, return exactly `raw:${hashFile(originalInput)}` as before, regardless of mutations to the private probe copy.
- If the input was split, hash at the exact boundary **copy → read-only detect → no-split normalization → clear resolve-undo → hash → write-tree** and return the existing `raw:` form. Save that hash before attempting write-tree so a failed probe cannot perturb fallback identity.

Capture computes the identity of its already portable staged artifact, so split/unmerged sender identity and receiver identity must agree on the same standalone serialization. The capture copy follows the same normalization/REUC ordering before stash. A failed stash/write-tree on the tested unmerged inputs leaves the normalized bytes unchanged. Ordinary input raw identity deliberately retains legacy REUC bytes, even though capture already stripped those bytes historically. Clear-resolve-undo and split/unmerged extensions are covered by permanent differential tests; if they do not agree, stop and revise this design rather than add another raw format. Existing volatile-stat overcapture behavior is not broadened into a semantic-index migration.

## Accepted scope: new captures; historical repair is separate

No old artifacts are deleted or reinterpreted. Ordinary merged/unmerged artifacts retain current reader behavior; normalized artifacts are consumed by the unchanged baseline reader. An old split artifact missing its shared dependency cannot be reconstructed from its index bytes alone. Old publishers can still emit that broken representation until upgraded.

A **local fingerprint cache schema bump** invalidates cached pre-change identities so they are recomputed. Its only responsibility is memo invalidation; it is not a completed-artifact-repair marker. This is one adjacent line in `fingerprint.ts` and creates no new wire format or durable authority.

However, that bump does **not** repair every historical artifact: a merged split index has the same write-tree OID after normalization, so `carryMatrixMatches` can still carry an old dependent artifact. The bounded code fix therefore repairs newly captured sections, not automatically every prior split section. Root accepts the firm boundary: this slice guarantees portable newly captured sections; historical artifact repair is a separate implementation slice. That follow-on must validate an existing forced-recapture/republish operation or a bounded artifact-portability migration before use. No per-repository repair flag, per-tick base-artifact download, or endless forced recapture belongs here. Completing design 289 does not imply fleet-wide repair of already published split sections.

Inspection rules out treating cache absence as a durable completed-repair marker: `loadGitDivergenceCache` collapses missing/mismatch/corrupt cases into the same empty cache, status/pull can populate that cache before push, and `RepoCaptureAttempt.classify` writes its cache before capture/publication. Although existing `forceCapture:true` bypasses carry, a failed or interrupted capture could consume a cache-based one-time trigger without repairing the artifact. A commit-bound repair trigger is required; it must not be inferred from a successful read cache. Historical repair is therefore explicitly deferred to its own accepted design, not left as an unresolved requirement for this bounded slice.
