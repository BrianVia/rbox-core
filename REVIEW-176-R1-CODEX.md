# Adversarial design review — 176, round 1 (Codex)

The field problems are real, but the design is not safe to implement as written. The `keep-mine` mechanism contradicts its own accepted-ACK invariant, applies design 130's narrow no-P manual authority to branch shapes that require durable artifacts, and has no resolve-time candidate on which to run the claimed v6 proof. The held-skip merge defect is real for the field topology but is not universal, and both UX rewrites need a stronger compatibility boundary than a frozen textual prefix.

## Findings

1. **BLOCKER — the proposed CLI-side clear occurs before publication, contradicting the accepted-ACK invariant it claims to reuse.**

   Evidence: the semantic contract says pending and sidecars clear “in the same accepted-ACK transition 174-B already uses” (`docs/design/176-wedge-ux-keep-mine.md:39-45`), but the mechanism clears `gitPendingRemote`, partial, attempt, and the apply deferral in the resolver and only then requests a push (`docs/design/176-wedge-ux-keep-mine.md:62-74`; the test repeats “cleared → next push” at `:129-132`). The shipped supersession path does the opposite: planning keeps P authoritative (`src/cli/sync-git/plan.ts:688-704`), the remote commit happens at `src/cli/sync/push.ts:647-675`, and only the accepted path deletes pending and supplies explicit null partial/attempt plus a predecessor-bound deferral clear (`src/cli/sync/push.ts:685-750`). A capture, upload, 422, 409, state-save failure, process crash, or daemon stop between the draft's clear and later push therefore loses the durable P/sidecar retry state without publishing the confirmed replacement.

   The workspace mutex does not close that gap. `gitResolveCmd` runs inside `withWorkspaceSyncMutex` (`src/cli/git-cmd.ts:712-729`), and that helper releases when its callback returns (`src/cli/sync-mutex.ts:313-323`); it cannot make a later daemon push atomic with an earlier state clear.

   Minimal fix: retain P and every sidecar in the resolver. Persist a token-bound, single-use `keep-mine` authorization/intent, make push planning capture and validate the authorized candidate, and consume the intent plus clear pending/partial/attempt/apply-deferral only in the accepted ACK packet. If the command executes a push synchronously instead, expose an already-locked push entry point and still keep P durable until ACK; do not nest the workspace mutex or pre-clear state.

2. **BLOCKER — design 130's no-P manual clause is not authority for an arbitrary current-local snapshot; branch absence/presence crossings need A/P handling.**

   Evidence: §2.3 says the manual candidate can retain all current local refs “never to invent P/A artifacts” and cites the already-terminal positive-branch clause as sufficient (`docs/design/176-wedge-ux-keep-mine.md:62-69`). The cited clause is explicitly limited to an already-terminal positive branch with positive previous BASE (`docs/design/130-follower-branch-hygiene.md:304-309,949-956`). Code enforces `before !== null && requested !== null` for `manual/no-p` (`src/cli/sync-git/base-composer.ts:380-398`), and the composer test proves absent→present remains pending (`src/cli/sync-git/base-composer.test.ts:277-301`). A positive BASE branch that is now locally absent needs an A witness even when the physical ref is already absent (`src/cli/sync-git/follow.ts:843-869`; `src/cli/sync-git/branch-transition.ts:211-237`). A local branch present over logical absence cannot manufacture no-P authority; the manual present path is the P/K path (`src/cli/sync-git/branch-transition.ts:238-290`). Non-branch tag/stash changes separately require safe-ref witnesses (`src/cli/sync-git/base-composer.ts:443-482`).

   Deferring BASE advancement to the existing publisher ACK only partly solves this: publisher ACK can add/advance present refs, but deliberately retains omitted prior refs (`src/cli/sync-git/base-composer.ts:335-347,504-505`). It cannot record a keep-local deletion by itself.

   Minimal fix: retract the blanket no-P/no-A claim and specify every ref shape. Prefer leaving BASE unchanged until the accepted publisher ACK for positive additions/advances, while adding a confirmed locked A settlement (or a new ACK-bound confirmed-absence authority) for deletions. If the resolver instead composes the whole local candidate before push, it must use the complete design-130 A/P/K and safe-ref protocols, including journal recovery and crash settlement—not just `manual/no-p`.

3. **BLOCKER — a workspace mutex plus a show-me snapshot is not design 130's `lockedProof`.**

   Evidence: design 130 says `lockedProof` is a prepared Git ref transaction, “not an in-process mutex,” whose reservations remain held through the state-generation CAS; a no-P decision verifies exact locked live N through that CAS (`docs/design/130-follower-branch-hygiene.md:403-418`). The draft specifies only the workspace mutex and manual candidate (`docs/design/176-wedge-ux-keep-mine.md:62-69`). The existing show-me identity is an unlocked observation of refs, reflogs, HEAD, index, op-state, stash, and oracle receipt (`src/cli/git-cmd.ts:105-117,328-366`). Current `take-theirs` obtains manual terminal decisions only through follow's ref-transaction path (`src/cli/sync-git/follow.ts:821-869`) and rechecks the snapshot in the lock-bound second proof (`src/cli/git-cmd.ts:937-970`).

   Minimal fix: state normatively that a keep-local BASE effect is committed through prepared verify/A/P/safe-ref reservations held across generation CAS, with a journaled recovery receipt. Better, remove pre-push BASE composition from `keep-mine` and use the ACK-bound intent described in finding 1, limiting any resolver-time artifact work to the exact confirmed-absence cases from finding 2.

4. **BLOCKER — there is no resolve-time CANDIDATE, so the “174 v6 proof reused as a REPORT” cannot run.**

   Evidence: design 174 defines capture and outbound normalization as producing exact final candidate C and makes only C the proof subject (`docs/design/174-apply-side-perf-and-held-repo-livelock.md:294-324,370-386`). Code agrees: `provePendingSupersession` requires both `pending` and `candidate` `GitSection`s and reads candidate HEAD, scope, config, op-state, refs, stash, and index presence (`src/cli/sync-git/pending-supersession.ts:156-190`). Planning calls it only after concurrent capture and final normalization (`src/cli/sync-git/plan.ts:900-918`).

   Resolve's `buildSnapshot` stages the incoming section and constructs a `SnapshotIdentity`; it never captures or normalizes local state into a `GitSection` (`src/cli/git-cmd.ts:369-479`). That identity lacks bundle/artifact fields, canonical config, and ref scope. The cheap pre-probe cannot substitute because it is admission-only, while final-C proof is deliberately later (`src/cli/sync-git/plan.ts:688-713,908-918`). This also leaves the “and/or apply deferral” case undefined: `incomingFor` falls back to BASE when no P exists (`src/cli/git-cmd.ts:208-212`), whereas v6 runs only for an actual pending section.

   Minimal fix: define the report subject. Either capture and normalize an exact local candidate before displaying confirmation, or extract a shared typed semantic-candidate assessor and build its complete live projection under the mutex. Specify that the force/discard assessment applies only to actual P and is vacuous when P is absent. The eventual push must re-assess the exact final captured candidate before spending the authorization.

5. **MAJOR — v6's boolean is neither a loss report nor the directional predicate promised by `keep-mine`.**

   Evidence: the draft promises a bounded list of exactly what old P contains that local lacks and requires force only for those non-subsumed lanes (`docs/design/176-wedge-ux-keep-mine.md:52-61`). The current API returns one boolean and collapses every validation error/exception to `false` (`src/cli/sync-git/pending-supersession.ts:156-190`), so it cannot enumerate simultaneous failures or distinguish definite loss from indeterminate proof.

   More fundamentally, v6 has exact/symmetric publication gates that are not the directional P→local loss relation described by the UX: exact config and op-state (`src/cli/sync-git/pending-supersession.ts:167-169`) and exact index presence before the clean-and-plain exception (`:184-187`). P-absent/local-present lanes can therefore fail v6 even though P contains nothing in that lane to discard, leaving the CLI either demanding force without naming incoming loss or falsely describing local-only state as discarded incoming state.

   Minimal fix: share low-level validators but define a separate exhaustive `assessPendingDiscardLoss(P, localCandidate)` returning typed per-lane `subsumed | not-subsumed | indeterminate` results. Make one-sided absence directional, explicitly define the pending-index loss rule, bound rendering without dropping the force decision, and treat indeterminate evidence as a typed refusal unless the design explicitly authorizes forcing unverified loss. Keep automatic v6's final-publication predicate separate.

6. **MAJOR — “reuse show-me's token flow verbatim” does not bind all inputs to the promised report.**

   Evidence: the token identity contains refs/reflogs/HEAD/index/op-state/stash and an oracle receipt (`src/cli/git-cmd.ts:105-117,328-366`), but no canonical config, ref scope/capture policy, or config ownership/read disposition. Those are candidate/proof inputs (`src/cli/sync-git/pending-supersession.ts:167-169`). A config-only change after display can therefore leave today's token unchanged while changing the discard assessment or final candidate. The second snapshot check in `gitResolveCmd` only helps for fields that participate in `SnapshotIdentity` (`src/cli/git-cmd.ts:829-834`).

   Minimal fix: bind the token to a hash of the complete typed report/candidate inputs, including canonical config and its read/ownership disposition, effective ref scope, repo kind/identity, and actual pending key. Recompute immediately before recording authorization. Add config-only, scope-only, and pending-key-change races; the old token must produce snapshot mismatch rather than a differently reasoned action.

7. **MAJOR — the held-skip merged blocker is real for the field shape, but the claim that it affects every pending held repo is false and the proposed neutralization can hide independent composer failures.**

   Evidence: apply conditionally appends the synthetic `{provenance:"composer", reason:"artifact"}` only when `composedFollow.disposition === "pending"` (`src/cli/sync-git/apply.ts:1300-1321`), and the allowlist rejects any reason outside local commits/stash (`src/cli/sync-git/held-skip.ts:35-38`). This confirms the field hypothesis when an allowlisted held ref also prevents BASE composition. It is not universal: the integration test creates a receiver-only local branch, persists pending plus a local-commits attempt, and the next apply successfully reports one held skip (`src/cli/sync-git/follow.test.ts:1243-1271`); the skip predicate itself requires P (`src/cli/sync-git/apply.ts:1123-1127`). That extra branch is held physically but is absent from both BASE and candidate, so the composer can remain terminal.

   Composer pending is also not always a consequence of an allowlisted hold. Independent safe-ref witness/scope failures and wrong-ref-class/checkout-incomplete conditions all collapse to the same disposition (`src/cli/sync-git/base-composer.ts:443-494`). Ignoring the generic composer blocker whenever any allowlisted classifier exists can suppress a productive or safety-required retry for up to the one-hour floor. The rig's present assertion is explicitly opportunistic and only forbids a full re-follow (`scripts/rig/scenarios/git-held-livelock.ts:173-186`), so its observed zero was not causal evidence.

   Minimal fix: narrow the diagnosis to the field topology and preserve typed `composedFollow.holds`. Permit skip only when every composer hold maps ref-for-ref and code-for-reason to an already-recorded allowlisted causal blocker; any unmatched composer hold remains ineligible. Add the exact pre-rewrite field topology plus a coexisting unmatched composer-hard-hold control. The requested non-opportunistic rig assertion is good, but the generic “composer-pending + local-commits” unit test is not sufficient.

8. **MAJOR — freezing only textual prefixes does not preserve the grammars current consumers use.**

   Evidence: the draft says additions occur only after a colon while listing `git-sync followed` as frozen (`docs/design/176-wedge-ux-keep-mine.md:100-105`), but the shipped followed line has no colon (`src/cli/sync-git/apply.ts:1331`), nor does the applied family before its optional parenthetical (`src/cli/sync-git/apply.ts:1535-1540`). Tests consume entire lines exactly (`src/cli/sync-git/follow.test.ts:268-278`; `src/cli/sync-git/git-sync.test.ts:519-527,566-582,609-617`), and a scheduler test parses the whole suffix of `git-sync applied (.+)` as the repo name (`src/cli/sync-git/git-sync.test.ts:654-665`). Appending prose preserves grepability but changes that consumer's data. Rig checks are mostly tolerant word-boundary/prefix regexes (`scripts/rig/scenarios/git-held-livelock.ts:116-123`; `scripts/rig/scenarios/git-commit-propagation.ts:194-208`), so “rig green” does not prove all consumers compatible.

   Minimal fix: inventory the exact ~12 old→new lines in the design and define a closed grammar/delimiter for each. Safest is to retain existing machine lines byte-for-byte and emit separately typed human companion lines. Otherwise migrate every parser and exact consumer deliberately. Expand test 5 to name follow/follow-matrix, git-sync scheduling/concurrency, sync-cmd routing, doctor redaction, shared rig fixtures, git-held-livelock, git-commit-propagation, and git-shapes.

9. **MAJOR — changing the shared `git deferred` line risks the daemon/doctor privacy boundary and duplicates an existing reason presentation.**

   Evidence: `renderGitDeferralLine` returns one exact line (`src/cli/status-view.ts:421-440`) and is shared by both status surfaces (`src/cli/status-cmd.ts:678-692,784-794`) and durable daemon logging (`src/cli/daemon/daemon.ts:218-253`). Doctor's fail-closed privacy parser end-anchors that exact grammar (`src/cli/doctor-cmd.ts:129-170`). Appending the proposed sentence to the same physical line makes it unrecognized and dropped; embedding a newline in the shared renderer creates an untyped continuation after a timestamped Git-family record, which the redactor deliberately discards (`src/cli/doctor-cmd.ts:171-190`). Exact renderer tests pin the current text (`src/cli/status-view.test.ts:60-75`).

   The bounded reason table already exists with `label`, `text`, `repair`, and an unknown fallback (`src/cli/status-view.ts:266-300`), and `rbox status --git` already prints its text and repair (`src/cli/status-cmd.ts:678-692`). The draft does not say whether that surface receives duplicated guidance.

   Minimal fix: keep `renderGitDeferralLine` and daemon records byte-stable. Add a status-only companion-help renderer based on the existing presentation table, emitted as a separate indented console line at both intended human status call sites, and specify `--git` deduplication plus JSON non-change. If same-line prose is required, update the doctor's closed grammar and privacy tests before shipping. Add exact status, daemon durable-line, and doctor fail-closed snapshots.

## Claims that survived checking

- The command parser already accepts `keep-mine`, and the implementation returns the typed unsupported result; `--force-discard-incoming` is present in dispatch/help (`src/cli/main-dispatch.ts:511-523`; `src/cli/git-cmd.ts:740-756`; `src/cli/help-registry.ts:196-203`). The design's `git-cmd.ts:536` anchor is stale, but the claim is true.
- The automatic v6 refusal on a non-fast-forward same-name branch is real: branch proof is equality-or-ancestor only and errors fail closed (`src/cli/sync-git/pending-supersession.ts:141-153,171-190`).
- The field-shaped composer blocker can explain `skippedHeld=0`: the generic artifact blocker is merged before attempt persistence and is excluded by the current allowlist (`src/cli/sync-git/apply.ts:1312-1321`; `src/cli/sync-git/held-skip.ts:35-38`). Its universality and the proposed untyped neutralization do not survive review.
- Advertised-based tombstone authoring/retention is shipped in the outbound normalizer, and accepted ACK stores advertised state; this does not make a pre-ACK clear safe (`src/cli/sync-git/publisher-tombstones.ts:50-80,107-121,171-192`; `src/cli/sync/push.ts:685-759`).
- The focused existing suites used for this review are green: `bun test src/cli/sync-git/held-skip.test.ts src/cli/sync-git/base-composer.test.ts src/cli/status-view.test.ts src/cli/doctor-cmd.test.ts` passed 73 tests.
