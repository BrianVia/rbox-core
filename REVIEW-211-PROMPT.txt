## What I want you to attack, in priority order

1. **Crash and concurrency safety of the registry.** Read
   `src/cli/binding-registry.ts` against `src/engine/git/lockfile.ts`
   (`acquireLock`/`OwnedLock`) and `src/engine/fsutil.ts` (`writeFileAtomic`),
   and against the prior art in `src/cli/autostart-cmd.ts`
   (`desiredRecordLock`/`mutateDesiredRecord`), which this deliberately mirrors.
   Can a concurrent CLI process lose an entry, resurrect a forgotten one, read a
   torn file, deadlock, leak a lock, or leave a `.rbox-tmp-*` file behind? Is
   swallowing write errors ("best effort") defensible here, or does it hide a
   failure the user needed to see?

2. **The migration/seeding claim.** Reads return the union of the persisted
   entries and `readDesiredDaemonRows()`. The design claims this makes existing
   users converge with no manual step AND cannot resurrect an untracked
   workspace, because `untrack` calls `removeDaemonRuntime(root)`. VERIFY that
   against the actual code (`src/cli/daemon/runtime-state.ts`,
   `src/cli/autostart-cmd.ts`) — is there any path that leaves a desired row
   behind after an untrack, or any path that writes a desired row for a
   workspace the user has forgotten? Also check `rememberResolvedRoot`'s
   staleness/freshness shortcut for a case where it never converges.

3. **Trust-gate preservation.** `collectMachineTriage` previously gated the
   ambient daemon record on process liveness AND boot-id binding before
   believing any field. Confirm the rewrite did not weaken that, and that the
   new `mode` / `lastSyncedAt` / `problem` fields are only ever populated from a
   record that cleared the gates.

4. **Test isolation.** The registry is host-global. Confirm no test in the
   repository can write into a developer's real `~/.rbox/workspaces.json`, given
   the `RBOX_HOME` → `RBOX_TEST_BINDING_REGISTRY_DIR` → `$HOME` precedence in
   `bindingRegistryDir()` and the preload. Try to find a suite that escapes it.

5. **Surface correctness.** `--all` + PATH mutual exclusion, `--json` shape
   stability, and whether `rbox untrack <root>` against a root whose `.rbox` is
   already gone can be tricked into removing something it should not (note the
   symlink/realpath guards in `untrack-cmd.ts` are BYPASSED on that path —
   is that safe, given nothing is deleted from the workspace tree?).
