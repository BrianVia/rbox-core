## Round 1 — codex (sol)

Reviewed against `main` at `dfed0053` (2026-07-10). The draft's core distinction remains valid: a mutex serializes writers, but only the daemon owns watcher-derived O(change) truth, so design 93 does not by itself eliminate the value of delegation. The implementation plan is nevertheless not runnable as written.

1. **BLOCKER — design 93 invalidates Layer B's lock ownership and post-ack fallback protocol.** Foreground `push` currently takes the workspace mutex before auth and before calling `push` (`src/cli/main-dispatch.ts:227-247`); foreground pull/sync does the same (`src/cli/sync-cmd.ts:55-84`). Every daemon pump iteration independently acquires that mutex, and leaves its request queued while contended (`src/cli/daemon.ts:419-432`). Therefore a CLI cannot acquire its current top-level lock and then ask the daemon to service a delegated operation: the daemon cannot start until the CLI releases. Delegation must be selected before CLI mutex acquisition; for a delegated operation the daemon must be the sole top-level mutex owner for decision -> filesystem mutation -> state transition, consistent with design 93 (`docs/design/93-git-config-sync.md:163-205`). Unsupported flags must select the local path before either RPC or lock acquisition.

   The failure proof in design 85 is now wrong as well. A CLI fallback gets only 16 x 50 ms before `another sync is in progress` (`src/cli/sync-mutex.ts:54-95`), so the proposed post-ack socket-close path cannot blindly start a concurrent full-scan push and satisfy section 7.2 while a live/stuck daemon still owns the lock. The mutex deliberately forbids the claimed daemon/CLI CAS race. Specify a state machine: pre-ack failure may choose the local owner; after ack the client must receive a terminal result, receive cancellation-and-lock-release acknowledgement, wait for proven daemon death/stale-lock reclamation, or return an explicit indeterminate/retry result. A thin daemon RPC is still the only proposed O(change) foreground path, but the mutex—not a 409—is now its ownership/failure boundary.

2. **BLOCKER — Layer A currently destroys its own unconditional deep-scan backstop.** Section 3.1 says the dircache applies to every full-scan site (`docs/design/85-incremental-scan.md:163-168`), while the invariant and rollout rely on `doDeepScan` being cache-bypassing and catching Layer A errors (`docs/design/85-incremental-scan.md:105-107,420-425`). Today `doDeepScan` merely supplies a fresh *hash* cache to the same `scanManifest` (`src/cli/daemon.ts:1144-1149`). If dircache reuse is added inside `scanManifest` by default, deep scan can reuse the same stale directory listing and cannot discover the omitted entry. Add an explicit unpruned-directory mode for deep scan, assert zero listing reuse, and rebuild (not trust) the dircache from that walk. The same distinction must govern watcher-degraded recovery (finding 8).

3. **BLOCKER — P0.2 is not runnable and its proposed estimator is unsound.** Shipped `ScanStats` has only walked dirs, file/cache counts, and aggregate phase timings (`src/engine/manifest.ts:32-55`); every directory is still unconditionally read (`src/engine/manifest.ts:263-271`). There is no previous scan start, directory mtime, racy-clean eligibility, reused-dir count, or per-directory cost. Moreover `eligible directory fraction x aggregate readdir time` is not a valid savings estimate because directory costs are highly skewed. Before Layer A, add a measurement-only harness/state that records per-dir mtime, prior scan boundary, eligibility, and readdir duration across consecutive scans. Report both eligible count and the **sum of readdir milliseconds for eligible directories**, plus instrumentation cost and projected dircache bytes. Run quiescent pairs and mutation cohorts (in-place file edit, create, delete, same-dir/cross-dir rename, ignore-rule change) on both fleet filesystems. Gate on weighted observed reclaimable wall time, not directory fraction.

4. **BLOCKER — P0.3 is also not runnable, so watcher-loss risk is presently unmeasured.** `doDeepScan` overwrites `this.manifest` without retaining or diffing the pre-scan incremental manifest and emits no drift counter (`src/cli/daemon.ts:1144-1149`). Implement the measurement before claiming a 24-hour soak: snapshot incremental truth; produce a fresh hash-cache- and dircache-bypassing manifest; compare path/type/SHA/size/mode/symlink target; classify added/deleted/modified; and record watcher health/error generation, time since safety scan, event counts, and ignore-rule changes. Exclude or separately classify paths mutating during the scan, otherwise churn is mislabeled as a dropped event. Report per APFS/ext4: deep scans, scans with drift, paths by class, and maximum inferred drift age. The full-scan stat/hash/stat fix in finding 6 (or a quiescent reverify) is prerequisite to credible attribution.

5. **MAJOR — P0.1 instrumentation already shipped, but it does not measure the decomposition promised by the draft.** `ScanStats` and its timers exist (`src/engine/manifest.ts:32-55,58-87,263-346`), CLI scans attach them through `recordDetails` (`src/cli/sync.ts:96-97,172-175,201-208,386-400`), and `RBOX_METRICS`/serialization are live (`src/cli/metrics.ts:17-27`; `src/engine/phase-report.ts:165-171,199-212`). Section 8.1 must therefore say collect/validate the shipped instrumentation, not ship it.

   It still cannot split `sort+alloc`: allocation, path construction, readlink, cache lookup, and loop overhead remain an unlabelled residual. It uses `Date.now()` around each tiny matcher call and file stat (`src/engine/manifest.ts:281-318,341-347`), including two matcher evaluations for some directories, which is quantized and may perturb a 100k-entry walk. Stats are also cumulative across recovery rescans through one `deps.scanStats` (`src/cli/sync.ts:133-135,172-175,201-208`), so one details object need not describe one scan. Before Layer A measure metrics-on versus metrics-off overhead and per-scan boundaries. On daemon-stopped local full scans on APFS and ext4, collect at least five warm steady samples and three genuinely cold samples where feasible: scan wall, readdir/stat/matcher/hash/sort, `residual = wall - component sum`, counts/cache-hit ratio, and p50/p95/range. The Layer A gate should use current measured reclaimable milliseconds, not the v0.9.10 2.3 s estimate.

6. **MAJOR — the mandatory torn-full-scan fix has not shipped and is now reinforced by design 92.** Incremental `statHashEntry` performs the stability check, but the full scan still records pre-hash size/mode/mtime immediately after `hashFile` with no second stat (`src/engine/manifest.ts:350-359`). Thus section 3.1's fix-in-passing remains a correctness prerequisite, not completed context. Give it its own implementation/test gate before Layer A or drift measurement: append/replace/chmod during deferred hashing must never create a mixed tuple. Design 92 makes this especially material because downstream encryption integrity cannot repair a poisoned scan tuple.

7. **MAJOR — the current scan-site model and citations undercount work.** Current direct daemon sites are startup (`src/cli/daemon.ts:246-249`), ignore-event rebuild (`src/cli/daemon.ts:685-693`), post-pull refresh (`src/cli/daemon.ts:784-794`), full scan (`src/cli/daemon.ts:1138-1142`), and deep scan (`src/cli/daemon.ts:1144-1149`), not the cited lines. But “five sites” is not the actual scan count: daemon `doPull` calls shared `pull`, which scans before apply (`src/cli/sync.ts:218-236`), then daemon scans again after pull; `pushManifest` recovery can also call `rescanForRetry` (`src/cli/sync.ts:201-208,489-497`). CLI push scans at `src/cli/sync.ts:380-400`, and sync composes pull plus push. Rewrite the baseline as scan *paths per operation/recovery*, since phase-0 samples and delegation savings otherwise compare unlike cycles. `applyWatchEvents` itself remains genuinely O(change), now at `src/engine/manifest.ts:94-110,134-182`.

8. **MAJOR — watcher self-clear semantics are stale and unsafe if a pruned scan counts as recovery.** On watcher error, current code permanently sets `watcherHealthy = false`, increments a generation, and pins safety scans to the 60 s floor (`src/cli/daemon.ts:285-297,326-346`). A generation-stable full/deep scan now clears only the user-visible `watcherDegraded` flag (`src/cli/daemon.ts:451-457,878-884`); it does not restore watcher trust. Design 85 must distinguish visible self-clear from health/cadence. More importantly, a dircache-pruned safety scan must not be called the “completed full-tree scan” that clears the warning unless the design explicitly proves cached-listing coverage is sufficient. Conservatively require an unpruned readdir pass for self-clear while retaining `watcherHealthy = false` and the pinned cadence. Do not gate delegation on the self-cleared presentation flag.

9. **MAJOR — directory-mtime correctness is bounded healing, not the absolute invariant currently claimed.** Ordinary APFS/ext4 namespace operations do update parent directory mtime: same-dir/case-only rename invalidates one parent, cross-dir move invalidates both, and a moved subtree has a new relpath cache key. The two-second racy-clean rule plausibly covers ordinary same-tick aliasing. But userspace on macOS/Linux can restore a directory mtime after add/remove/rename; equality plus age alone (`docs/design/85-incremental-scan.md:120-150`) can then reuse a stale listing. The design handles mtime-preserving *file* writes with future ctime (`docs/design/85-incremental-scan.md:255-266`) but never scopes directory timestamp restoration. Either explicitly exclude adversarial timestamp restoration and weaken “NEVER silently missed” to “healed by the next unpruned deep scan,” or add a stronger directory identity/version mechanism. Ctime is useful evidence but is not a universal delete/recreate proof.

10. **MAJOR — the `(mtime,size,ctime)` HashCache change is an existing CLI correctness change, not merely Layer A support.** Current cache remains `(mtime,size)` (`src/engine/hashcache.ts:10-21,33-37`) and its safety comment relies on watcher invalidation, which foreground CLI scans do not have. A same-size write followed by mtime restoration can therefore reuse stale SHA today. Specify cache format/version detection (the current JSON has no header), whole-cache migration/discard behavior, all lookup/record signature changes, and ordering. This should ship and be tested independently before Layer A/delegation, rather than be left embedded in section 9's resolved prose.

11. **MAJOR — the daemon safety/deep sites do not emit the phase-0 data the design says will self-report in the field.** `beginReport` is wired around daemon push/pull, but `doFullScan` and `doDeepScan` call `scanManifest` with neither report nor `ScanStats` (`src/cli/daemon.ts:1138-1149`). P0.2/P0.3 concern precisely those steady daemon ticks. Add a bounded, non-PII stats/report or dedicated soak logger at those sites; define whether the following queued push shares or starts a report. Without that, CLI P0.1 is runnable but the daemon gates are not.

12. **MAJOR — several user-visible delegation decisions remain for an implementer to improvise.** Section 3.2 explicitly defers supported flag/config enumeration (`docs/design/85-incremental-scan.md:240-244`), while section 9 leaves pull delegation and progress fidelity open (`docs/design/85-incremental-scan.md:428-444`). The protocol also lacks request authentication/peer-credential mechanics behind “same uid,” simultaneous client semantics (join one cycle versus queue distinct cycles), mapping an `opId` to the exact pump iteration/result, cancellation/disconnect behavior, daemon pull-only mode behavior (`requestPush` suppresses pushes at `src/cli/daemon.ts:383-391`), stdout/stderr/log compatibility, and socket cleanup/collision rules across stale daemons. Resolve these before implementation. In particular, “set booleans in `want`” coalesces requests and cannot by itself prove which request owns which terminal result.

13. **MINOR — platform acceptance needs native semantic probes, not only an end-state soak.** The shipped watcher targets Apple Silicon macOS and Linux x64/arm64 (`src/cli/watcher.ts:188-200`). On actual APFS and ext4, record Node-observed directory `mtimeMs`/ctime/inode before and after create, unlink, same-dir rename, cross-dir rename, atomic replace, rapid repeated operations, clock steps, and APFS case-only rename. Also test relpath cache eviction for moved/deleted subtrees. The functional soak in section 7 can then validate the measured assumptions rather than merely hope its scheduling hits timestamp races.

14. **MINOR — update stale references before spec-first dispatch.** Examples: `applyWatchEvents` is at `src/engine/manifest.ts:94-110`, watcher error handling at `src/cli/daemon.ts:285-297`, safety scheduling at `src/cli/daemon.ts:326-346`, self-clear at `src/cli/daemon.ts:878-884`, native pruning at `src/cli/watcher.ts:258-260`, and ignore-layer safety healing is documented at `src/engine/ignore.ts:146-150,179-184`. `pushManifest` no longer begins near the draft's cited `sync.ts:391`. These are not cosmetic where the old citation now hides changed semantics (mutex ownership, self-clear, nested scans).

**Verdict: REVISE.** Layer B remains architecturally defensible, but must be redesigned around the shipped workspace mutex and a non-racing failure protocol. Layer A must preserve a truly unpruned deep-scan/self-clear path, and no Layer A implementation should begin until P0.1 is collected with overhead/residuals and new P0.2/P0.3 instrumentation produces weighted APFS/ext4 evidence.

## Round 2 — codex (sol)

Re-verified against the current branch at `ee5e3708`, including designs 95 and 96. The revision resolves Round 1 findings 2, 3, 5, 7–11, 13, and 14 at design level, and substantially resolves the normal-case ownership half of finding 1. Findings 4, 6, and 12 are not fully resolved; the current lock degradation behavior also exposes a new ownership hole.

1. **BLOCKER — P-1 still cannot pass its own chmod gate because the specified second-stat predicate ignores chmod.** The current full-scan pending tuple contains `size`, `mode`, and `mtimeMs`, then `drainHashes` records all three without a second stat (`src/engine/manifest.ts:238-244,351-362`). The revision correctly promotes a second stat, but says only “on mtime/size shift” to defer. A chmod changes mode and ctime, ordinarily not mtime or size, so the required test “chmod injected between stat and deferred hash must yield a deferred path” would still bake SHA from one instant with mode from another (or retain the pre-hash mode, depending on the implementation). P-1 must define one exact stability predicate and use the post-hash tuple: at minimum file type, size, mtime, ctime, and permission mode must match; replacement detection should include inode/device where the platform exposes them. The incremental `statHashEntry` guard has the same current mtime/size-only limitation (`manifest.ts:210-233`), so “same contract as midwrite” is not sufficient unless that contract is strengthened too. Round 1 finding 6 remains open.

2. **BLOCKER — the delegation proof assumes an exclusive mutex, but current design-93 code deliberately has an unlocked degraded mode.** `acquireWorkspaceSyncMutex` returns an acquired-looking handle with no lock when the lock primitive is unsupported (`src/cli/sync-mutex.ts:42-55,85-88`); both CLI and daemon then continue through the legacy state path. In the proposed alive-but-opaque arm, the CLI’s “ordinary mutex acquisition attempt” can therefore succeed immediately with a degraded handle while the live daemon is still mutating, and LOCAL races the delegated owner. More generally, the claim that every delegated operation has exactly one exclusive owner is false on a workspace where locking has degraded. The hello/ack must carry a positively established exclusive-lock capability/mode, delegation must be rejected when it is unavailable, and every post-ack fallback must distinguish a real owned lock from `workspaceSyncMutexDegraded`; a degraded acquisition can never prove that no daemon op is in flight. This is a new blocker exposed by verifying the revision against the current mutex implementation.

3. **MAJOR — P0.3 still misclassifies ordinary scan-time churn as watcher loss.** The revision separately classifies paths in `pendingEvents`/`deferredRetryPaths` or whose classification re-lstat mismatches the fresh entry. That does not cover an add or delete occurring during the deep scan before its watcher event is delivered: an added path can be present both in the fresh entry and at re-lstat, while a deleted path can be absent both from the fresh manifest and at re-lstat. Both are legitimate scan-window races but are counted as drift. Snapshotting the old manifest is not a temporal snapshot of the filesystem. Use watcher generations covering the entire scan plus a settled post-scan drain/reconciliation, or run a second quiescent verification/diff before attributing non-racing drift. Until then the 24-hour drop-rate evidence and acceptance gate 5 are not trustworthy. Round 1 finding 4 remains partially open.

4. **MAJOR — same-euid peer authentication is specified without a runnable runtime mechanism.** The repository runs Bun/TypeScript and currently has no socket peer-credential binding; the only FFI seam is the narrow `bun:ffi` declaration used by I/O priority. Neither the Node/Bun `net.Socket` API nor the proposed newline protocol itself supplies `SO_PEERCRED`/`getpeereid`. The design must choose and gate a concrete implementation per shipped target (for example a reviewed Bun FFI shim with exact Linux/macOS structs and lifecycle, or a small native helper), state failure behavior, and add native integration tests. Otherwise an implementer must improvise a security-critical part of Round 1 finding 12, and “drops any connection whose euid differs” is not yet implementable from the enumerated work.

5. **MAJOR — pre-bind cancellation cannot safely “deflate” the shared `want` boolean with the proposed bookkeeping.** Current `want.push`/`want.pull` are also set by watcher events, remote catch-up, safety/deep scans, and pull follow-up (`src/cli/daemon.ts:387-395,445-461`). The proposed delegated map records only delegated requesters, so “clear the corresponding want flag if no other requester needs it” cannot tell whether an ambient daemon cause also needs that op. Clearing it can consume a real watcher/catch-up wakeup; never clearing it makes cancellation spuriously run an operation, contradicting `{cancelled} -> LOCAL` as proof that nothing remains in flight for that request. Track per-kind demand provenance/generations (ambient plus delegated), or give delegated requests a separate queue that is merged into pump selection without erasing ambient demand. Round 1 finding 12 remains partially open.

6. **MINOR — the delegated `sync` result is underspecified across its two bound iterations.** The map pops pull and then push, but the terminal result is described as built from “that iteration’s outcome,” which is only the final push. Current sync has meaningful pull actions/conflicts and can fail on either leg. Specify an op-scoped aggregate accumulated across both bindings, including which leg failed, pull actions/conflicts, final sequence/commit status, reports, and output/JSON parity; otherwise gate 6’s schema-equivalence requirement is not testable.

Verdict: REVISE
