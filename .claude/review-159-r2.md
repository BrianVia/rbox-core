# Adversarial design review — 159 typeahead directory picker (round 2)

## Verdict: CHANGES-REQUIRED

V2 correctly retracts the existence-validation claim, preserves setup's
nonexistent-path/create-confirm contract, selects an available custom-prompt
primitive, and names the six real PTY flows. The remaining findings are
narrower transition defects in the new v2 mechanism: the empty state lists the
wrong directory, the pinned literal row conflicts with Tab completion, and an
uncached directory still needs an explicit loading policy.

## Findings

1. **HIGH — Empty input derives the base's parent as `listDir`, so the initial picker shows the wrong directory.**

   V2 defines `resolved = resolve(base, input)` and then chooses `dirname(resolved)` whenever the input does not end in `/` (`docs/design/159-typeahead-directory-picker.md:27-32`). The initial input is empty, and `"".endsWith("/")` is false. For a base of `/work/project`, the formula therefore produces `resolved=/work/project`, `listDir=/work`, and an empty filter. The advertised `use this directory` row points at `/work`, and the child rows are `/work`'s children, even though bare Enter separately returns `/work/project` (`docs/design/159-typeahead-directory-picker.md:49-55`). Treat empty input as a path boundary (`input === "" || input.endsWith("/")`) and require an initial-state test that proves both the displayed directory and bare-Enter answer are `base`; the current comparator-only empty-input test does not pin this derivation (`docs/design/159-typeahead-directory-picker.md:86-87,121-123`).

2. **BLOCKER — The pinned use-input row and the required Tab completion cannot both use the stated highlighted-row rule.**

   Literal compatibility depends on the synthetic `use "<resolved>"` row being first after any nonempty edit, so immediate Enter returns the typed literal (`docs/design/159-typeahead-directory-picker.md:41-45,103-105`). But Tab is defined as completing the *highlighted child's* path (`docs/design/159-typeahead-directory-picker.md:33`), while that first/highlighted row is synthetic, not a child. If Tab acts on row 1, typing a partial `pro` completes to `pro/`, not the ranked child `project/`; if the initial highlight instead moves to `project`, immediate Enter no longer has the pinned-literal behavior on which `typo-no-phantom` and the unchanged literal flows rely. This is also the exact interaction the new `type, Tab, Enter` flow is supposed to prove (`docs/design/159-typeahead-directory-picker.md:106-108`). Specify separate executable defaults—for example, edits reset Enter's selection to the use-input row while Tab targets the best matching child—or another explicit highlight/key transition that preserves both contracts.

3. **HIGH — Synchronous cached filtering does not eliminate the loading window on the first visit to a `listDir`.**

   Filtering an already loaded listing synchronously is sound, but v2 still requires one `readdir` for every distinct directory, including rapid descent (`docs/design/159-typeahead-directory-picker.md:62-68`). Unless that read is explicitly synchronous, each cache miss has a pending listing despite the absolute claim that Enter has no loading window (`docs/design/159-typeahead-directory-picker.md:56-58,126-127`). A custom `@inquirer/core` prompt also cannot await its way to serialized key processing: `useKeypress` invokes the handler without awaiting it (`node_modules/@inquirer/core/dist/lib/use-keypress.js:9-13`). An asynchronous completion additionally needs generation/abort ownership and a render-triggering state update; changing only the visible-input state to its existing value is a no-op in core (`node_modules/@inquirer/core/dist/lib/use-state.js:8-14`). The real rig sends a literal and Enter in consecutive tmux calls with no picker-settle barrier (`scripts/ux/tui.ts:146-155`; for example `scripts/ux/flows/tilde-expansion.flow.ts:12-14`). Choose and test one policy: blocking `readdirSync` on cache miss, or explicit pending/generation/render state with row-1 Enter semantics and Tab/navigation gating. The latter requires narrowing the “ONE piece of state” and “no loading window” claims.

4. **HIGH — “Symlinks-to-directories are listed” is incompatible with `Dirent`/`lstat` classification plus “never followed for listing.”**

   `readdir(..., { withFileTypes: true })`/`lstat` can establish only that an entry is a symbolic link; for a symlink whose target is a directory, `isDirectory()` is false. Determining that it is specifically a symlink *to a directory* requires following it with `stat`, and descending via `readdir` follows the path as well. That followed-`stat` behavior is exactly what the current setup caller uses to accept a directory (`src/cli/setup-cmd.ts:619,713-718`). V2 nevertheless promises all three of: list symlinks-to-directories, use lstat-style dirents/the downstream acceptance rule, and never follow them for listing (`docs/design/159-typeahead-directory-picker.md:50-54`). Pick an implementable policy: follow candidate symlinks with `stat`, list every symlink and leave target rejection to the caller, or omit them from suggestions while retaining literal access through row 1. The required symlink test must pin the chosen policy (`docs/design/159-typeahead-directory-picker.md:124-125`).

5. **MED — `opts.default` is still modeled as a resolution base, changing the exported `promptPath` contract outside today's production call pattern.**

   Current `promptPath` treats `default` as the input widget's bare-Enter answer, but resolves every actual answer against the injected `opts.cwd` (`src/cli/prompt.ts:83-97`). V2 instead sets `base = opts.default ?? cwd` and resolves every typed relative value beneath that base (`docs/design/159-typeahead-directory-picker.md:27-30`). With `{ cwd: "/injected", default: "/suggested" }`, typing `child` currently returns `/injected/child`; v2 returns `/suggested/child`. A relative default is worse: bare Enter is specified to return that relative `base`, and `resolve(base, input)` falls through to the process CWD rather than the injected CWD. Production happens to pass `default === cwd` at all three sites (`src/cli/init-cmd.ts:83`; `src/cli/setup-cmd.ts:657,710`), so this is narrower than round 1, but it contradicts the unchanged-signature and byte-parity contracts (`docs/design/159-typeahead-directory-picker.md:21-23,110-115`). Keep `cwd` as the immutable resolution base and model `default` separately as the empty-input answer, or explicitly redefine and test the exported behavior.

## Verified claims with no finding

- **`@inquirer/core` is available in-tree.** `@inquirer/core@11.2.1` is locked (`bun.lock:163`), its installed public entry point exports `createPrompt`, `useKeypress`, `useState`, `isTabKey`, and the other required primitives (`node_modules/@inquirer/core/dist/index.d.ts`), and `prompt.ts` already imports `ExitPromptError` from it (`src/cli/prompt.ts:19`). Relative to the current tree, the picker introduces no new package requirement.
- **The create-confirm/no-phantom contract is preserved by row 1.** Setup still receives an arbitrary resolved answer, calls `stat`, asks before `mkdir` only on `ENOENT`, and performs no remote mutation before that local loop completes (`src/cli/setup-cmd.ts:707-731`). `typo-no-phantom` types two nonexistent literals, observes both create prompts, and asserts zero workspaces (`scripts/ux/flows/typo-no-phantom.flow.ts:8-21`). Subject to finding 2's key-selection rule, v2's row-1 answer reaches that contract unchanged.
- **The flow inventory is now accurate.** The six named flows are the prompt-driving flows, and the existing bare-Enter and literal transcripts are compatible with the intended row-1 rule once findings 2 and 3 specify selection during edits/cache misses. Cached filtering itself is synchronous after a `listDir` has loaded; the remaining issue is only first-load/re-anchor behavior.
