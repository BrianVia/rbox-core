# Design 160 adversarial review — round 2

**Verdict: CHANGES-REQUIRED**

The v2 mechanisms close most round-1 gaps. In particular, `readOnly` is feasible without changing matcher decisions: a cache miss already obtains and retains the tracked paths in memory (`src/engine/ignore.ts:593-609`), and the only workspace mutation on that successful path is the `writeTrackedCache` call at line 608, whose implementation creates/writes/renames under `.rbox/state/git-tracked` (`src/engine/ignore.ts:650-680`). Threading `readOnly` through `BuildIgnoreMatcherOptions` to `loadTrackedRepoSet` and suppressing only that call preserves the existing hit, miss, corrupt-cache, and unavailable-index branches. The remaining issues are narrower contract edges in the new three-set, budget, and shared-step mechanisms.

1. **BLOCKER — A tracked file ignored by the root `.gitignore` creates a fourth, inverse policy set that A/B/C cannot represent.**

   Evidence: the root `.gitignore` is loaded into the legacy layer, but `legacyDecision` still attributes a matching root rule to source `.gitignore` (`src/engine/ignore.ts:281-288,342-351`). Tracked evaluation is enabled when `respectGitignore` is true and disabled when it is false (`src/engine/ignore.ts:293-295`). Consequently, `ignores()` re-includes a tracked root-ignored file in the true mode because its decision source is `.gitignore` (`src/engine/ignore.ts:426-436`), while the false mode applies the same legacy exclusion without tracked protection. The existing root-`*.txt` test demonstrates the true-mode half of this behavior (`src/engine/ignore.test.ts:296-310`).

   This directly falsifies v2's claims that root-ignored files are never synced under option 2, that the policy delta is nested-only, and that root `.gitignore` exclusions all belong to set A (`docs/design/160-gitignore-sync-preview.md:17-27,56-63`). The missing outcome is “skipped only with `respectGitignore: false`.” It is user-visible, not merely attribution: the proposed “either way” and “additionally skips” copy can report the wrong choice for a tracked file.

   Required change: define all four outcomes of the two-policy comparison, including the inverse set, and specify honest copy when that set is nonempty. Make the parity fixture's tracked-but-ignored case specifically include a file matched by the **root** `.gitignore`; the current fixture requirement at design lines 108-115 can be satisfied only with a nested rule and miss this edge.

2. **HIGH — The shared budget has no seam into matcher preparation, and a partially prepared matcher has no sound decision contract.**

   Evidence: v2 introduces only `buildIgnoreMatcher(root, { ..., readOnly: true })` (`docs/design/160-gitignore-sync-preview.md:65-71`), and the actual `BuildIgnoreMatcherOptions`/matcher construction has no budget or cancellation result (`src/engine/ignore.ts:207-223,266-279`). Construction eagerly completes repository discovery and then tracked-set loading before returning the boolean-only matcher (`src/engine/ignore.ts:473-480`). Those internals are synchronous and unbudgeted: discovery recursively uses full-array `readdirSync` (`src/engine/ignore.ts:570-590`), and each repository load may perform `rev-parse`, stat/cache work, and `ls-files` (`src/engine/ignore.ts:593-609`). A clock/budget injected into `runGitignoreStep` cannot account for or stop those operations through the stated resolver API. The dedicated preview walk's `fs.opendir` does not make the preceding discovery streaming, so the promised large-directory allocation test at design lines 120-121 can still fail before that walker starts.

   More importantly, merely stopping discovery or tracked-set loading on cap would make decisions unsound. An undiscovered or not-yet-loaded repository is absent from `trackedRepos`; `isTracked` then returns false (`src/engine/ignore.ts:384-395`), so tracked ignored files can be classified as untracked. The matcher API has no “preparation incomplete/unknown” state to prevent presenting those partial decisions as production decisions.

   Required change: specify a shared-budget resolver-preparation seam, make discovery streaming too, and define the cap result before decisions are exposed. A cap during discovery or between repository probes must either abort classification with an explicit incomplete result or install fail-closed unknown repository state; it cannot silently return an ordinary matcher. Add cap tests at both boundaries, not only during the inventory walk.

3. **MEDIUM — The entry cap counts work operations, but the capped copy claims distinct inventory entries.**

   Evidence: the budget definition charges “one dirent processed OR one git repo probed,” while the output says `previewed the first 20,000 entries` (`docs/design/160-gitignore-sync-preview.md:84-90`). Under the stated architecture, repository discovery precedes the dedicated inventory walker (`src/engine/ignore.ts:473-478`). A filesystem dirent examined during discovery can therefore be charged again when the preview walker encounters the same path, and a repository probe consumes a unit despite not being an inventory entry at all. For example, 15,000 root dirents charged during discovery can leave only 5,000 traversal observations before the 20,000-unit cap, yet the copy would claim that 20,000 entries were previewed.

   Required change: separate the internal work-unit budget from the distinct inventory-entry count used in output, or integrate discovery and inventory so each tree entry is charged/classified once. The cap test must assert both counters and the rendered sampled count; “entry accounting covers discovery + git probes + walk” alone (`docs/design/160-gitignore-sync-preview.md:120-121`) would lock in the overclaim.

4. **HIGH — The direct-init call site can pass a relative root to the preview even though first sync resolves it against the injected `cwd`.**

   Evidence: at the direct-init seam, `promptMissing` can already have a raw relative `flags.root`, so the path-prompt normalization branch is skipped (`src/cli/init-cmd.ts:43-54,82-84,102-107`). The eventual plan resolves that value with `path.resolve(cwd, flags.root ?? cwd)` (`src/cli/init-plan.ts:168-170`; pinned at `src/cli/init-plan.test.ts:91-97`). By contrast, setup's `dir` comes from `promptPath`, which returns `path.resolve(opts.cwd, ...)`, and setup validates or creates it before its gitignore prompt (`src/cli/prompt.ts:83-101`; `src/cli/setup-cmd.ts:710-730,796-800`). The proposed `runGitignoreStep(root, deps)` signature does not state that direct init must perform the planner-equivalent resolution first (`docs/design/160-gitignore-sync-preview.md:46-52`). A literal `runGitignoreStep(next.root, deps)` can therefore preview a path relative to the process cwd while first sync targets a different path relative to the injected cwd.

   Required change: make the seam require an absolute, planner-resolved root. Direct init should pass `path.resolve(cwd, next.root ?? cwd)` (or the helper should accept `cwd` and apply exactly the planner rule); setup can pass `dir` unchanged. Add a live-call-site test using a relative `--root` and an injected `cwd` different from `process.cwd()`.

The helper's policy return mapping itself is sound: init can store the returned `"true" | "false"` directly, while setup can convert it with `=== "true"`; `workspaceFlags` deliberately represents false by absence and `resolveInitPlan` defaults absence to false (`src/cli/setup-cmd.ts:60-70`; `src/cli/init-plan.ts:178-186`). Targeted baseline verification completed with `47 pass, 0 fail` for `src/engine/ignore.test.ts` and `src/cli/init-plan.test.ts`.
