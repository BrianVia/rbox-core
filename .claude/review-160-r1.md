# Design 160 adversarial review — round 1

**Verdict: CHANGES-REQUIRED**

The action-loop idea is implementable, and `GITIGNORE_CHOICES` is indeed the two-row exported constant at `src/cli/init-cmd.ts:111-122`. The design is not implementable under its stated parity, cap, and purity contracts yet. The main blockers are that the two policies are described more broadly than the engine implements, and the production matcher performs unbounded work plus cache writes while it is being constructed.

1. **BLOCKER — The proposed “skip” versus “sync-everything” contrast is not the engine's actual policy delta.**

   Evidence: `buildIgnoreMatcher` always adds the workspace-root `.gitignore` to `legacyIg` (`src/engine/ignore.ts:281-288`). With `respectGitignore: false`, `ignores()` still calls `fullDecision(..., false)`, whose legacy decision includes that root file (`src/engine/ignore.ts:413-437`). Design 72 explicitly preserves the workspace-root `.gitignore` as legacy behavior and adds nested `.gitignore` honoring under the flag (`docs/design/72-respect-gitignore.md:61-76,124-127`). Builtin and `.rboxignore` exclusions also apply in both modes. Consequently, option 2 does not “sync gitignored files too” in general, and the proposed `sync-everything would additionally upload ~X` line measures only the paths newly excluded by the `respectGitignore: true` machinery, principally nested rules. A root-ignored file remains excluded in both modes; builtin `.env`, `node_modules/`, and `dist/` also remain excluded unless a valid `.rboxignore` negation rescues an overridable rule.

   Required change: define the preview as three explicit sets—always skipped by rbox policy, skipped only when nested gitignore honoring is enabled, and synced under either choice—or formally expand this design to change the underlying policy semantics and labels. The latter would violate the current non-goal of no semantic/default changes and needs a separate product decision. Do not call the second result “sync-everything” unless the engine is changed to make that true.

2. **BLOCKER — The production resolver is callable with a root before workspace creation, but it is not read-only in the required mode.**

   Evidence: `buildIgnoreMatcher(root, { respectGitignore: true })` needs no workspace config, so pre-workspace invocation is syntactically possible (`src/engine/ignore.ts:207-223,279`). However, `respectGitignore: true` enables tracked evaluation (`src/engine/ignore.ts:293-295`). Matcher construction discovers Git repositories, runs `git rev-parse`/`git ls-files`, and on a cache miss calls `writeTrackedCache` (`src/engine/ignore.ts:473-479,593-609`). That writer creates `.rbox/state/git-tracked` and writes/renames a cache file (`src/engine/ignore.ts:650-680`). This directly contradicts design 160's “No writes, no state; pure read + print” contract at line 51 and could create `.rbox` in a direct-init target before a workspace exists.

   Required change: specify and test a read-only tracked-set provider/cache mode that preserves the same tracked/untracked decisions without creating or mutating `.rbox`. “Extracting the seam is part of implementation” is not enough because cache behavior affects the purity contract. Add a before/after filesystem snapshot test, including a real Git repo with an index and no pre-existing `.rbox`.

3. **HIGH — The advertised entry/time caps do not currently bound the resolver phase, and “2s hard wall clock” is not enforceable as written.**

   Evidence: before a preview walker can inspect its first entry, matcher construction calls the synchronous recursive `discoverGitReposSync` with no entry/depth/deadline budget (`src/engine/ignore.ts:473-478,570-590`). It may then make synchronous Git subprocess calls with a 50 MiB output buffer (`src/engine/ignore.ts:593-608,636-639`). The scanner's own walker is likewise not early-stoppable: `runWalk` and `walk` have no visitor/budget return contract (`src/engine/manifest.ts:485-640,655-659`). A dedicated walker using `readdir` also allocates an entire directory listing at once (`src/engine/manifest.ts:524-540`), so “20k entries” does not bound a single enormous directory's listing cost. No cooperative JavaScript deadline can preempt one blocked filesystem call or `spawnSync`, so 2 seconds can only be a best-effort deadline unless subprocess and I/O architecture changes.

   Required change: put one shared budget over resolver preparation, Git trackedness work, and traversal; define exactly what consumes an entry; use streaming `opendir` (or explicitly accept the per-directory allocation); and call the time bound a cooperative deadline with overshoot semantics. If a true hard deadline is required, use abortable/asynchronous subprocesses and state the remaining uninterruptible filesystem limitation. Tests must put a large/pruned tree and nested Git repo in front of the preview, not merely cap a mock walker after matcher construction.

4. **HIGH — The current resolver exposes inclusion booleans, not the pattern attribution required by the output contract.**

   Evidence: `IgnoreMatcher` exposes `ignores`, directory-prune decisions, trackedness, and an unevaluated-repo safety query, but no matched rule, source layer for a positive decision, or grouping key (`src/engine/ignore.ts:191-205`). The internal `RuleDecision` carries only `ignored` and a coarse source, not the winning pattern (`src/engine/ignore.ts:248-264,342-423`). `effectiveIgnoreRules` is not a substitute: it reads only root `.gitignore` and root `.rboxignore`, omitting nested `.gitignore` files (`src/engine/ignore.ts:686-705`). Therefore `+N more patterns` and a pattern-ranked summary cannot be produced from the shared resolver without a new provenance API or a drifting second implementation.

   Required change: choose and specify the summary key. If it is an actual winning pattern, extend the authoritative decision path to return stable rule identity/base/source while keeping `ignores()` as a wrapper. If it is top-level skipped subtrees/paths, change the copy from “patterns” to “groups/paths” and define aggregation. The parity test must exercise the same decision API used by `scanManifest`, not merely compare two independent walkers that happen to import the same module.

5. **HIGH — Reusing the scanner walker cannot produce the promised ignored-directory counts/sizes.**

   Evidence: the real scan checks `matcher.prunes()` and immediately skips an ignored directory before descending (`src/engine/manifest.ts:572-585`). Thus it cannot report `node_modules/ (~9,400 files)` or bytes below any pruned directory. Reusing it with only an “early-stop visitor,” as design 160 lines 79-83 propose, does not change that fact. A preview walker that descends into ignored directories can estimate those counts, but it is deliberately not walker-parity with the scanner and will spend its budget in the very trees the scanner avoids.

   Required change: resolve the open decision in the design: use a dedicated bounded inventory walker, share the authoritative per-path decision/provenance seam, and explicitly state that preview traversal differs by descending into skipped directories for estimates. Define whether an ignored directory itself counts as one skipped item or whether descendants consume the budget and contribute to file/byte totals. Also define treatment of symlinks, special files, unreadable directories, and paths that disappear during the walk.

6. **MEDIUM — `@inquirer/select` supports an action value, but not a truly “non-answering row.”**

   Evidence: the project wraps `@inquirer/prompts` select directly (`src/cli/prompt.ts:18-40`) and resolves `@inquirer/select@5.2.1` (`bun.lock:179,185`). Every enabled choice has a `value`; Enter calls `done(selectedChoice.value)`, switches the prompt to `done`, and renders the selected choice as the completed answer (`node_modules/@inquirer/select/dist/index.d.ts`, `node_modules/@inquirer/select/dist/index.js`). A separator or disabled row cannot run an action. Therefore a preview row can cleanly return a distinct sentinel to an outer loop, but the terminal transcript will first show “Preview what each choice syncs…” as a completed select answer and then render a new select. It is non-policy at the application layer, not non-answering at the widget layer.

   Required change: state this transcript contract explicitly and accept it (optionally set a truthful `short`, such as “Previewing…”), or specify a custom prompt if the row must act without completing the widget. Add a rendering/transcript-level test or a deliberately factored wrapper test; a mocked select that returns a sentinel alone cannot verify the visual contract under attack.

7. **MEDIUM — The claimed shared wizard step and existing “info-then-reprompt” pattern do not exist in the form described.**

   Evidence: interactive init assigns the raw string returned by its select directly to `next["respect-gitignore"]` (`src/cli/init-cmd.ts:102-107`). Setup owns a separate select and converts the string to boolean inline (`src/cli/setup-cmd.ts:796-800`); `SETUP_GITIGNORE_CHOICES` is only an alias of the constant (`src/cli/setup-cmd.ts:902`). There is no current gitignore choice mapper or shared step module. Existing wizard loops do reprompt after subflow failure/back navigation—for example enrollment (`src/cli/setup-cmd.ts:521-577`) and the workspace parent loop (`src/cli/setup-cmd.ts:107-120`)—but there is no established informational select action with the widget behavior above. Current tests pin the two arrays independently (`src/cli/init-cmd.test.ts:22-35`, `src/cli/setup-cmd.test.ts:114-127`); they do not pin a common mapper.

   Required change: name the shared helper/module to be introduced, its return type (`"true" | "false"`, never the preview sentinel), and injected dependencies (`select`, preview computation, stderr writer/clock/budget). Both prompt sites must call that helper with the already-resolved root. Keep `GITIGNORE_CHOICES` two-valued, compose a separate three-row prompt list, and test both live call sites so setup cannot bypass the loop or convert the sentinel as a policy.

8. **HIGH — The no-root `.gitignore` copy claims exhaustive knowledge that a capped/effective walk may not have.**

   Evidence: design 160 simultaneously promises recursive discovery, an exact-looking `found 14 .gitignore files across subfolders`, `+N more patterns`, and termination at the first 20,000 entries/2 seconds (`docs/design/160-gitignore-sync-preview.md:16-17,41-50`). Once capped, neither the number of files nor the number of omitted patterns is known. Moreover, `.gitignore` files below a parent pruned by Git semantics are not consulted by the real resolver (`src/engine/ignore.ts:321-339,440-452`; `docs/design/72-respect-gitignore.md:129-134`). Counting those physical files would describe rules that cannot affect sync; excluding them means “recursively find” is not a physical-tree count. Builtin-pruned directories create the same distinction.

   Required change: define “found” as either encountered physical files or effective rule files. Prefer effective/encountered copy tied to the sample, e.g. `among 20,000 previewed entries, found 14 effective .gitignore files in subfolders; none at the root`. Never print `+N more patterns` unless N is actually known; otherwise use `additional rules may exist beyond the preview limit`. Add capped and uncapped no-root fixtures, including a `.gitignore` beneath an excluded parent, so the copy cannot overclaim.

9. **MEDIUM — The required parity test is under-specified and can pass while the user-facing comparison is wrong.**

   Evidence: the scanner's inclusion result combines file-versus-directory handling, `prunes()`, tracked-file protection, hard excludes, builtin rules, root legacy `.gitignore`, nested `.gitignore`, and `.rboxignore` rescue (`src/engine/manifest.ts:572-638`; `src/engine/ignore.ts:413-460`). A single vaguely described “skip-set EQUALS scanner skip-set” has no defined universe because the manifest contains syncable files/symlinks but not directories or special files, and a capped preview sees only a sample. It also covers only the recommended policy, while finding 1 shows that the user-facing delta between both choices is the risky part.

   Required change: define parity on an uncapped fixture's inventory of syncable entries: for each sampled file/symlink, preview classification under each policy must equal inclusion under `scanManifest` using the corresponding production matcher options. Include root and nested rules, a tracked-but-ignored file, an untracked ignored file, builtin `.env`, `.rboxignore` negation beneath an ignored parent, a symlink, and a pruned directory. Separately test cap mechanics and sampled-copy honesty; do not mix truncation into the semantic oracle. Also assert zero network calls and zero filesystem mutations by preview.

Baseline verification: `bun test src/cli/init-cmd.test.ts src/cli/setup-cmd.test.ts src/engine/ignore.test.ts src/cli/sync/sync.test.ts` completed with **152 pass, 1 skip, 0 fail**. This establishes that the cited current contracts/tests are green; it does not validate design 160's new behavior.
